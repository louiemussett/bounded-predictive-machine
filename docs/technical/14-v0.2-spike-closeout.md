# v0.2 Spike Closeout

## Purpose

This document summarizes v0.2 as a non-LLM cognitive runtime spike.

v0.2 was not a polished product release. It was a rapid implementation spike to
test whether the bounded predictive runtime can become more inspectable and
useful without adding an LLM, web access, autonomous external actions, or real
document editing.

## Source Precedence

The source hierarchy remains unchanged:

1. Prototype 3 root `Source Documents/` files are the current source of truth.
2. `Source Documents/1-17/` is Prototype 2 supporting prior design detail.
3. `Source Documents/V0 - V9/` is Prototype 1 historical implementation
   lineage.

v0.2 implementation work should remain subordinate to the Prototype 3 design.
Where the runtime adds spike-level mechanisms, those mechanisms are provisional
implementation experiments, not changes to the source hierarchy.

## What v0.2 Added

v0.2 added a runnable, inspectable local runtime around the existing bounded
loop:

- CLI execution for one manual loop.
- Readable JSON output by default.
- Human-readable summary output with `--summary`.
- Optional JSONL persistence with `--save`.
- Lightweight JSON Schema validation for current records.
- Explicit uncertainty gate behavior.
- Abstention and clarification-style records.
- Transparent evidence scoring.
- Belief update/no-update confidence fields.
- Local JSONL memory retrieval without embeddings.
- Optional memory use in `run-once` with `--use-memory`.
- Capped, tokenized, deterministic memory search.
- Summary reporting for retrieved memory.

These additions did not change the core v0.1 principle: signal does not directly
become belief, belief does not directly become action, and actions must pass
safety checks before they can be treated as selected or safe.

## What the Runtime Can Now Do

The runtime can now:

- Run one deterministic manual text loop from the CLI.
- Create a generic prior-based prediction before interpreting the signal.
- Wrap manual text as a signal without treating it as truth.
- Interpret the signal deterministically.
- Assess categorical evidence quality.
- Add transparent score components to evidence.
- Produce belief update or no-update records.
- Produce no-action, abstention, or clarification-style records when evidence
  is insufficient.
- Check candidate write actions against local boundary rules.
- Create outcome and memory trace records.
- Link the loop into an ordered `LoopRecord`.
- Persist records to local JSONL files when explicitly requested.
- Search prior JSONL traces by record type, loop id, and keyword tokens.
- Include retrieved memory in the loop chain when explicitly requested.
- Report what happened without using an LLM to narrate or infer missing reasons.

## What Remains Deliberately Rough

The following areas remain intentionally spike-level:

- Evidence scores are simple deterministic heuristics.
- Belief confidence changes are provisional, not a final probabilistic model.
- Interpretation is rule-like and shallow.
- Memory retrieval is keyword/token based.
- JSON Schemas are minimal and not final contracts.
- Persistence is append-only JSONL without replay semantics.
- Action selection is narrow and mostly demonstrative.
- Safety policy is deterministic but not a complete operational policy.
- The CLI is an inspection surface, not a product interface.
- Reports are template-based and intentionally avoid invented explanations.

These rough edges are useful because they keep v0.2 inspectable. The spike
should make weaknesses visible rather than hide them behind fluent generation.

## What Failed or Is Risky

The largest risk is that non-LLM methods can become superficially reassuring
while still being brittle.

Known risks:

- Keyword retrieval can miss relevant memories when wording changes.
- Keyword retrieval can return noisy matches when common terms overlap.
- Evidence scores may look more precise than they are.
- Abstention may block useful updates if thresholds are too conservative.
- Simple interpretation may fail on vague, indirect, or multi-topic input.
- Persisted JSONL may make provisional record shapes feel more stable than they
  are.
- Schema work can overfit the current dataclasses.
- Safety can remain too path-oriented unless action intent and permission are
  modeled more explicitly.

The spike partially mitigates these risks by preserving score components,
uncertainty fields, source references, and ordered loop records.

## How the System Currently Says "I Do Not Know"

The system says "I do not know" through records, not through generated prose.

Current mechanisms:

- Low or inconclusive evidence produces `NoUpdateRecord`.
- Empty or ambiguous input can trigger an uncertainty gate.
- The uncertainty gate can produce an `AbstentionRecord` or
  `ClarificationRequestRecord`.
- No-action remains a valid result when evidence is insufficient.
- Reports surface the abstention reason, no-update reason, and remaining
  uncertainty.

This preserves a technical distinction:

- The runtime did not update belief.
- The runtime did not select an action.
- The runtime recorded why it lacked enough evidence.

That is the current non-LLM version of "I do not know."

## How Memory Works Without Embeddings

Memory retrieval is local and file-based.

Current behavior:

- Saved records are loaded from JSONL trace files.
- Retrieval can filter by `record_type`.
- Retrieval can filter by `loop_id`.
- Retrieval tokenizes multi-word queries.
- Punctuation-only tokens are ignored.
- Short or common tokens are ignored where useful.
- Results match when at least one meaningful query token appears in searchable
  record fields.
- Results are capped by a maximum result count.
- Results are ordered by matched token count, then stable record fields.
- Duplicate source record ids are not returned.

Current trace sources:

```text
traces/events.jsonl
traces/loops.jsonl
traces/memory.jsonl
```

This is deliberately not semantic memory. It is a transparent local retrieval
mechanism for proving that prior runtime records can be found and linked back
into a new loop.

## Retrieved Memory Is Context, Not Truth

Retrieved memory must not automatically become current truth.

The current rule is:

- Retrieved records may provide context.
- Retrieved records may be referenced in the loop chain.
- Retrieved records may influence later design decisions about evidence.
- Retrieved records do not directly update belief.
- Retrieved records do not directly create action.
- Retrieved records do not override the current signal, prediction, evidence
  quality, or safety shell.

This matters because memory is reconstructive and uncertain. A retrieved prior
record may be stale, partial, low-quality, or relevant to a different target.
The runtime therefore treats retrieval as inspectable context that must still
pass through evidence and uncertainty handling before it can matter to belief or
action.

## Scoring Is Transparent, Not Final Bayesian Reasoning

v0.2 adds scores to make evidence and belief decisions more inspectable.

Current score fields include:

- `evidence_score`
- `prior_confidence`
- `posterior_confidence`
- `confidence_delta`
- `score_components`
- `update_threshold`

These fields are useful because they show why an update did or did not happen.
They are not final Bayesian reasoning.

Current limitations:

- Scores are deterministic heuristics.
- Score components are hand-designed.
- Priors and posteriors are not derived from a formal probability model.
- Thresholds are provisional.
- Scores should not be treated as calibrated probabilities.

The current value is transparency. A later version may replace or strengthen
the scoring model, but v0.2 should not pretend that lightweight scores are a
complete probabilistic architecture.

## Commands to Observe Current Behavior

Run one loop and print JSON:

```powershell
python -m bpm_runtime.main run-once "The current section is too vague."
```

Run one loop and print a readable summary:

```powershell
python -m bpm_runtime.main run-once "The current section is too vague." --summary
```

Observe empty-input abstention or clarification behavior:

```powershell
python -m bpm_runtime.main run-once --summary
```

Persist one loop to JSONL traces:

```powershell
python -m bpm_runtime.main run-once "The current section is too vague." --save
```

Search saved local memory:

```powershell
python -m bpm_runtime.main memory-search "vague section"
```

Search saved local memory with an explicit cap:

```powershell
python -m bpm_runtime.main memory-search "vague section" --max-results 3
```

Run one loop with local memory retrieval:

```powershell
python -m bpm_runtime.main run-once "vague section" --use-memory --summary
```

Run one loop with capped memory retrieval:

```powershell
python -m bpm_runtime.main run-once "vague section" --use-memory --memory-max-results 3 --summary
```

## Current Known Constraints

The current runtime intentionally has these constraints:

- No LLM integration.
- No web access.
- No autonomous external actions.
- No broad shell or tool automation.
- No real document editing.
- No embedding retrieval.
- No vector database.
- No final Bayesian model.
- No final JSON Schema contract.
- `Source Documents/` remains read-only reference material.

These constraints are part of the test. v0.2 is evaluating how far the runtime
can go with transparent local mechanisms before adding heavier inference tools.

## Recommended v0.3 Directions

### Optional Embedding Retrieval Spike

Test whether embeddings improve retrieval enough to justify the dependency.

Questions:

- Do embeddings find useful memories that keyword search misses?
- Do embeddings add too many plausible but irrelevant matches?
- Can similarity scores be represented transparently in records?
- Can embedding retrieval remain optional and local?

Do not add embedding retrieval until there is a clear evaluation set.

### Stronger Bayesian or Probabilistic Model Spike

Replace or augment heuristic scores with a more principled model.

Questions:

- Which variables are actually probabilistic?
- What counts as prior evidence?
- How should source reliability affect posterior confidence?
- Can the model remain inspectable enough for safety review?

This should be a spike, not a silent rewrite of evidence handling.

### Action Registry and Human Approval

Make action admission more explicit before any real action surface expands.

Needed work:

- Define registered actions.
- Define expected effects.
- Define required permissions.
- Represent human approval as a record.
- Separate proposed, selected, approved, attempted, blocked, and completed
  actions.

No real document editing should be admitted until this is clearer.

### Better Persistence and Replay

Turn JSONL traces into a more useful debugging surface.

Possible work:

- Replay one loop from saved records.
- Validate trace chains.
- Detect missing linked records.
- Summarize prior loops.
- Separate experimental trace format from stable storage contracts.

### Richer Evaluation Cases

Create cases that expose failure modes.

Useful cases:

- Empty input.
- Ambiguous input.
- Low-quality evidence.
- Conflicting memory.
- Relevant memory that should not force belief update.
- Action candidate with missing expected effect.
- Attempted write outside boundary.
- Stale memory.
- Multiple matches with noisy overlap.

Evaluation should test whether the runtime preserves uncertainty rather than
whether it produces impressive output.

## Closeout Assessment

v0.2 is successful as a spike if the goal is inspectability and bounded
behavior. It demonstrates that a local non-LLM runtime can run, persist,
retrieve, score, abstain, and report using records.

It is not yet a robust cognitive runtime. The next decision is whether v0.3
should deepen the non-LLM path with embeddings and stronger scoring, or first
stabilize action admission, replay, and evaluation around the existing local
loop.
