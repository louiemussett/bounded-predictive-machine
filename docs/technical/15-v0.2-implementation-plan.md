# v0.2 Implementation Plan

## Purpose

This document turns the v0.2 non-LLM cognitive runtime spike brief into a
practical implementation plan.

v0.2 is a rapid experimental spike, not a polished product release. The goal is
to learn whether the bounded predictive runtime can become more capable using
non-LLM methods such as rules, schemas, retrieval, embeddings, scored evidence,
deterministic uncertainty gates, and graph-like records.

## v0.2 Boundaries

Do not build in v0.2:

- LLM integration.
- Web access.
- Broad shell or tool automation.
- Autonomous external actions.
- Real document editing.
- UI or product polish.
- Cloud deployment.

Allowed work:

- CLI execution of the existing loop.
- Optional local JSONL persistence.
- Readable reports generated from records.
- Config-driven policies.
- Deterministic uncertainty and abstention.
- Local memory retrieval experiments.
- Lightweight schema validation.
- Tests that enforce first-build invariants.

## Recommended Implementation Sequence

### 1. CLI Runner and Readable Loop Report

Goal:

- Run one manual loop from the command line.
- Print readable JSON by default.
- Optionally print a concise summary.

Likely files:

- `src/bpm_runtime/main.py`
- `src/bpm_runtime/loop.py`
- `src/bpm_runtime/records.py`
- `tests/test_main.py` or `tests/test_cli.py`
- `tests/test_loop_report.py`

Dependencies:

- None required.

Tests:

- `python -m bpm_runtime.main run-once "text"` returns success.
- Output contains prediction, signal, evidence, belief result, action result,
  outcome, memory trace, and loop record.
- Summary mode is deterministic.
- No files are written by default.

Why first:

- It gives the fastest feedback loop without changing the cognitive runtime.

### 2. JSONL Persistence Flags

Goal:

- Allow explicit persistence of records when requested.
- Keep no-persistence as the default.

Likely files:

- `src/bpm_runtime/main.py`
- `src/bpm_runtime/trace.py`
- `src/bpm_runtime/loop.py`
- `tests/test_trace.py`
- `tests/test_cli.py`

Dependencies:

- None required.

Tests:

- `--save` writes only inside configured `traces/`.
- Default CLI writes nothing.
- One JSON object per line.
- Persisted chain can be read back as valid JSON.

Risk:

- Persistence may make trace semantics look final too early. Keep formats
  marked as spike-level.

### 3. Config-Driven Runtime Policies

Goal:

- Move boundary, action, evidence, and uncertainty policy from hard-coded
  defaults toward explicit config files.

Likely files:

- `config/boundary.json`
- `config/action_registry.json`
- `config/evidence_policy.json`
- `config/uncertainty_policy.json`
- `src/bpm_runtime/paths.py`
- `src/bpm_runtime/safety.py`
- `src/bpm_runtime/evidence.py`
- `tests/test_config_policy.py`

Dependencies:

- None required at first.

Tests:

- Missing config fails closed.
- Unknown write targets are rejected.
- `Source Documents/` remains read-only.
- Action candidate must be registered before selection.

Risk:

- Config files can become a full policy language. Keep them small.

### 4. Deterministic Uncertainty and Abstention

Goal:

- Make abstention a first-class runtime result.
- Return no-update and no-action when evidence is too weak or conflicted.

Likely files:

- `src/bpm_runtime/records.py`
- `src/bpm_runtime/evidence.py`
- `src/bpm_runtime/belief.py`
- `src/bpm_runtime/actions.py`
- `src/bpm_runtime/loop.py`
- `tests/test_abstention.py`

Possible records:

- `AbstentionRecord`
- `ClarificationRequestRecord`
- `ConflictRecord`
- `UncertaintyGateRecord`

Dependencies:

- None required.

Tests:

- Empty, unclear, conflicting, or low-score input produces abstention or
  no-action.
- Abstention references evidence and uncertainty.
- Abstention does not update belief or create executable action.

Risk:

- Gates may block too much. Preserve reasons and thresholds for tuning.

### 5. Readable Loop Reports

Goal:

- Generate human-readable reports from records without an LLM.

Likely files:

- `src/bpm_runtime/report.py`
- `src/bpm_runtime/main.py`
- `tests/test_report.py`

Dependencies:

- None required.

Tests:

- Report includes prediction, signal, interpretation, evidence, belief result,
  action/no-action, safety, outcome, memory, and uncertainty.
- Report is generated only from record fields.
- Missing records are reported explicitly.

Risk:

- Reports may become narrative invention. Keep them template-based.

### 6. Schema Validation

Goal:

- Validate core record dictionaries where useful.

Likely files:

- `schemas/base.schema.json`
- `schemas/prediction.schema.json`
- `schemas/signal.schema.json`
- `schemas/loop.schema.json`
- `src/bpm_runtime/schema.py`
- `tests/test_schema_validation.py`

Dependencies:

- `jsonschema`

Tests:

- Valid records pass.
- Missing required fields fail.
- Invalid records do not drive belief, action, memory, or loop records.

Risk:

- Schema work can overfit current dataclasses. Start with base and loop records.

### 7. Local Memory Retrieval

Goal:

- Retrieve relevant prior memory traces without an LLM.

Likely files:

- `src/bpm_runtime/retrieval.py`
- `src/bpm_runtime/memory.py`
- `src/bpm_runtime/records.py`
- `tests/test_retrieval.py`

Dependencies to consider:

- Start with no dependency: JSONL keyword search.
- Then consider `sentence-transformers`.
- Then consider Chroma for a local vector index.

Tests:

- Similar prior memory is retrieved from local records.
- Retrieval record references source memory.
- Retrieval does not become belief without evidence assessment.
- No web access occurs.

Risk:

- Embeddings may return semantically plausible but irrelevant matches.

### 8. Scored Evidence Model

Goal:

- Extend categorical evidence with transparent score components.

Likely files:

- `src/bpm_runtime/evidence.py`
- `src/bpm_runtime/belief.py`
- `src/bpm_runtime/records.py`
- `config/evidence_policy.json`
- `tests/test_scored_evidence.py`

Possible fields:

- `prior_confidence`
- `source_reliability`
- `semantic_similarity`
- `interpretation_confidence`
- `conflict_penalty`
- `posterior_confidence`
- `update_threshold`

Dependencies:

- None required for initial scoring.
- Embeddings optional later.

Tests:

- Low score produces no-update.
- Conflict penalty lowers evidence quality.
- Score reasons are preserved.
- Scores remain target-specific.

Risk:

- Fake precision. Scores must be explained and treated as spike-level.

### 9. Graph-Like Record Relationships

Goal:

- Represent causal or dependency links between records.

Likely files:

- `src/bpm_runtime/graph.py`
- `src/bpm_runtime/records.py`
- `src/bpm_runtime/loop.py`
- `tests/test_record_graph.py`

Dependencies:

- Start with simple dictionaries or records.
- Consider `networkx` only if graph queries become useful.

Tests:

- `low_evidence -> no_update -> no_action`.
- `action_candidate -> safety_check -> outcome`.
- Graph links are reconstructable from record ids.

Risk:

- A graph library may add complexity before the spike needs it.

### 10. Property-Based Safety Tests

Goal:

- Stress the boundary and safety invariants.

Likely files:

- `tests/test_safety_properties.py`
- `tests/test_boundary_properties.py`

Dependencies:

- `Hypothesis`

Tests:

- Any path under `Source Documents/` is rejected for write.
- Unknown write paths are rejected.
- Action without expected effect cannot pass safety.
- Signal cannot directly create action or belief.

Risk:

- Poorly scoped generators can make test failures noisy.

## Dependencies to Consider

Add dependencies only when a chunk needs them and after approval.

Likely early:

- `jsonschema`: useful for lightweight record validation.
- `Hypothesis`: useful for safety invariants after deterministic tests are
  stable.

Possibly v0.2:

- `scikit-learn`: useful if rule-based text classification is insufficient.
- `sentence-transformers`: useful for local semantic retrieval.
- `Chroma`: useful if local vector storage is needed.
- `NetworkX`: useful if graph queries become real.

Defer unless clearly needed:

- `FAISS`: likely premature for this spike.
- `pgmpy`: likely too heavy before simple scoring proves useful.
- `PyMC`, `DoWhy`, larger probabilistic tooling: later research, not v0.2.

Do not add:

- LLM SDKs or adapters.
- Web clients for runtime behavior.
- Browser automation dependencies.

## Tests to Add

CLI and report tests:

- CLI runs one loop.
- CLI output is parseable JSON.
- Summary output is deterministic and record-backed.
- CLI writes no files unless `--save` is explicit.

Persistence tests:

- JSONL append writes one object per line.
- Saved records preserve loop order.
- Persistence stays within `traces/`.

Config and policy tests:

- Missing config fails closed.
- Unknown action is rejected.
- Unregistered action is rejected.
- `Source Documents/` is never writable.

Abstention tests:

- Empty input abstains.
- Unclear input abstains.
- Conflicting interpretation abstains.
- Abstention does not update belief or create executable action.

Retrieval tests:

- Prior memory can be retrieved by keyword.
- Retrieved memory is referenced by id.
- Retrieval does not bypass evidence quality.

Scoring tests:

- Score components are visible.
- Low score blocks update.
- Medium/high score can update only scoped targets.

Schema tests:

- Base record validation.
- Invalid records are rejected from downstream cognition.

Property tests:

- Path writes remain bounded.
- Signal cannot directly become belief or action.
- Outcome cannot be assumed from action intent.

## Risks

- v0.2 may become too broad for one spike.
- Dependencies may outpace learning.
- Embeddings may add noise rather than clarity.
- Bayesian-style scoring may create fake precision.
- Abstention may block too many loops.
- Reports may become polished prose instead of record-backed explanation.
- Config policy may become too complex.
- Persistence may freeze record shape too early.
- Graph modeling may distract from the loop.
- Safety may drift if action registry and capability admission are vague.

## Acceptance Criteria

v0.2 succeeds if it can demonstrate most of the following without an LLM:

- CLI can run one deterministic manual loop.
- Default execution writes no files.
- Optional persistence writes valid JSONL inside boundary.
- Readable reports are generated from records.
- Input can be classified at least coarsely.
- Low-confidence input produces no-update, no-action, or abstention.
- Evidence quality includes visible reasons and, if added, visible scores.
- Belief update remains scoped.
- Action policy remains deterministic.
- Safety rejects read-only and unknown write targets.
- Memory retrieval can find at least simple relevant prior records.
- The loop remains reconstructable from linked records.
- Existing first-build invariants remain green.

v0.2 fails or needs redesign if:

- The runtime needs an LLM to classify simple inputs.
- Retrieval is noisy enough to mislead belief updates.
- Scoring is not inspectable.
- The system cannot explain why it abstained or updated.
- Safety policy becomes unmanageable.
- Dependencies become the architecture.

## What Not to Build Yet

Do not build yet:

- LLM proposal adapters.
- Web browsing.
- Autonomous shell or tool execution.
- Real document editing.
- Background task execution.
- UI.
- Cloud or database deployment.
- Full Prototype 2 cognitive tick.
- Full final JSON Schema set.
- Heavy probabilistic programming.
- Mature vector-memory infrastructure.

## Decisions After the Spike

After the v0.2 spike, decide:

- Did non-LLM interpretation provide useful signal?
- Did embeddings help retrieval enough to justify the dependency?
- Did scored evidence improve decisions or only add fake precision?
- Should abstention become a permanent first-class record?
- Which config files should become stable contracts?
- Which records need JSON Schema first?
- Is a graph representation worth keeping?
- Should v0.3 continue non-LLM work or admit tightly bounded LLM proposal
  adapters?
- What safety policy is required before any real document editing is admitted?
- Which Prototype 2 concepts should be promoted from inherited guidance to
  current implementation detail?

## First Recommended Implementation Chunk

Start with the CLI runner and readable loop report.

Reason:

- It changes the least runtime behavior.
- It gives immediate operator feedback.
- It creates a place to inspect the loop before adding persistence,
  embeddings, scoring, or new records.
- It keeps v0.2 anchored in the v0.1 loop rather than drifting into dependency
  work.

Proposed first code chunk:

```text
src/bpm_runtime/main.py
tests/test_cli.py
tests/test_loop_report.py
```

The first chunk should support:

```powershell
python -m bpm_runtime.main run-once "some manual text"
```

It should call `run_manual_text_loop(...)`, print readable JSON, optionally
print a simple summary, and write no files by default.
