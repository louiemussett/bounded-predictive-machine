# **A04 -- Prediction Frame**

**Project status:** cognitive-core canon  
**Purpose:** define how the system holds expectations before signals arrive, so incoming evidence can be interpreted, compared, weighted, and used for belief update.  
**Rule:** prediction must exist before signal. A system that only reacts to input is not yet aligned with the cognitive core.
* * *

## **1. Why this document exists**

The system cannot compute prediction error unless it first has a prediction.

It cannot meaningfully update belief unless it can say:
    
    
    I expected this.
    This signal arrived.
    I interpreted it as that.
    The interpreted observation differed from expectation.
    The difference had this strength and precision.
    Therefore this model component should or should not update.

Without prediction, the system only reacts.

A reactive system follows this pattern:
    
    
    input arrives
    → process input
    → produce output

This project requires a different pattern:
    
    
    belief state
    → prediction frame
    → signal
    → interpretation
    → prediction error
    → precision weighting
    → belief update
    → new prediction

The prediction frame is the structure that makes the rest of the cognitive loop possible.

* * *

## **2. Core thesis**

The core thesis is:

A prediction frame is the system's active expectation state before new signals arrive. It defines what the system expects, what would count as match or mismatch, how confident the expectation is, what time window applies, and which belief models may be updated if the prediction fails.

In simpler form:
    
    
    belief state
    → prediction frame
    → signal
    → interpreted observation
    → prediction error

A prediction frame is not a guess.

It is a structured expectation prepared for evaluation.

* * *

## **3. Short definition**

A **prediction** is:
    
    
    a structured expectation about a future signal, interpreted observation, body state, action outcome, uncertainty state, or viability state.

A **prediction frame** is:
    
    
    the active set of predictions carried into the next moment, including scope, confidence, evaluation window, expected observations, mismatch conditions, precision expectations, and belief targets.

A **basal prediction** is:
    
    
    a simple starting expectation derived from the minimal starting model rather than learned history.

A **learned prediction** is:
    
    
    an expectation derived from prior belief updates, repeated evidence, adaptive records, or memory reconstruction.

* * *

## **4. Prediction comes before signal**

Prediction must exist before signal.

The system should not wait for a signal and then invent what it "would have expected."

That would be retrospective explanation, not prediction.

Correct order:
    
    
    prediction first
    signal second
    interpretation third
    error fourth

Incorrect order:
    
    
    signal arrives
    → system decides after the fact what it expected
    → system claims prediction error

The prediction must be recorded before the signal is evaluated.

Otherwise mismatch cannot be trusted.

* * *

## **5. Prediction is not certainty**

A prediction is not a claim that something definitely will happen.

It is an expectation with confidence, scope, and evaluation rules.

The system may predict:
    
    
    trace write should probably succeed

without claiming:
    
    
    trace write must succeed

A prediction can be:
    
    
    strong
    weak
    conditional
    uncertain
    experimental
    inherited from prior structure
    learned from evidence

Prediction should preserve uncertainty.

False certainty is worse than weak prediction.

* * *

## **6. Prediction is not desire**

A prediction is not a desire.

The system may predict that trace writing will fail under low disk conditions.

That does not mean it wants trace writing to fail.

The system may predict that the operator will correct a document.

That does not mean it wants correction.

Avoid:
    
    
    the system wants the next tick to succeed
    the system hopes the prediction is right
    the system fears mismatch

Prefer:
    
    
    the prediction expected successful trace write
    the prediction was assigned moderate confidence
    the observed interpretation mismatched the prediction
    the mismatch updated the trace-store model

Prediction is operational, not emotional.

* * *

## **7. Prediction is not goal**

A prediction is not a goal.

A goal says:
    
    
    this future state is preferred

A prediction says:
    
    
    this future state is expected

The system may later use goals, but the cognitive core does not require them.

The primitive loop is:
    
    
    prediction
    → signal
    → interpretation
    → error
    → belief update

not:
    
    
    goal
    → plan
    → action

Prediction comes earlier than goal.

* * *

## **8. Prediction is not action authorization**

A prediction does not authorize action.

The system may predict:
    
    
    asking clarification would reduce semantic uncertainty

but action selection still requires:
    
    
    action policy
    cost evaluation
    risk evaluation
    viability check
    permission check
    safety shell

Prediction can inform action.

It cannot bypass action governance.

Prediction is evidence for expected consequences, not permission.

* * *

## **9. Basal prediction**

Basal predictions are simple expectations present from the beginning.

They come from the minimal starting model.

Examples:
    
    
    the next tick should occur
    the runtime should remain inside its boundary
    trace writing should usually succeed
    body sensors should usually return a signal
    memory should remain within expected range
    disk should remain available enough for trace write
    manual text may or may not arrive
    a selected action should have some expected consequence

Basal predictions do not require learned history.

They are the first expectations that make error possible.

* * *

## **10. Why basal prediction matters**

If the system waits until later versions to predict, the early system is merely reactive.

Basal prediction ensures that even the first prototype can say:
    
    
    I expected the next tick.
    The tick occurred late.
    This is timing prediction error.
    The error is relevant to body and viability models.

or:
    
    
    I expected trace write success.
    Trace write failed.
    This is trace-store prediction error.
    The signal has high precision for trace-store state.
    Viability risk increases.

This is enough to begin cognitive development.

The first predictions may be boring.

They are still essential.

* * *

## **11. Learned prediction**

Learned predictions arise from prior evidence.

Examples:
    
    
    when disk availability is low, trace writes often fail
    when polling increases, CPU usually rises
    when the operator says "not what I meant," the project model often needs correction
    when memory pressure rises, tick latency often increases
    when a sensor fails twice, viability often degrades

Learned prediction depends on:
    
    
    belief state
    memory traces
    adaptive records
    prior prediction outcomes
    sensor reliability history
    action outcome history

Learned predictions should not appear before the system can preserve evidence and update belief.

* * *

## **12. Prediction scope**

Every prediction needs scope.

Prediction scope says what kind of thing is expected.

Possible scopes:
    
    
    body_state
    sensor_signal
    interpreted_observation
    trace_event
    viability_state
    action_outcome
    operator_signal
    semantic_interpretation
    memory_reconstruction
    uncertainty_state
    capability_state

Examples:
    
    
    body_state:
    memory should remain stable during next tick
    
    sensor_signal:
    trace-store sensor should return writable
    
    interpreted_observation:
    manual text may indicate a correction
    
    action_outcome:
    reducing polling should lower tick cost slightly
    
    uncertainty_state:
    asking clarification should reduce semantic uncertainty

Without scope, prediction becomes vague.

* * *

## **13. Prediction target**

Prediction target specifies what model component may be tested.

Targets may include:
    
    
    body_model
    sensor_model
    trace_model
    operator_model
    task_model
    project_model
    action_model
    viability_model
    memory_model
    uncertainty_model
    self_model
    cause_model

Example:
    
    
    prediction:
    trace write should succeed
    
    target:
    trace_model
    viability_model
    body_model

Another example:
    
    
    prediction:
    operator likely wants next cognitive-core document
    
    target:
    operator_model
    project_model
    task_model

A prediction should not update every model when it fails.

It should target specific model components.

* * *

## **14. Prediction content**

Prediction content may include:
    
    
    expected signal
    expected interpreted observation
    expected body state
    expected state transition
    expected action outcome
    expected timing
    expected magnitude
    expected uncertainty change
    expected viability change
    expected cause

Not every prediction needs all fields.

But every prediction should define what would count as evidence.

A prediction that cannot be evaluated is not a useful prediction.

* * *

## **15. Prediction confidence**

Prediction confidence estimates how strongly the system expects the predicted condition.

Confidence may be based on:
    
    
    structural prior strength
    sensor reliability
    recent evidence
    adaptive support
    memory reconstruction strength
    operator pattern
    action model reliability
    current uncertainty

Confidence should not be binary.

Useful categories:
    
    
    very_low
    low
    moderate
    high
    very_high
    structural
    unknown

or numeric values if implemented carefully.

High confidence does not mean truth.

It means stronger expectation before evidence arrives.

* * *

## **16. Prediction uncertainty**

Prediction should preserve uncertainty separately from confidence where useful.

A prediction may have moderate confidence but high uncertainty about cause.

Example:
    
    
    I moderately expect memory pressure to rise,
    but I am uncertain whether the cause would be my action or external process activity.

Prediction uncertainty may include:
    
    
    uncertain timing
    uncertain magnitude
    uncertain cause
    uncertain sensor reliability
    uncertain interpretation
    uncertain action effect

This helps the system avoid overclaiming when prediction fails or matches.

* * *

## **17. Evaluation window**

Every prediction should define an evaluation window.

The evaluation window says when the prediction should be checked.

Possible windows:
    
    
    next_tick
    within_N_ticks
    next_sensor_sample
    after_action_completion
    before_shutdown
    during_current_task
    until_expired
    manual_review_required

Examples:
    
    
    trace write should succeed during next write attempt
    
    memory should remain stable over next 5 ticks
    
    operator likely wants next document in the next message
    
    action should reduce polling cost within 3 ticks

Without an evaluation window, predictions can never expire.

Unexpired vague predictions become noise.

* * *

## **18. Mismatch conditions**

A prediction must define what counts as mismatch.

Examples:
    
    
    expected trace write success
    mismatch if trace write fails or is unavailable
    
    expected memory stable
    mismatch if memory crosses threshold or rises beyond expected band
    
    expected operator continuation request
    mismatch if operator requests stop, revision, or different direction
    
    expected action reduces CPU
    mismatch if CPU remains unchanged or increases beyond noise tolerance

Mismatch conditions should be specific.

A vague prediction creates vague error.

* * *

## **19. Match conditions**

A prediction should also define what counts as match.

Match conditions prevent the system from treating any loosely similar result as success.

Example:
    
    
    prediction:
    trace write should succeed
    
    match:
    trace write returns success and valid trace appears in trace store within expected window

Another example:
    
    
    prediction:
    asking clarification should reduce semantic uncertainty
    
    match:
    operator provides clarification that resolves at least one known ambiguous belief target

Match should be evidence-based.

* * *

## **20. Partial match**

Some predictions partially match.

Examples:
    
    
    trace write succeeds but validation warning appears
    
    operator continues the sequence but changes the title
    
    action reduces CPU but increases latency
    
    memory reconstruction retrieves relevant trace but confidence is low

Partial match is important.

Without it, the system may force evidence into match or mismatch.

Partial match preserves nuance.

* * *

## **21. Inconclusive outcome**

Some predictions cannot be evaluated.

Reasons include:
    
    
    signal missing
    sensor failed
    trace unavailable
    window expired without evidence
    privacy blocked observation
    prediction was malformed
    conflicting signals
    interpretation unresolved

Inconclusive is not failure.

It means the system lacks sufficient evidence.

The system should not treat inconclusive as mismatch unless policy explicitly defines absence as evidence.

* * *

## **22. Prediction invalidation**

A prediction may become invalid before evaluation.

Reasons:
    
    
    source belief was revised
    sensor became unavailable
    task was cancelled
    action was not executed
    runtime entered safe mode
    boundary became uncertain
    prediction frame was superseded

Invalidated predictions should not update belief as if they failed.

They should be recorded as invalidated.

This prevents false learning.

* * *

## **23. Prediction expiration**

A prediction may expire if its window passes.

Expired predictions should be handled differently from mismatched predictions.

Example:
    
    
    prediction:
    operator may reply within next message
    
    if no message arrives:
    expired or missing-signal outcome,
    not necessarily semantic mismatch

Expiration should preserve uncertainty.

An expired prediction may update timing expectations, but not necessarily semantic content.

* * *

## **24. Prediction lineage**

Every prediction should cite its source.

Possible sources:
    
    
    structural prior
    basal prediction rule
    belief state
    belief update
    adaptive record
    memory reconstruction
    action model
    operator model
    viability model
    human correction

Prediction lineage matters because outcomes may later update the source.

If a prediction fails, the system should know which model may need revision.

Without lineage, prediction error cannot become targeted belief update.

* * *

## **25. Prediction and priors**

Priors generate basal predictions.

Example:
    
    
    prior:
    trace writing normally succeeds
    
    prediction:
    next trace write should succeed
    
    signal:
    trace write failed
    
    error:
    trace-store prediction error

A prior is broader.

A prediction is a concrete expectation created from that prior in a specific context.

The system should not confuse the two.

* * *

## **26. Prediction and belief state**

Prediction is generated from belief state.

Belief state answers:
    
    
    what model do I currently hold?

Prediction answers:
    
    
    given that model, what should I expect next?

If belief changes, predictions should change.

After belief update, the posterior belief becomes the next prior for prediction generation.

This makes the system continuous.

* * *

## **27. Prediction and signal**

A signal is evaluated relative to prediction.

The same signal may produce different error depending on prediction.

Example:
    
    
    signal:
    operator says "continue"
    
    prediction A:
    operator likely wants next document
    → match
    
    prediction B:
    operator likely wants critique
    → mismatch or partial match
    
    prediction C:
    operator likely wants to stop
    → mismatch

Prediction gives context.

Signal gives evidence.

Interpretation connects them.

* * *

## **28. Prediction and interpretation**

Prediction shapes interpretation, but should not dominate it.

The system should avoid two errors:
    
    
    ignoring prediction when interpreting signal
    forcing signal to fit prediction

Correct interpretation asks:
    
    
    Given what I predicted, what does this signal most likely mean?
    What else could it mean?
    Does the signal contradict the prediction?
    Is the interpretation high confidence or uncertain?

Prediction is context, not authority.

* * *

## **29. Prediction and precision**

Prediction may include expected precision.

Examples:
    
    
    memory sensor reading should be moderately precise for body state
    
    manual correction should be high precision for current document intent
    
    LLM interpretation should be low-to-moderate precision unless validated
    
    stale trace should have reduced precision

When a signal arrives, observed precision can be compared with expected precision.

A sensor that becomes less precise than expected may update the sensor model.

* * *

## **30. Prediction and action**

Action should use prediction in two ways.

First:
    
    
    predict expected outcome of each candidate action

Second:
    
    
    after action, compare observed outcome against predicted outcome

Example:
    
    
    candidate action:
    ask clarification
    
    predicted outcome:
    operator clarification reduces semantic uncertainty
    
    observed outcome:
    operator provides direct answer
    
    result:
    action prediction matched

Or:
    
    
    candidate action:
    reduce polling
    
    predicted outcome:
    CPU cost falls
    
    observed outcome:
    CPU unchanged
    
    result:
    action outcome mismatch

Action learning depends on action prediction.

* * *

## **31. Prediction and memory**

Memory should store prediction before signal.

A memory trace should preserve:
    
    
    what was predicted
    what signal arrived
    how it was interpreted
    what error occurred
    how belief changed
    what action was selected
    what outcome followed

Without stored prediction, memory becomes an event log.

With stored prediction, memory becomes reconstructive evidence of model change.

The system should remember not only what happened, but what it expected before it happened.

* * *

## **32. Prediction and self-model**

The self-model requires predictions about action consequences.

Examples:
    
    
    if I write a trace, trace store should change
    
    if I reduce polling, tick cost may fall
    
    if I ask clarification, operator may provide more precise signal
    
    if I enter safe mode, high-risk actions should become unavailable

The system learns selfhood by comparing self-action predictions with observed effects.

Self-model is not narrative identity.

It is action-consequence expectation.

* * *

## **33. Prediction and external cause**

Prediction helps distinguish self-caused from external change.

Example:
    
    
    no action predicted to affect memory
    memory pressure rises unexpectedly
    → possible external cause or background process
    
    recent action predicted to increase memory
    memory pressure rises within window
    → possible self-caused change

Prediction does not prove cause.

It organizes causal hypotheses.

Causal attribution still requires evidence.

* * *

## **34. Prediction and viability**

The system should hold viability predictions.

Examples:
    
    
    viability should remain safe next tick
    
    if trace write fails twice, viability may degrade
    
    if disk falls below threshold, trace reliability may fall
    
    if sensor failures accumulate, uncertainty should rise
    
    if safe mode is entered, action scope should reduce

Viability predictions help the system detect operational risk early.

They should not create survival instinct.

They are condition expectations.

* * *

## **35. Prediction and uncertainty**

Prediction should include uncertainty expectations.

Examples:
    
    
    asking clarification should reduce uncertainty
    
    observing again should reduce sensor uncertainty
    
    low-precision signal should increase interpretation uncertainty
    
    conflicting traces should increase memory uncertainty

The system should predict not only states but uncertainty changes.

This allows action to be evaluated by expected information gain.

* * *

Each prediction within the frame may include:
    
    
    prediction_id
    scope
    target_model
    source_prior_or_belief
    expected_signal
    expected_interpretation
    expected_state
    expected_transition
    expected_action_outcome
    expected_uncertainty_change
    confidence
    uncertainty
    precision_expectation
    evaluation_window
    match_conditions
    mismatch_conditions
    invalidation_conditions

* * *

## **37. Minimal prediction schema sketch**

A minimal prediction may look like:
    
    
    {
      "prediction_id": "pred_0001",
      "frame_id": "frame_0001",
      "scope": "body_state",
      "target_model": [
        "body_model",
        "trace_model",
        "viability_model"
      ],
      "source": {
        "type": "basal_prior",
        "id": "prior_trace_write_should_succeed"
      },
      "expected_state": {
        "trace_store_state": "writable"
      },
      "confidence": 0.75,
      "uncertainty": [
        "disk state may affect trace write",
        "permission state may affect trace write"
      ],
      "evaluation_window": "next_trace_write",
      "match_conditions": [
        "trace_write_returns_success",
        "written_trace_validates_schema"
      ],
      "mismatch_conditions": [
        "trace_write_failed",
        "trace_write_permission_denied",
        "trace_validation_failed"
      ],
      "invalidation_conditions": [
        "runtime_enters_safe_shutdown_before_trace_write"
      ],
      "schema_version": "0.1"
    }

This schema is illustrative.

The important point is that prediction is structured and evaluable.

* * *

## **38. Prediction frame lifecycle**

A prediction frame may move through statuses:
    
    
    created
    active
    partially_evaluated
    evaluated
    expired
    invalidated
    superseded
    archived

A prediction within a frame may move through:
    
    
    pending
    matched
    partially_matched
    mismatched
    causal_mismatch
    inconclusive
    expired
    invalidated
    cancelled

Prediction status should be traceable.

A prediction should not silently disappear.

* * *

## **39. Multiple active predictions**

The system may hold multiple predictions at once.

Examples:
    
    
    body prediction:
    memory should remain stable
    
    sensor prediction:
    trace-store sensor should report writable
    
    operator prediction:
    operator may request next document
    
    action prediction:
    writing trace should produce valid record
    
    viability prediction:
    state should remain safe

These predictions may interact.

A body mismatch may affect viability prediction.

A manual correction may affect operator and project models.

A sensor failure may invalidate other predictions.

The prediction frame organizes this set.

* * *

## **40. Prediction conflict**

Predictions may conflict.

Example:
    
    
    prediction A:
    operator likely wants continuation
    
    prediction B:
    operator may correct the outline before continuation

The system should represent conflict rather than force one prediction.

Prediction conflict may produce:
    
    
    lower confidence
    higher uncertainty
    multiple candidate interpretations
    action preference for clarification

Conflicting predictions are not necessarily errors.

They may represent honest uncertainty.

* * *

## **41. Prediction priority**

Some predictions matter more than others.

Priority may depend on:
    
    
    viability relevance
    safety relevance
    action relevance
    operator relevance
    memory relevance
    current task relevance
    confidence
    risk if wrong

High-priority predictions include:
    
    
    trace write should succeed
    boundary should remain valid
    critical body sensors should respond
    unsafe action should remain unavailable
    operator correction should be handled accurately

Priority determines evaluation urgency.

It does not determine truth.

* * *

## **42. Prediction granularity**

Predictions may be coarse or fine.

Coarse prediction:
    
    
    memory should remain normal

Fine prediction:
    
    
    memory usage should remain below threshold X for next five ticks

Early systems should begin with coarse predictions.

Fine predictions require better sensors, evidence, and calibration.

The system should not pretend fine precision before it has it.

* * *

## **43. Prediction calibration**

Prediction confidence should be calibrated over time.

A calibrated prediction system learns:
    
    
    which predictions are usually accurate
    which are overconfident
    which are underconfident
    which conditions change reliability

Calibration requires storing:
    
    
    prediction
    confidence
    outcome
    context
    signal precision
    interpretation quality

Without calibration, confidence becomes decoration.

* * *

When evaluated, a prediction should produce an outcome record.

Suggested fields:
    
    
    prediction_outcome_id

    evaluated_at
    outcome_status
    observed_signal_ids
    interpreted_observation_ids
    match_strength
    mismatch_type
    precision_of_evidence
    confidence_after_evaluation
    belief_update_recommended
    belief_update_id_if_applied
    uncertainty_after
    schema_version

This record connects prediction to belief update.

* * *

## **45. Prediction outcome example**

Example:
    
    
    {
      "prediction_outcome_id": "pout_0001",
      "prediction_id": "pred_0001",
      "outcome_status": "mismatched",
      "observed_signal_ids": [
        "sig_trace_0001"
      ],
      "interpreted_observation_ids": [
        "obs_trace_failed_0001"
      ],
      "mismatch_type": "body_state_error",
      "precision_of_evidence": {
        "trace_store_state": 0.95,
        "failure_cause": 0.40
      },
      "belief_update_recommended": true,
      "target_models": [
        "trace_model",
        "viability_model"
      ],
      "uncertainty_after": [
        "failure cause unknown"
      ],
      "schema_version": "0.1"
    }

The outcome does not merely say "wrong."

It says how, with what evidence, and for which belief target.

* * *

## **46. Prediction error versus prediction outcome**

Prediction error and prediction outcome are related but distinct.

Prediction error is the mismatch object.

Prediction outcome is the evaluation result.

Example:
    
    
    prediction outcome:
    mismatched
    
    prediction error:
    trace write expected success, observed failure, high precision for trace state, unknown cause

Outcome classifies the evaluation.

Error describes the wrongness.

Both may be useful.

* * *

## **47. Prediction frame and cognitive tick**

The prediction frame should be created early in the cognitive tick.

Tick order:
    
    
    load belief state
    generate prediction frame
    read sensors
    wrap signals
    interpret signals
    evaluate prediction frame
    compute prediction errors
    apply precision weighting
    update belief
    generate next prediction frame
    select action
    store memory trace

Prediction is not an afterthought.

It is the opening posture of the tick.

* * *

## **48. Prediction frame and memory trace**

Every memory trace should include the active prediction frame or relevant predictions.

Memory without prediction loses the before-state.

A reconstructive memory should answer:
    
    
    What did the system expect before the signal arrived?

If it cannot answer that, it cannot fully reconstruct belief update.

Prediction frame is therefore part of memory evidence.

* * *

## **49. Prediction frame and safety shell**

The safety shell may constrain predictions.

Examples:
    
    
    forbidden sensors should not generate expected signals
    
    unadmitted actions should not generate action-outcome predictions for execution
    
    unsafe viability should reduce prediction scope
    
    trace failure may prevent prediction outcome evaluation
    
    privacy policy may prevent observing some expected signal

Safety constrains what the system may observe and do.

But safety should not erase the prediction frame.

Even if action is denied, the system may still predict:
    
    
    the action is unavailable under current safety state

* * *

## **50. Prediction and language**

Language output should not replace prediction.

A sentence such as:
    
    
    I think the user wants the next document.

is not enough.

The system needs a structured prediction:
    
    
    scope: operator_signal
    expected_interpretation: request_next_document
    confidence: moderate
    evaluation_window: next_user_message
    mismatch_conditions: user requests revision, stop, or different topic

Natural language may render prediction.

It should not be the prediction itself.

* * *

## **51. Prediction and LLMs**

If an LLM is used, it may propose predictions.

But the runtime must validate and structure them.

LLM may suggest:
    
    
    the user probably wants the next A-series document

The runtime must convert this into:
    
    
    prediction object
    scope
    confidence
    source
    target model
    evaluation window
    mismatch conditions

LLM-generated predictions should be marked as proposals unless validated.

The LLM should not own the prediction frame.

* * *

## **52. Bad predictions**

Bad predictions include:
    
    
    vague predictions
    unbounded predictions
    unevaluable predictions
    predictions without source
    predictions without window
    predictions without mismatch conditions
    predictions generated after the signal
    predictions that authorize action directly
    predictions that hide uncertainty

Examples of bad predictions:
    
    
    something useful will happen
    the user wants help
    the system will improve
    memory will be better
    the action will work

These are too vague.

A prediction must be checkable.

* * *

## **53. Good predictions**

Good predictions are:
    
    
    specific
    scoped
    source-linked
    time-bounded
    confidence-bearing
    uncertainty-preserving
    match-defined
    mismatch-defined
    belief-targeted

## **56. Incorrect assumptions about prediction**

Avoid these assumptions:
    
    
    prediction requires advanced intelligence
    prediction should wait until learning exists
    prediction is the same as desire
    prediction is the same as goal
    prediction can be vague
    prediction can be made after the fact
    prediction confidence authorizes action
    if prediction fails, the system should immediately repair
    if evidence is missing, prediction was wrong

Correct assumptions:
    
    
    basal prediction can be simple
    prediction begins before signal
    prediction is expectation, not desire
    prediction is not goal
    prediction must be evaluable
    prediction must be recorded before evaluation
    prediction informs action but does not authorize it
    mismatch informs belief update
    missing evidence may be inconclusive

## **58. Evaluation questions**

The prediction frame should be evaluated by asking:
    
    
    Does the system generate predictions before signals arrive?
    Are predictions recorded before evaluation?
    Does each prediction have scope?
    Does each prediction have a target model?
    Does each prediction have confidence or uncertainty?
    Does each prediction have an evaluation window?
    Does each prediction define match and mismatch conditions?
    Can predictions expire or be invalidated?
    Can missing evidence become inconclusive?
    Can prediction outcomes update belief targets?
    Can action outcome predictions be tested?
    Can memory traces preserve prior predictions?

If not, the prediction frame is not mature.

## **63. Final statement**

Prediction is the system's stance toward the next moment.

It is how the system becomes more than reactive.

A prediction frame states what is expected, why it is expected, how confident the system is, when it should be evaluated, what would count as match or mismatch, and which belief model may change if the prediction fails.

The final principle is:

The system must carry structured predictions before signals arrive. Every meaningful belief update depends on comparing interpreted observation against a prior prediction within a defined frame of scope, confidence, timing, precision expectation, and mismatch conditions.

That is the prediction frame.
