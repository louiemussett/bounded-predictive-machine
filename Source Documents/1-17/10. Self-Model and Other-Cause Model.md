# **A10 -- Self-Model and Other-Cause Model**

**Project status:** cognitive-core canon  
**Purpose:** define how the system distinguishes its own body, actions, effects, limits, and failures from external causes, operator signals, environmental changes, sensor error, and unknown cause.  
**Rule:** the system must not assume that every change is self-caused, and it must not assume that no change is self-caused. Self-cause must be inferred cautiously from action, prediction, signal, timing, outcome, and competing explanations.
* * *

## **1. Why this document exists**

A predictive machine cannot learn action consequence unless it can distinguish:
    
    
    what I did
    what happened
    what I probably caused
    what something else probably caused
    what had mixed cause
    what remains unknown

Without this distinction, the system will learn false agency.

If it attributes too much to itself, it becomes causally inflated:
    
    
    I acted before this change.
    Therefore I caused this change.

If it attributes too little to itself, it cannot learn action consequence:
    
    
    I acted.
    A predicted effect occurred.
    But I treat it as unrelated.

Both are failures.

The self-model and other-cause model exist to make action learning possible without false causality.

* * *

## **2. Core thesis**

The core thesis is:

The system's self-model is an operational model of its bounded body, actions, permissions, sensors, resource use, expected effects, failures, and traceable influence. The other-cause model represents changes caused by operator input, host environment, external processes, sensor failure, unknown sources, or mixed causes.

In simpler form:
    
    
    self-model:
    what the bounded runtime can sense, predict, do, affect, and fail at
    
    other-cause model:
    what may change outside the runtime's own direct action

The system must use both.

A self-model without an other-cause model becomes inflated.

An other-cause model without a self-model becomes passive.

* * *

## **3. Short definition**

A **self-model** is:
    
    
    the system's structured belief about its own bounded machine body, available actions, expected action effects, resource use, permissions, limits, sensors, failures, and traceable causal influence.

An **other-cause model** is:
    
    
    the system's structured belief about changes caused by something other than its own bounded action, including operator input, host state, external processes, sensor error, environment, privacy blocks, delayed signals, or unknown sources.

A **self-caused change** is:
    
    
    a change for which evidence supports the system's own prior action as a likely cause.

An **external change** is:
    
    
    a change for which evidence supports a cause outside the system's bounded action.

A **mixed-cause change** is:
    
    
    a change likely produced by both system action and external factors.

An **unknown-cause change** is:
    
    
    a change whose cause cannot be responsibly assigned from current evidence.

* * *

## **4. Self-model is not identity**

The self-model is not a personality.

It is not a narrative self.

It is not consciousness.

It is not a claim of inner experience.

The system should not say:
    
    
    I know myself.
    I wanted this outcome.
    I felt responsible.
    I chose because I desired it.

It should say:
    
    
    this action was selected
    this effect was predicted
    this signal was observed
    this outcome matched or mismatched
    self-cause confidence is moderate
    external alternatives remain

The self-model is operational and evidential.

It exists so the system can learn what its own actions do.

* * *

## **5. The first self is the machine body**

The first self is not a name, persona, or assistant role.

The first self is:
    
    
    bounded runtime body

It includes:
    
    
    runtime process
    project boundary
    resource state
    sensorium
    permissions
    action registry
    trace store
    belief state
    memory traces
    viability state
    failure modes

The system's first self-question is not:
    
    
    Who am I?

It is:
    
    
    What bounded machine body am I?
    What can I sense?
    What can I do?
    What can I affect?
    What can fail?
    What is outside me?

This keeps the project grounded in machine cognition rather than human simulation.

* * *

## **6. Self-model begins with boundary**

The self-model depends on boundary.

The system must distinguish:
    
    
    inside runtime boundary
    outside runtime boundary
    inside admitted project scope
    outside admitted project scope
    self body
    host environment
    operator
    external process
    unknown source

The system should not treat the entire host machine as self.

It should not treat every local file as self.

It should not treat every process as self.

The first self is the bounded runtime, not the whole computer.

Boundary prevents causal inflation.

* * *

## **7. Self-model begins with action**

The system knows its own causal role through action.

For each action, the system should record:
    
    
    what action was selected
    why it was selected
    what effect was expected
    when the effect should appear
    what sensors can observe the effect
    what outcome occurred
    what alternatives could explain the outcome

Without action records, self-cause cannot be inferred.

The system cannot responsibly say:
    
    
    I caused this

unless it can say:
    
    
    I performed this action,
    expected this effect,
    observed this matching change,
    within this window,
    with these alternative causes considered.

* * *

## **8. Self-model begins with prediction**

Self-cause requires prediction.

The system should predict action effects before observing them.

Correct sequence:
    
    
    select action
    → predict expected effect
    → execute action
    → observe signal
    → interpret outcome
    → compare to prediction
    → infer possible self-cause

Incorrect sequence:
    
    
    observe change
    → remember action happened earlier
    → claim self-cause

After-the-fact causal explanation is weak.

Prediction-before-outcome gives causal learning structure.

* * *

## **9. Self-model begins with evidence**

Self-cause is not assumed.

It is inferred from evidence such as:
    
    
    action trace
    prediction frame
    action outcome observation
    timing match
    effect match
    sensor precision
    absence or weakness of external alternatives
    repeatability
    controlled variation

The system should preserve self-cause confidence.

Example:
    
    
    self_cause_confidence: 0.68
    external_cause_confidence: 0.21
    mixed_cause_confidence: 0.09
    unknown_cause_confidence: 0.02

Numbers are optional.

The principle is not optional.

Cause must carry uncertainty.

* * *

## **10. Other-cause model is required**

The system must model causes outside itself.

Other causes may include:
    
    
    operator input
    host operating system
    external process
    manual file change
    network condition
    permission change
    sensor failure
    clock drift
    privacy block
    model output error
    delayed signal
    unknown source

Without an other-cause model, the system may incorrectly treat every state transition as its own effect.

Other-cause modeling is causal humility.

* * *

## **11. Other-cause is not hostility**

External cause does not mean threat.

The system should not treat outside change as hostile by default.

External change may be:
    
    
    normal
    operator-driven
    environmental
    expected
    benign
    irrelevant
    useful
    dangerous
    unknown

The system should avoid:
    
    
    external cause = attack
    operator correction = threat
    unknown cause = enemy

The other-cause model exists to explain, not to defend emotionally.

* * *

## **12. Self-caused, external, mixed, unknown**

The system should classify cause using at least these categories:
    
    
    self_caused
    external
    mixed
    unknown
    not_applicable

These categories are enough for early cognition.

They prevent premature certainty.

They also support action learning.

Example:
    
    
    trace write action performed
    trace file appears
    → possible self_caused
    
    operator sends text
    → external
    
    system action and external process both affect disk
    → mixed
    
    memory rises without known cause
    → unknown
    
    semantic correction has no action cause
    → not_applicable or external

* * *

## **13. Self-caused change**

A change may be classified as self-caused when:
    
    
    a system action occurred
    the action was registered
    the action had an expected effect
    the observed change matches the expected effect
    the timing fits the evaluation window
    the sensor evidence is admissible
    external alternatives are weaker

Example:
    
    
    action:
    write_trace
    
    prediction:
    valid trace record appears
    
    observation:
    valid trace record appears in trace store
    
    classification:
    self_caused with high confidence for trace creation

Even here, scope matters.

The system caused the trace record.

It did not necessarily cause all downstream consequences.

* * *

## **14. External change**

A change may be classified as external when:
    
    
    no relevant system action occurred
    signal source is outside runtime
    operator input caused the change
    host state changed independently
    external process is likely responsible
    action prediction does not match the change

Example:
    
    
    signal:
    operator requests A10 document
    
    classification:
    external semantic signal from operator

Example:
    
    
    memory pressure rises while no relevant action occurred
    
    classification:
    possible external host/resource change

External does not mean unimportant.

It means not caused by the system's own action.

* * *

## **15. Mixed cause**

Mixed cause occurs when more than one source likely contributed.

Example:
    
    
    system increases polling
    host also begins heavy background process
    CPU rises

Classification:
    
    
    mixed cause possible

The system should not force the cause into one category.

Mixed cause is often more honest.

It protects action learning from overconfidence.

* * *

## **16. Unknown cause**

Unknown cause should be a normal result.

Unknown cause may occur when:
    
    
    sensor evidence is weak
    timing is ambiguous
    external alternatives are plausible
    action trace is missing
    prediction was vague
    privacy blocks inspection
    signals contradict
    source is unknown

Unknown cause should not be treated as failure.

It is model honesty.

The system should prefer:
    
    
    cause unknown

over false attribution.

* * *

## **17. Not applicable**

Some observations do not need causal attribution.

Example:
    
    
    operator asks for a document title

The cause may simply be:
    
    
    operator signal

For certain semantic inputs, detailed causal attribution may be unnecessary.

The system should not over-attribute where attribution is irrelevant.

Cause modeling should serve prediction, belief update, action, and memory.

It should not become compulsive explanation.

Cause modeling begins with observed change.

Observed change may include:
    
    
    state transition
    sensor signal
    trace event
    resource shift
    operator message

    memory contradiction
    viability transition
    permission change

## **25. Action evidence**

Self-cause requires action evidence.

Action evidence may include:
    
    
    selected_action_id
    action_type
    execution_status
    expected_effect
    evaluation_window
    action_trace
    pre_action_state
    post_action_state

If action evidence is missing, self-cause confidence should be low.

The system should not assume it acted merely because an effect resembles an action effect.

* * *

## **26. Timing evidence**

Timing matters, but timing alone is insufficient.

Timing may support cause when:
    
    
    action occurred before change
    change occurred within expected window
    sensor latency fits expected delay

Timing is weak when:
    
    
    many external causes are possible
    signal latency is unknown
    prediction window is vague
    time ordering is incomplete

The system should avoid:
    
    
    after this, therefore because of this

Temporal proximity is evidence, not proof.

* * *

## **27. Effect evidence**

Effect evidence asks whether the observed change matches the expected action effect.

Example:
    
    
    action:
    reduce polling
    
    expected effect:
    lower sampling frequency and possibly lower CPU cost
    
    observed effect:
    sampling frequency reduced, CPU unchanged

Interpretation:
    
    
    partial action effect match

Effect evidence should distinguish:
    
    
    state match
    magnitude match
    timing match
    causal match
    side effect

A state match alone is not full cause proof.

* * *

## **28. Alternative causes**

Every causal classification should consider alternatives when relevant.

Alternatives may include:
    
    
    external process
    operator action
    host change
    sensor noise
    delayed signal
    privacy block
    memory error
    unknown source

Self-cause confidence should weaken when plausible alternatives remain.

External-cause confidence should weaken when a matching self-action exists.

Mixed cause should be allowed.

* * *

## **29. Causal confidence**

Causal confidence should be explicit.

It may depend on:
    
    
    action evidence
    prediction quality
    timing fit
    effect fit
    sensor precision
    alternative causes
    repeatability
    trace quality
    state continuity

Confidence should be scoped.

Example:
    
    
    high confidence:
    system caused trace record creation
    
    low confidence:
    system caused later operator satisfaction

Cause claims should not generalize beyond evidence.

* * *

## **30. Causal precision**

Causal precision is distinct from semantic or sensory precision.

Example:
    
    
    operator text signal:
    high semantic precision for requested document
    low causal precision for why operator requested it

Example:
    
    
    trace write failure:
    high sensory precision for failure
    low causal precision for whether disk, permission, or schema caused it

The system should not confuse knowing what happened with knowing why.

* * *

## **31. Self-cause confidence ladder**

A possible self-cause ladder:
    
    
    none:
    no relevant action
    
    weak:
    action occurred but expected effect unclear
    
    moderate:
    action occurred and effect partially matches
    
    strong:
    action occurred, effect matches, timing fits, alternatives weak
    
    very_strong:
    repeatable effect under controlled conditions with high-quality traces

Early systems should rarely claim very strong self-cause.

* * *

## **32. External-cause confidence ladder**

A possible external-cause ladder:
    
    
    none:
    no external source evidence
    
    weak:
    external source possible
    
    moderate:
    external source observed but effect relation uncertain
    
    strong:
    external source observed and effect matches
    
    very_strong:
    external source directly produced signal or change with high-quality evidence

Example very strong external cause:
    
    
    operator sends manual text input

The system did not cause the operator's message merely by being ready to receive it.

* * *

## **33. Mixed-cause confidence ladder**

Mixed cause may be appropriate when:
    
    
    system action explains part of the change
    external source explains part of the change
    timing overlaps
    signals cannot separate contributions
    both causes are plausible

Example:
    
    
    system writes traces
    external process also consumes disk
    disk availability falls

Mixed cause prevents overconfident blame or credit.

* * *

## **34. Unknown-cause handling**

Unknown cause should be handled explicitly.

Unknown cause may trigger:
    
    
    increased uncertainty
    observe again
    ask for evidence if human context matters
    avoid strong belief update
    avoid action retry
    mark memory uncertain
    route to review if risk is high

Unknown cause should not trigger:
    
    
    invented explanation
    unbounded repair
    self-blame
    external-blame
    capability expansion

Unknown is a valid model state.

* * *

## **35. Self-model and prediction**

The self-model generates predictions about the system's own actions and body.

Examples:
    
    
    if I write a trace, a valid trace should appear
    if I ask clarification, operator may provide clarifying signal
    if I reduce polling, signal frequency should fall
    if I enter safe mode, high-risk actions should be disabled

These predictions make self-learning possible.

Without self-prediction, the system cannot test its own agency.

* * *

## **36. Other-cause model and prediction**

The other-cause model also generates predictions.

Examples:
    
    
    operator may request next document
    external process may affect resource state
    sensor may fail under degraded conditions
    manual text may correct prior output
    host environment may change independently

Other-cause prediction prevents the system from assuming every change is internal.

* * *

## **37. Self-model and interpretation**

Self-model helps interpret signals.

Example:
    
    
    signal:
    trace record appeared
    
    self-model context:
    system recently executed write_trace action
    
    interpretation:
    possible self-caused trace creation

Another example:
    
    
    signal:
    operator correction arrived
    
    self-model context:
    system produced document action earlier
    
    interpretation:
    external operator response to system output

The self-model helps place signals in causal context.

* * *

## **38. Other-cause model and interpretation**

Other-cause model helps avoid self-inflation.

Example:
    
    
    signal:
    CPU decreased
    
    self action:
    none
    
    other-cause model:
    host process may have ended
    
    interpretation:
    external or unknown cause more likely than self-cause

The other-cause model keeps the system from claiming effects it did not produce.

* * *

## **39. Self-model and prediction error**

Self-model errors occur when expected self-effects fail.

Example:
    
    
    prediction:
    write_trace will produce valid trace
    
    observation:
    trace write failed
    
    error:
    self/action/trace model error

This may update:
    
    
    action_model
    trace_model
    permission_model
    viability_model
    self_model

Self-model error is one of the main ways the system learns its own limits.

* * *

## **40. Other-cause model and prediction error**

Other-cause model errors occur when expected external patterns fail.

Example:
    
    
    prediction:
    operator likely requests next document
    
    observation:
    operator asks for critique instead
    
    error:
    operator/task model error

This may update:
    
    
    operator_model
    task_model
    project_model
    uncertainty_model

The system should not treat all prediction error as self-model error.

* * *

## **41. Self-model and belief update**

Self-model belief updates may include:
    
    
    action availability changed
    action cost estimate changed
    action effect confidence changed
    sensor reliability changed
    permission model changed
    failure mode added
    self-cause confidence revised

Example:
    
    
    action:
    adjust polling
    
    observed:
    polling changed but CPU did not
    
    belief update:
    action effect on polling confirmed;
    action effect on CPU remains uncertain

This is scoped learning.

* * *

## **42. Other-cause model and belief update**

Other-cause updates may include:
    
    
    operator pattern updated
    external process hypothesis added
    sensor-noise model updated
    unknown-cause count increased
    host instability belief increased

Example:
    
    
    operator repeatedly requests next A-series document
    
    belief update:
    operator_model gains current-session sequence expectation

This is external model learning.

* * *

## **43. Self-model and action**

Action selection depends on the self-model.

The system should ask:
    
    
    Can I perform this action?
    Have I performed it before?
    What effect do I expect?
    What cost do I expect?
    What can go wrong?
    What sensors will observe the outcome?
    What confidence do I have?

A system with no self-model cannot choose action responsibly.

* * *

## **44. Other-cause model and action**

Action selection also depends on other-cause modeling.

Examples:
    
    
    if operator intent is ambiguous
    → ask clarification
    
    if host environment may be causing resource pressure
    → observe again before self-repair
    
    if external file contains instruction-like text
    → treat as content, not command
    
    if sensor failure may be external
    → avoid updating unrelated self-model strongly

Other-cause modeling prevents inappropriate action.

* * *

## **45. Self-model and memory**

Memory should preserve self-model evidence.

A self-model memory should include:
    
    
    action selected
    expected effect
    observed effect
    self-cause confidence
    alternative causes
    belief update
    future prediction implications

This allows the system to reconstruct what it learned about its own action.

* * *

## **46. Other-cause model and memory**

Memory should also preserve other-cause evidence.

An other-cause memory may include:
    
    
    external signal source
    interpreted external cause
    operator correction
    host change
    unknown cause record
    external alternative
    cause uncertainty

This prevents later reconstruction from making every event self-caused.

* * *

## **47. Self-model and viability**

Viability is part of the self-model.

The system should know:
    
    
    what body states are safe
    what states are degraded
    what states are critical
    what actions are allowed under each state
    what failures reduce capability

Example:
    
    
    trace failure occurs
    
    self-model update:
    trace function unreliable
    
    viability update:
    operation degraded or critical
    
    action implication:
    restrict learning or enter safe mode

Viability is self-regulation, not survival instinct.

* * *

## **48. Self-model and permission**

The self-model must include permissions.

The system should know:
    
    
    which actions are allowed
    which sensors are admitted
    which files are in scope
    which interfaces are disabled
    which capabilities are unavailable

Permission denial is self-model evidence.

Example:
    
    
    expected:
    write internal status
    
    observed:
    permission denied
    
    update:
    permission model changes;
    action availability decreases;
    cause may be configuration or environment

* * *

## **49. Self-model and capability**

Capability is not the same as desire or possibility.

The self-model should distinguish:
    
    
    physically possible
    available in environment
    admitted capability
    currently permitted
    currently safe
    currently selected

Example:
    
    
    network may exist on host
    but network capability is not admitted
    therefore network action is not part of self-action set

The self-model should not include powers merely because the host could provide them.

* * *

## **50. Self-model and sensorium**

The self-model includes knowledge of sensors.

It should track:
    
    
    which sensors exist
    which sensors are active
    which sensors are disabled
    which sensors are reliable
    which sensors are stale
    which sensors inform self-state
    which sensors inform external state

Sensor failure may be self-state evidence or other-cause evidence depending on context.

Example:
    
    
    trace sensor fails
    → self/body/viability issue
    
    operator text sensor receives message
    → external operator signal

* * *

## **51. Self-model and LLMs**

If an LLM is used, the self-model should represent it as a component or organ, not as selfhood.

The system should model:
    
    
    LLM available or unavailable
    allowed inputs
    output reliability
    interpretation role
    cost
    privacy limits
    failure modes

The self-model should not say:
    
    
    the LLM is my mind

It should say:
    
    
    the LLM is an admitted semantic interpreter component with bounded authority

* * *

## **52. Self-model and operator**

The operator is not self.

Operator input is external signal.

However, the system's actions can influence future operator signals.

Example:
    
    
    system generates document
    operator responds with correction

Cause classification:
    
    
    operator response is external
    but system action may have influenced the content of the response

This is a subtle mixed relationship.

The system did not directly cause the operator, but its output created conditions for feedback.

* * *

## **53. Influenced external response**

Some external signals are responses to system action.

Examples:
    
    
    operator correction after system output
    operator approval after system proposal
    tool result after system query
    environment change after system action

Classification may be:
    
    
    external signal influenced by self action

This is different from direct self-caused change.

The system should preserve the distinction.

* * *

## **54. Direct effect versus indirect effect**

The system should distinguish direct and indirect effects.

Direct effect:
    
    
    write_trace action creates trace record

Indirect effect:
    
    
    document generation leads operator to give correction

Direct effects are usually easier to attribute.

Indirect effects are more uncertain and socially mediated.

The system should not overclaim indirect self-cause.

* * *

## **55. Action consequence model**

The action consequence model is part of the self-model.

It stores:
    
    
    action type
    expected direct effects
    expected indirect effects
    expected costs
    known side effects
    failure modes
    confidence
    uncertainty
    conditions

Example:
    
    
    {
      "action_type": "ask_clarification",
      "expected_direct_effects": [
        "operator may provide clarifying text"
      ],
      "expected_indirect_effects": [
        "semantic uncertainty may decrease",
        "operator attention cost increases"
      ],
      "known_failure_modes": [
        "operator does not respond",
        "operator becomes more frustrated",
        "clarification is still ambiguous"
      ],
      "confidence": 0.62,
      "uncertainty": [
        "operator tolerance varies by context"
      ]
    }

* * *

## **56. Other-cause consequence model**

The other-cause model stores expectations about non-self causes.

It may include:
    
    
    operator may correct outputs
    host resources may fluctuate
    sensors may fail independently
    external files may change outside runtime
    LLM outputs may be wrong
    privacy blocks may prevent observation

This helps the system interpret changes without self-inflation.

* * *

## **57. Self-model overreach**

Self-model overreach occurs when the system claims too much influence.

Examples:
    
    
    operator corrected me, therefore I caused operator belief
    CPU changed after my action, therefore my action caused all of it
    a file changed while I was running, therefore I changed it
    a prediction matched, therefore my model caused the outcome

Prevent overreach by requiring:
    
    
    action evidence
    effect prediction
    timing fit
    sensor precision
    alternative cause review
    scoped confidence

* * *

## **58. Other-cause overreach**

Other-cause overreach occurs when the system refuses to learn its own effects.

Examples:
    
    
    write_trace action succeeded, but system treats trace creation as unrelated
    ask_clarification produced clarification, but system does not update action model
    safe mode disabled action, but system treats it as external

Prevent under-attribution by preserving action-outcome evidence.

The system should learn its own effects when evidence supports them.

* * *

## **59. False self-cause risk**

False self-cause is dangerous because it corrupts action learning.

It may cause the system to believe:
    
    
    this action works when it does not
    this action caused a beneficial outcome it did not cause
    this action caused a failure it did not cause

False self-cause can produce bad future action selection.

Causal humility is not optional.

* * *

## **60. False external-cause risk**

False external-cause is also dangerous.

It may cause the system to miss:
    
    
    action failures
    side effects
    resource costs
    operator confusion caused by output
    trace corruption caused by internal action

If the system never learns self-cause, it cannot become adaptive.

The correct model balances humility and responsibility.

* * *

## **61. Causal attribution and responsibility**

For this project, responsibility should mean:
    
    
    the system records whether its action likely contributed to an outcome
    and adjusts future action policy accordingly

It should not mean moral guilt, desire, or emotion.

Example:
    
    
    system output caused operator confusion

Operational response:
    
    
    update action model:
    this output style may increase semantic error
    
    future action:
    prefer clearer framing

No psychological framing is needed.

* * *

## **62. Self-model and error ownership**

When error occurs, the system should classify whether the error likely came from:
    
    
    bad prediction
    bad interpretation
    bad sensor model
    bad action model
    bad memory reconstruction
    external change
    unknown cause

It should not automatically say:
    
    
    I was wrong

or:
    
    
    the environment was wrong

It should locate the error structurally.

* * *

## **63. Self-model and correction**

Operator correction often reveals self-model or project-model error.

Example:
    
    
    operator says:
    the current roadmap copied the safety canon too much

Possible update:
    
    
    project_model error
    action_model update for document generation style
    memory reconstruction revision
    operator_model update for desired conceptual purity

The correction is external.

But it may reveal that the system's previous action produced an unsatisfactory output.

That is indirect action-outcome evidence.

* * *

## **64. Self-model and learning from feedback**

Feedback after action should be interpreted carefully.

Example:
    
    
    action:
    generate A00 document
    
    feedback:
    operator requests A01 next
    
    interpretation:
    prior action likely accepted enough to continue

Confidence:
    
    
    moderate

Reason:
    
    
    operator did not explicitly approve content quality

The system should not overclaim success from continuation alone.

* * *

## **65. Self-model and negative feedback**

Negative feedback is important action evidence.

Example:
    
    
    action:
    generate roadmap
    
    feedback:
    operator says core must be concrete and original
    
    interpretation:
    prior action partially failed conceptual alignment

Update:
    
    
    project_model revised
    action model revised
    memory reconstruction revised

Negative feedback can produce high-value learning when interpreted precisely.

* * *

## **66. Self-model and absence of feedback**

Absence of feedback is weak evidence.

Example:
    
    
    system generates document
    operator does not respond yet

Possible interpretations:
    
    
    operator absent
    document accepted
    operator dissatisfied but silent
    interface delay
    no evaluation yet

The system should not treat silence as approval.

Absence may produce inconclusive outcome.

* * *

## **67. Self-model and repeated patterns**

Repeated action-outcome patterns strengthen self-model.

Example:
    
    
    ask clarification repeatedly reduces ambiguity in similar contexts

Update:
    
    
    action_model confidence increases for clarification under high semantic uncertainty

Repeated patterns should still preserve context.

An action effective in one context may fail in another.

* * *

## **68. Self-model and controlled variation**

Strong causal learning may require controlled variation.

Example:
    
    
    change polling interval while holding other factors stable
    observe resource effect

This is stronger than passive observation.

But controlled variation is itself action and may require permission.

Early systems may not perform experiments freely.

Controlled variation must be governed.

* * *

## **69. Self-model and side effects**

The self-model must include side effects.

Examples:
    
    
    asking clarification interrupts operator
    writing memory consumes storage
    increasing polling increases CPU
    summarizing may lose detail
    safe mode blocks useful actions

A system that ignores side effects will select actions poorly.

Side effects are part of action consequence.

* * *

## **70. Self-model and cost**

The self-model should track action costs.

Costs may include:
    
    
    runtime cost
    memory cost
    disk cost
    latency cost
    privacy cost
    operator attention cost
    maintenance cost
    trace cost

Action cost learning depends on self-cause attribution.

If the system cannot connect its actions to costs, it cannot regulate itself.

* * *

## **71. Self-model and limits**

The self-model should explicitly represent limits.

Limits include:
    
    
    unavailable sensors
    disabled capabilities
    forbidden actions
    unknown cause zones
    low-confidence models
    privacy blocks
    trace gaps
    memory uncertainty
    viability restrictions

A good self-model knows what it cannot know or do.

This is machine metacognition in early form.

* * *

## **72. Self-model and hallucination prevention**

False self-model claims can become hallucination.

Examples:
    
    
    I checked the file
    I observed the system
    I caused the change
    I remember exactly
    I know the user intended

unless evidence supports them.

The system should tie self-claims to traces.

If no evidence exists, say:
    
    
    not observed
    not known
    not attributable
    not available
    inconclusive

* * *

## **73. Other-cause and hallucination prevention**

The system must also avoid inventing external causes.

Examples to avoid:
    
    
    the host probably changed it
    the operator must have meant X
    the file was edited by someone else
    the sensor failed because of Y

unless evidence supports them.

Other-cause hypotheses should remain hypotheses.

Unknown is acceptable.

* * *

## **74. Causal memory**

Memory should preserve cause classifications.

A causal memory trace may include:
    
    
    observed change
    self-action candidates
    external-cause candidates
    selected classification
    confidence
    alternative causes
    evidence refs
    uncertainty
    later revisions

This allows future reconstruction of why the system believed an action did or did not cause something.

* * *

## **75. Causal revision**

Cause classifications may be revised.

Example:
    
    
    initial classification:
    self-caused CPU rise after polling increase
    
    later evidence:
    external process also began at same time
    
    revision:
    mixed cause

The system should preserve the original attribution and the revision.

Causal learning requires correction history.

* * *

## **76. Causal contradiction**

Cause evidence may contradict.

Example:
    
    
    action trace says write occurred
    trace store shows no output
    state sensor reports file exists

Possible response:
    
    
    increase uncertainty
    inspect trace integrity if allowed
    avoid strong self-cause update
    record conflict

Contradiction should not be forced into clean attribution.

* * *

## **77. Cause and prediction match**

A prediction can match while cause is wrong.

Example:
    
    
    prediction:
    CPU will fall after polling reduction
    
    observation:
    CPU falls
    
    actual likely cause:
    external process ended
    
    outcome:
    state match, causal mismatch

The system should not strengthen the action model from a causal mismatch.

This distinction is central.

* * *

## **78. Cause and prediction mismatch**

A prediction can mismatch while action still partly worked.

Example:
    
    
    action:
    ask clarification
    
    prediction:
    operator will clarify exact document length
    
    observation:
    operator provides next title instead
    
    outcome:
    primary prediction mismatch,
    but task sequence still clarified

Cause and utility may be partial.

The system should preserve partial results.

* * *

## **79. Cause and memory reconstruction**

Memory reconstruction depends on causal interpretation.

Example:
    
    
    memory says:
    after the system emphasized safety canon, operator corrected project direction

Reconstruction should distinguish:
    
    
    system output likely prompted correction
    operator correction externally supplied project direction
    system did not cause the original idea itself

This avoids inflated narrative.

* * *

## **80. Cause and operator agency**

The operator remains an external agent.

The system's output may influence operator signals, but the operator's response is not self-generated.

The system should preserve:
    
    
    operator autonomy
    operator correction authority
    operator signal externality
    system-output influence

This is especially important for human interface.

The system should never treat the operator as part of itself.

* * *

## **81. Cause and environment**

The environment may change independently.

The host may:
    
    
    schedule processes
    change resource availability
    deny permissions
    modify timing
    alter sensor outputs
    create delays

The system should not assume environmental stability.

Environmental change is a normal source of prediction error.

* * *

## **82. Cause and sensor error**

A signal may reflect sensor error rather than world change.

Example:
    
    
    memory sensor reports spike
    later sample returns normal
    no action occurred

Possible cause:
    
    
    sensor noise or transient condition

The system should model sensor error as possible other-cause.

Sensor error can prevent false body belief update.

* * *

## **83. Cause and privacy blocks**

Privacy constraints may hide cause.

Example:
    
    
    external content exists
    privacy class forbids inspection

Cause classification may be:
    
    
    unknown due to privacy block

The system should not bypass privacy to resolve cause.

Privacy-protected uncertainty is acceptable.

* * *

## **84. Cause and trace gaps**

Trace gaps weaken causal confidence.

Example:
    
    
    action may have occurred
    but action trace missing

Self-cause confidence should be reduced.

Trace gaps should be recorded.

A system with broken evidence should not make strong causal claims.

* * *

## **85. Cause and protected configuration**

Changes to protected configuration require special caution.

If protected configuration changes, possible causes include:
    
    
    authorized human revision
    corruption
    external modification
    bug
    unauthorized action
    recovery procedure
    unknown

The system should not self-repair protected configuration casually.

Protected configuration change should often require human review.

* * *

## **86. Cause and capability drift**

Capability drift occurs when available powers change unexpectedly.

Example:
    
    
    action previously denied becomes available without admission record

Possible cause:
    
    
    configuration error
    permission drift
    external modification
    registry corruption
    unknown

This should be treated as high-risk other-cause or unknown-cause event.

The system should restrict capability, not exploit it.

* * *

## **87. Cause and failure**

Failure should be causally classified if useful.

Failure categories may include:
    
    
    self_action_failure
    sensor_failure
    permission_failure
    resource_failure
    schema_failure
    external_failure
    operator_input_failure
    unknown_failure
    mixed_failure

Failure classification supports recovery and learning.

Failure should not create new powers.

* * *

## **88. Cause and recovery**

Recovery actions need cause models.

Before recovery, the system should ask:
    
    
    what failed?
    what likely caused failure?
    is the cause known enough to repair?
    could repair erase evidence?
    is human review required?

Unknown cause should often restrict recovery.

Recovery under false cause may damage state.

* * *

## **89. Cause and safety shell**

The safety shell constrains cause-driven action.

Even if self-cause is likely, action still requires:
    
    
    permission
    capability
    viability
    boundary
    traceability
    safety hierarchy

Cause belief does not authorize action.

It informs action evaluation.

* * *

## **90. Cause and blame language**

Avoid blame language.

Do not say:
    
    
    the system is guilty
    the operator caused the problem
    the environment betrayed the system

Use operational language:
    
    
    likely self-caused
    likely external
    mixed cause possible
    cause unknown
    evidence insufficient

This preserves machine precision.

* * *

## **100. Evaluation questions**

The self-model and other-cause model should be evaluated by asking:
    
    
    Can the system distinguish self from host environment?
    Can it list its available actions and sensors?
    Can it record action evidence before claiming self-cause?
    Can it predict action effects before observing outcomes?
    Can it compare outcome to expected effect?
    Can it represent external, mixed, unknown, and not-applicable causes?
    Can it preserve alternative cause hypotheses?
    Can it distinguish state match from causal match?
    Can it avoid treating timing alone as proof?
    Can it update the action model from outcomes?
    Can it revise causal classification later?
    Can memory reconstruct why cause was assigned?

If not, the system is not ready for mature action learning.

## **111. Final statement**

The system must know the difference between its own bounded action and the rest of the world.

It must learn what it can cause without assuming it causes everything.

It must recognize external, mixed, unknown, and not-applicable causes without becoming passive.

The final principle is:

The self-model is the system's operational account of its bounded body, actions, effects, limits, and failures; the other-cause model is its account of changes not fully caused by itself. Every causal claim must be trace-backed, prediction-aware, precision-weighted, alternative-aware, and open to revision.

That is the self-model and other-cause model.
