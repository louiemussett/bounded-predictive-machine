# **A13 -- Cognitive Data Model**

**Project status:** cognitive-core canon  
**Purpose:** define the concrete data objects, references, schemas, records, and relationships required to make the cognitive core buildable.  
**Rule:** the system must not rely on vague language, hidden state, loose memory, or unstructured logs as its core substrate. Every major cognitive operation must produce structured records that preserve prediction, signal, interpretation, error, precision, belief update, action, outcome, metacognition, and memory lineage.
* * *

## **1. Why this document exists**

The previous documents define the cognitive loop:
    
    
    machine body
    → sensorium
    → priors
    → prediction
    → signal
    → interpretation
    → error
    → precision
    → belief update
    → action
    → outcome
    → memory
    → metacognition
    → next tick

But this loop cannot become real unless it has objects.

A system cannot responsibly say:
    
    
    I predicted.
    I interpreted.
    I updated belief.
    I selected action.
    I remembered.

unless those events exist as structured records.

The cognitive data model defines those records.

It turns the project from conceptual architecture into an implementable information structure.

* * *

## **2. Core thesis**

The core thesis is:

The cognitive core must be represented by explicit, schema-valid, traceable data objects. Prediction, signal, interpretation, error, precision, belief, action, memory, self-cause, and metacognition must not live only in prose, prompts, logs, or hidden runtime state.

In simpler form:
    
    
    no hidden cognition
    no unstructured belief
    no memory without source
    no action without expected effect
    no update without error
    no error without prediction
    no prediction without belief
    no confidence without target

The data model is what makes the system auditable, testable, recoverable, and eventually buildable.

* * *

## **3. Short definition**

A **cognitive data model** is:
    
    
    the structured set of records, schemas, identifiers, references, lifecycles, and validation rules used to represent the system's cognitive loop.

A **cognitive object** is:
    
    
    a schema-valid record representing one part of the loop, such as a prediction, signal, interpretation, error, belief update, action, outcome, memory trace, or metacognitive assessment.

A **reference** is:
    
    
    a stable pointer from one cognitive object to another.

A **lineage chain** is:
    
    
    the linked evidence path from prior belief through prediction, signal, interpretation, error, update, action, outcome, and memory.

A **schema** is:
    
    
    the structural contract that defines what a record must contain before it can be used downstream.

* * *

## **4. The data model is not a database first**

This document is not primarily about choosing a database.

It is about defining the shape of cognition.

The system may eventually use:
    
    
    JSON files
    JSONL traces
    SQLite
    PostgreSQL
    event store
    object store
    vector index
    graph database
    hybrid storage

But storage choice is secondary.

The first question is not:
    
    
    Where do we store it?

The first question is:
    
    
    What must exist as structured evidence for the cognitive loop to be valid?

Database comes later.

Data model comes first.

* * *

## **5. The data model is not memory alone**

The cognitive data model is broader than memory.

Memory is one family of records.

The model also includes:
    
    
    machine body records
    sensor records
    signal envelopes
    prediction frames
    interpreted observations
    prediction errors
    precision estimates
    belief states
    belief updates
    action candidates
    selected actions
    action outcomes
    cause classifications
    metacognitive states
    tick records
    audit traces

Memory reconstructs from these.

It does not replace them.

* * *

## **6. The data model is not logs**

Logs are usually chronological text or events.

The cognitive data model needs structured relationships.

A log may say:
    
    
    trace write failed

A cognitive record should say:
    
    
    prediction expected trace write success
    signal reported trace write failure
    interpretation classified trace-store failure
    error type was trace_error
    precision was high for trace-store state
    belief update targeted trace_model and viability_model
    action candidate entered safe mode
    memory trace preserved the event

A log records occurrence.

A cognitive data model records meaning, evidence, relation, update, and uncertainty.

* * *

## **7. Design principles**

The cognitive data model follows these principles:
    
    
    1. Every cognitive object has an identifier.
    2. Every object has a schema version.
    3. Every object has provenance.
    4. Every object has status.
    5. Every object may carry uncertainty.
    6. Every object may carry confidence only when scoped.
    7. Every downstream object references upstream evidence.
    8. Raw signal is separated from interpretation.
    9. Belief is separated from memory.
    10. Action selection is separated from action execution.
    11. Outcome is separated from action attempt.
    12. Cause classification is separated from state change.
    13. Memory reconstruction is separated from source trace.
    14. Summaries never replace source evidence.
    15. Invalid records do not drive cognition.

These principles prevent hidden drift.

## **9. Canonical lineage chain**

The most important relationship in the data model is the lineage chain:
    
    
    BeliefState
    → PredictionFrame
    → SignalEnvelope
    → InterpretedObservation
    → PredictionError
    → PrecisionEstimate
    → BeliefUpdate
    → PosteriorBeliefState
    → ActionCandidate
    → SelectedAction
    → ActionOutcome
    → CauseClassification
    → MemoryTrace
    → MetacognitiveState
    → NextPredictionFrame

Not every tick uses every object fully.

But the data model should be able to represent the full chain.

If the chain cannot be reconstructed, the system cannot explain how it changed.

## **10. Identifier discipline**

Every cognitive object should have a stable identifier.

Recommended patterns:
    
    
    body_*
    sensor_*
    signal_*
    obs_*
    pred_*
    frame_*
    err_*
    prec_*
    belief_*
    bu_*
    actcand_*
    act_*
    outcome_*
    cause_*
    memtrace_*
    memrec_*
    meta_*
    tick_*
    trace_*

Identifiers should support reference, audit, and reconstruction.

They should not depend on natural language titles.

A document title may change.

A record identifier should not.

* * *

## **11. Reference discipline**

Objects should reference each other explicitly.

Example:
    
    
    {
      "prediction_error_id": "err_0013",
      "prediction_id": "pred_0013",
      "interpreted_observation_id": "obs_0013",
      "precision_estimate_id": "prec_0013",
      "target_models": [
        "task_model",
        "operator_model"
      ]
    }

References make cognition reconstructable.

Without references, the system has disconnected fragments.

Disconnected fragments cannot support responsible belief update.

* * *

## **12. Schema version discipline**

Every object should include:
    
    
    schema_version

This matters because the system will evolve.

A future record may not have the same fields as an early record.

The system must know which schema governed each record.

Example:
    
    
    {
      "object_type": "SignalEnvelope",
      "schema_version": "0.1"
    }

Schema versioning is not bureaucracy.

It is survival against drift.

* * *

## **13. Status discipline**

Every major object should have a status.

Possible statuses include:
    
    
    created
    active
    pending
    validated
    invalid
    blocked
    applied
    delayed
    superseded
    revised
    archived
    quarantined
    failed
    unknown

Status prevents records from being treated as complete when they are not.

Example:
    
    
    belief update candidate

is not the same as:
    
    
    applied belief update

The data model must preserve that difference.

* * *

## **14. Provenance discipline**

Every meaningful object should preserve where it came from.

Provenance may include:
    
    
    source object id
    source sensor id
    source prediction id
    source trace id
    created by module
    created during tick
    created from operator signal
    created from system action
    created from memory reconstruction

A record without provenance is weak evidence.

A belief update without provenance is unsafe.

* * *

## **15. Confidence discipline**

Confidence must always have a target.

Bad:
    
    
    {
      "confidence": 0.9
    }

Better:
    
    
    {
      "confidence": {
        "current_task_interpretation": 0.97,
        "desired_length": 0.82,
        "causal_explanation": 0.40
      }
    }

Confidence without target becomes fake certainty.

The system should know what the confidence refers to.

* * *

## **16. Uncertainty discipline**

Uncertainty should be explicit.

Uncertainty may be represented as:
    
    
    free text
    typed uncertainty objects
    severity categories
    targeted uncertainty records
    confidence intervals
    unknown markers
    alternative hypotheses

A simple early form is acceptable:
    
    
    {
      "uncertainty": [
        "desired length not explicitly stated",
        "operator has not yet evaluated output quality"
      ]
    }

The important rule is:
    
    
    do not hide uncertainty

* * *

## **17. Privacy discipline**

Many objects may include or reference sensitive content.

Every signal, memory, trace, and output-relevant object should carry a privacy class.

Possible privacy classes:
    
    
    public
    internal_runtime
    operator_input
    sensitive
    secret
    forbidden
    unknown

Privacy class affects:
    
    
    storage
    retrieval
    memory inclusion
    trace inclusion
    LLM eligibility
    human display
    external output
    retention

Useful information does not override privacy class.

* * *

## **18. Object minimalism**

The data model should begin small.

The first implementation does not need every possible field.

But it must preserve the core distinctions:
    
    
    prediction is not signal
    signal is not interpretation
    interpretation is not error
    error is not update
    belief is not memory
    action candidate is not selected action
    selected action is not outcome
    outcome is not cause proof
    memory reconstruction is not source trace

A minimal data model is acceptable.

A blurred data model is not.

* * *

## **20. Schema registry**

The system should maintain a schema registry.

The schema registry records:
    
    
    schema_id
    object_type
    schema_version
    required_fields
    optional_fields
    validation_rules
    deprecated_fields
    successor_schema

The registry prevents the runtime from accepting unknown record shapes as valid cognition.

If a record fails schema validation, it should not drive adaptation, belief update, action, or memory reconstruction.

* * *

## **21. Object registry**

The system may maintain an object registry.

The object registry records:
    
    
    object_type
    allowed_statuses
    allowed_transitions
    required_references
    downstream_allowed_uses
    privacy_requirements
    retention_policy

Example:
    
    
    PredictionError requires Prediction and InterpretedObservation.
    BeliefUpdate requires PredictionError and target model.
    SelectedAction requires ActionCandidate and policy evaluation.
    MemoryTrace requires at least one source reference.

This makes the data model enforce the architecture.

# **Part XV -- Relationship Rules**

## **73. Prediction relationship rule**

A prediction must reference:
    
    
    source belief or prior
    prediction frame
    target model
    evaluation window
    match and mismatch conditions

A prediction without source is weak.

A prediction without evaluation window is not checkable.

* * *

## **74. Signal relationship rule**

A signal must reference:
    
    
    sensor model
    payload or payload limitation
    timestamp
    privacy class
    admissibility status
    belief targets

A signal without sensor model should not strongly update belief.

* * *

## **75. Interpretation relationship rule**

An interpreted observation must reference:
    
    
    source signal
    active prediction frame
    sensor model
    belief targets
    alternative interpretations when relevant

Interpretation without source signal is hallucination risk.

* * *

## **76. Error relationship rule**

A prediction error must reference:
    
    
    prediction
    interpreted observation
    error type
    target model
    precision estimate

Error without prediction is retrospective explanation.

Error without interpretation is raw-signal overreach.

* * *

## **77. Belief update relationship rule**

A belief update must reference:
    
    
    prior belief
    source error
    weighted error
    target model
    posterior belief
    uncertainty after update

Belief update without error is not adaptation.

It is uncontrolled model mutation.

* * *

## **78. Action relationship rule**

A selected action must reference:
    
    
    action candidate
    policy evaluation
    expected effect
    pre-action check
    permission and capability status

Action without expected effect cannot be evaluated.

Action without permission is invalid.

* * *

## **79. Outcome relationship rule**

An action outcome must reference:
    
    
    selected action
    execution record
    expected effect
    observed effect
    match status
    precision estimate

Outcome is not attempt.

The system learns from observed effect, not intention.

* * *

## **80. Cause relationship rule**

A cause classification must reference:
    
    
    observed change
    cause hypotheses
    supporting evidence
    alternative causes
    confidence
    uncertainty

Cause without alternatives is overconfident.

Cause without evidence is speculation.

* * *

## **81. Memory relationship rule**

A memory trace must reference at least one upstream cognitive object.

Strong memory should reference:
    
    
    prediction
    signal
    interpretation
    error
    precision
    belief update
    action
    outcome
    cause
    metacognition

Memory without source is not memory.

It is unsupported narrative.

* * *

## **82. Metacognition relationship rule**

A metacognitive state must reference the objects it assesses.

Examples:
    
    
    prediction confidence references Prediction
    interpretation ambiguity references InterpretedObservation
    action readiness references ActionCandidate
    memory confidence references MemoryReconstruction
    causal uncertainty references CauseClassification

Metacognition without target becomes vague caution.

* * *

# **Part XVII -- Anti-Drift Rules**

## **87. Do not collapse objects**

Avoid collapsing:
    
    
    signal into interpretation
    interpretation into belief
    belief into memory
    memory into transcript
    action candidate into action
    action attempt into outcome
    outcome into cause
    summary into source
    confidence into truth

Each collapse creates architectural drift.

The data model exists to keep these distinctions alive.

* * *

## **88. Do not let language become the data model**

Natural language can render records.

It should not replace them.

Bad:
    
    
    The system thought the user wanted A13 and wrote it.

Better:
    
    
    prediction pred_0013 expected next A-series request
    signal signal_0013 carried manual text
    observation obs_0013 interpreted A13 request
    belief update bu_0013 set current task
    action act_0013 generated document
    memory memtrace_0013 preserved event

Language explanation is useful.

Structured record is authoritative.

* * *

## **89. Do not let LLM output become record truth**

If an LLM helps generate a field, mark it.

Suggested field:
    
    
    generated_by

or:
    
    
    interpretation_source

Example:
    
    
    {
      "semantic_content": "operator requests A13 document",
      "interpretation_source": "runtime_inference",
      "llm_assisted": false
    }

If LLM-assisted:
    
    
    {
      "llm_assisted": true,
      "validation_status": "runtime_validated"
    }

LLM output is proposal until validated.

* * *

## **90. Do not make memory the primary evidence store**

Memory reconstructs from records.

It should not be the only place evidence exists.

If memory says:
    
    
    belief changed

there should also be:
    
    
    belief update record
    source error record
    interpreted observation
    prediction reference

Memory without source chain is weak.

* * *

## **91. Do not make confidence global**

Avoid:
    
    
    confidence: high

Use:
    
    
    confidence in current task interpretation: high
    confidence in causal attribution: low
    confidence in desired length: moderate

Global confidence creates overclaiming.

Scoped confidence supports metacognition.

* * *

## **92. Do not erase invalid records silently**

Invalid records should be:
    
    
    rejected
    quarantined
    marked invalid
    routed to review
    excluded from downstream use

They should not vanish without trace.

Invalid evidence is still useful as evidence of failure.

* * *

# **Part XVIII -- Evaluation**

## **93. Data model evaluation questions**

The cognitive data model should be evaluated by asking:
    
    
    Can every major cognitive operation produce a structured record?
    
    Can prediction be traced to belief or prior?
    
    Can signal be traced to sensor?
    
    Can interpretation be traced to signal and prediction frame?
    
    Can error be traced to prediction and interpreted observation?
    
    Can precision be traced to sensor and context?
    
    Can belief update be traced to weighted error?
    
    Can action be traced to candidate, policy, and expected effect?
    
    Can outcome be traced to action and observation?
    
    Can cause classification preserve alternatives?
    
    Can memory reconstruct the full loop?
    
    Can metacognition assess confidence, uncertainty, and readiness?
    
    Can invalid records be blocked from downstream use?
    
    Can a human audit the lineage chain?

If not, the data model is not yet sufficient.

* * *

## **94. Minimal pass criteria**

The first version of the cognitive data model passes when:
    
    
    core object schemas exist
    objects have ids
    objects have schema versions
    objects have statuses
    objects reference upstream evidence
    signals are separate from interpretations
    belief updates require error references
    actions require expected effects
    outcomes are separate from attempts
    memory traces reference source objects
    uncertainty can be represented
    invalid records can be quarantined

It fails when:
    
    
    logs are treated as traces
    text is treated as belief
    memory is treated as source
    actions lack expected outcome
    confidence is global
    records cannot be linked
    schema validation is optional

# **Part XX -- Final Statement**

The cognitive core cannot be implemented as vague language, hidden context, unstructured logs, or loose memory.

It needs a data model.

The data model must preserve the distinctions that make the project original:
    
    
    body is not world
    sensor is not truth
    signal is not interpretation
    prediction is not desire
    error is not surprise
    precision is not confidence
    belief is not memory
    action is not obedience
    outcome is not cause
    memory is not transcript
    metacognition is not consciousness

The final principle is:

The cognitive data model is the skeleton of the bounded predictive machine. Every prediction, signal, interpretation, error, precision estimate, belief update, action, outcome, cause classification, memory trace, metacognitive assessment, and tick must be represented as structured, referenceable, schema-valid evidence, so the system can know not only what it did, but why it expected, how it interpreted, where it was wrong, what changed, what remained uncertain, and what should happen next.

That is the cognitive data model.
