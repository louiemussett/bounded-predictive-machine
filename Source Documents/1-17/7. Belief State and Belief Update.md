# **A07 -- Belief State and Belief Update**

**Project status:** cognitive-core canon  
**Purpose:** define belief as structured model state and define belief update as the system's core adaptive act.  
**Rule:** belief is not opinion, memory, language, or an LLM response. Belief is the structured model the system uses to predict, interpret, evaluate error, select action, and reconstruct memory. Belief may update only through admissible, precision-weighted prediction error.
* * *

## **1. Why this document exists**

The system cannot be adaptive unless it can change its model.

But model change must be precise.

The system should not update merely because:
    
    
    a signal arrived
    a user said something
    an LLM produced an explanation
    a memory was retrieved
    an action failed
    a trace exists

Those may become evidence.

They are not automatically belief updates.

The system needs a structured account of:
    
    
    what it currently models
    what prediction came from that model
    what signal arrived
    how the signal was interpreted
    what prediction error occurred
    how precise that error was
    which part of the model should change
    how strong the change should be
    what uncertainty remains afterward

This document defines that structure.

* * *

## **2. Core thesis**

The core thesis is:

Belief is the system's structured operating model, and belief update is the controlled transformation of that model under pressure from admissible, precision-weighted prediction error.

In simpler form:
    
    
    belief state
    → prediction
    → signal
    → interpretation
    → prediction error
    → precision weighting
    → belief update
    → posterior belief state
    → new prediction

Belief is not something the system "feels."

Belief is the model it uses.

Belief update is not remembering.

Belief update is model change.

* * *

## **3. Short definition**

A **belief state** is:
    
    
    the current structured model used by the system to predict, interpret, evaluate error, select action, and reconstruct memory.

A **belief component** is:
    
    
    a specific part of belief state, such as body model, sensor model, operator model, action model, memory model, or viability model.

A **belief update** is:
    
    
    a recorded transformation from prior belief to posterior belief, justified by weighted prediction error.

A **posterior belief** is:
    
    
    the updated belief state after a belief update has been applied.

A **prior belief** is:
    
    
    the belief state before the update.

* * *

## **4. Belief is not opinion**

The word "belief" can be misleading.

In this project, belief does not mean personal opinion.

It does not mean faith.

It does not mean preference.

It does not mean subjective conviction.

It means:
    
    
    the current model state from which the system predicts and acts.

The system should not say:
    
    
    I believe this because I feel it is right.

It should be able to say:
    
    
    this model component currently has this value,
    this confidence,
    this evidence lineage,
    this uncertainty,
    and this update history.

Belief is operational.

* * *

## **5. Belief is not language**

A sentence is not belief.

A paragraph is not belief.

An explanation is not belief.

A chat response is not belief.

Language may describe belief, but it should not be the belief state itself.

Example language:
    
    
    The system expects trace writes to succeed under normal disk conditions.

Underlying belief component:
    
    
    {
      "belief_component": "trace_model",
      "claim": "trace_write_succeeds_under_normal_disk",
      "confidence": 0.78,
      "conditions": {
        "disk_state": "normal",
        "permission_state": "valid"
      },
      "uncertainty": [
        "limited failure history"
      ],
      "source_updates": [
        "bu_trace_001",
        "bu_trace_004"
      ]
    }

The language is a rendering.

The structured object is the belief.

* * *

## **6. Belief is not memory**

Memory stores evidence for reconstruction.

Belief is the current model that uses evidence.

Memory may contain:
    
    
    what was predicted
    what signal arrived
    how it was interpreted
    what error occurred
    what update happened
    what action followed
    what outcome occurred

Belief contains:
    
    
    what the system currently treats as model-state for future prediction

Memory can support belief update.

Memory does not equal belief.

A memory trace may be old, uncertain, contradicted, or context-specific.

Belief must decide how much that memory matters now.

* * *

## **7. Belief is not an LLM response**

An LLM response may propose:
    
    
    interpretations
    summaries
    alternative hypotheses
    possible belief updates

But it must not become belief automatically.

The LLM may say:
    
    
    The user likely wants the next A-series document.

That is not belief yet.

The runtime must convert or reject it through:
    
    
    source check
    signal envelope
    interpretation
    precision estimate
    prediction error
    update eligibility
    belief target

The LLM is a semantic organ.

It does not own belief state.

Each component should be inspectable.

Each component should have evidence lineage.

Each component should have uncertainty.

Each component should be updateable only through allowed update rules.

## **11. Belief state must support prediction**

Belief exists so the system can predict.

A belief that cannot generate prediction is weak.

Example:
    
    
    belief:
    trace writes usually succeed when disk and permission states are normal
    
    prediction:
    next trace write should succeed under current normal disk and permission state

Example:
    
    
    belief:
    operator is continuing the A-series document sequence
    
    prediction:
    next operator request likely asks for the next A-series document

Belief should produce expectations.

If it cannot, it may be archive, not belief.

* * *

## **12. Belief state must support interpretation**

Belief also shapes interpretation.

Example:
    
    
    current belief:
    operator is building a cognitive-core canon
    
    signal:
    "A07 -- Belief State and Belief Update"
    
    interpretation:
    operator requests generation of the next A-series canon document

Without belief state, interpretation becomes contextless.

With belief state, signal can be interpreted relative to the system's current model.

Belief shapes interpretation, but must not force signal to fit.

* * *

## **13. Belief state must support action**

Belief supports action by modelling expected consequences.

Example:
    
    
    belief:
    asking clarification often reduces semantic uncertainty when operator request is ambiguous
    
    action candidate:
    ask clarification
    
    predicted effect:
    semantic uncertainty decreases

Example:
    
    
    belief:
    writing a document directly is appropriate when operator request is precise and low risk
    
    action candidate:
    generate document
    
    predicted effect:
    operator receives requested document

Action should use belief.

Action should not bypass belief.

* * *

## **14. Belief state must support memory reconstruction**

Belief affects memory retrieval.

A memory trace is reconstructed under current belief.

Example:
    
    
    old memory:
    operator asked for roadmap
    
    new belief:
    operator wanted original predictive-core alignment, not safety-canon continuation
    
    reconstruction:
    the roadmap request should be interpreted as conceptual recentering, not merely another governance document

Memory is not static.

Belief can revise how memory is reconstructed.

But belief must not rewrite the original trace.

* * *

## **15. Prior belief**

A prior belief is the model before an update.

Before updating, the system should preserve:
    
    
    prior_belief_ref
    prior_claim
    prior_confidence
    prior_uncertainty
    prior_evidence

A belief update without prior reference is incomplete.

The system must know what changed.

Example:
    
    
    prior:
    project centre is safety-governed runtime architecture
    
    posterior:
    project centre is predictive machine cognition; safety canon is containment shell

The difference is the update.

* * *

## **16. Posterior belief**

Posterior belief is the model after update.

It should record:
    
    
    what changed
    what stayed the same
    what confidence changed
    what uncertainty remains
    what evidence caused the change
    what predictions should change next

Posterior belief becomes the next prior.

This is the continuity of the cognitive loop.
    
    
    prior
    → prediction
    → error
    → update
    → posterior
    → next prediction

* * *

## **17. Belief update is model change**

A belief update is not a note.

It is not a memory.

It is not a summary.

It is a structured change in the model.

A belief update should answer:
    
    
    which model component changed?
    what prior belief was changed?
    what evidence caused the change?
    what prediction error applied pressure?
    how precise was the evidence?
    how strong was the update?
    what is the new belief?
    what uncertainty remains?

If these cannot be answered, adaptation has not occurred.

* * *

## **18. Belief update requires prediction error**

Belief update should be caused by prediction error, not raw signal.

Correct:
    
    
    prediction
    → interpreted observation
    → prediction error
    → weighted error
    → belief update

Incorrect:
    
    
    signal
    → belief update

Example:
    
    
    signal:
    operator says current framing is wrong
    
    interpretation:
    operator correction targets project model
    
    prediction error:
    system expected safety canon continuation but operator wants original cognitive core
    
    weighted error:
    high
    
    belief update:
    project model recenters around predictive machine cognition

The update comes from the error, not from signal alone.

* * *

## **19. Belief update requires precision**

Prediction error must be weighted by precision before updating belief.

A large error with low precision may produce only weak update.

A small but high-precision correction may produce meaningful update.

Example:
    
    
    low precision:
    ambiguous external file implies a new project direction
    
    update:
    do not update project model strongly

Example:
    
    
    high precision:
    operator directly corrects current framing
    
    update:
    strong scoped update to project_model and task_model

Precision protects the model from noise.

* * *

## **20. Belief update requires target**

An update must specify its belief target.

Possible targets:
    
    
    body_model
    sensor_model
    operator_model
    task_model
    project_model
    action_model
    self_model
    cause_model
    viability_model
    memory_model
    uncertainty_model
    safety_model

A belief update should not update everything.

Example:
    
    
    trace write failed

Targets:
    
    
    trace_model
    body_model
    viability_model

Not:
    
    
    operator_model
    project_model
    semantic_memory

Targeting prevents model pollution.

* * *

## **21. Belief update requires scope**

An update must have scope.

Scope defines how far the update applies.

Possible scopes:
    
    
    current_tick
    current_document
    current_task
    current_operator_session
    current_project
    specific_sensor
    specific_action
    specific_memory
    general_model
    structural_rule

Example:
    
    
    operator correction:
    "this roadmap should not copy the safety canon"

Valid scope:
    
    
    current project-document generation and conceptual alignment

Invalid scope:
    
    
    all future documents must avoid all safety concepts

Scope prevents overgeneralization.

* * *

## **22. Belief update requires strength**

Update strength determines how much confidence changes.

Possible strengths:
    
    
    none
    weak
    moderate
    strong
    critical
    structural_revision_required

Update strength may depend on:
    
    
    weighted error
    precision
    relevance
    source reliability
    prior confidence
    contradictory evidence
    scope
    risk

Strong update should require strong evidence.

Structural revision should require protected review.

* * *

## **23. Belief update preserves uncertainty**

A belief update should not erase uncertainty.

It should record what remains unknown.

Example:
    
    
    posterior:
    cognitive core should be central
    
    remaining uncertainty:
    exact implementation order remains provisional
    relationship between A-series and old safety canon requires integration
    schemas are still conceptual

Uncertainty is not a flaw.

It is part of the posterior model.

* * *

## **24. Belief update preserves alternatives**

A belief update should record rejected or weaker alternatives when useful.

Example:
    
    
    update:
    operator wants A-series cognitive-core canon
    
    rejected alternatives:
    operator wants only a short outline
    operator wants canvas edit
    operator wants old safety-canon continuation

Alternatives help future reconstruction.

They also prevent false certainty.

* * *

## **25. Belief update may be local**

Many updates should be local.

Example:
    
    
    operator asks for A07

Local update:
    
    
    current task is A07 generation
    operator is continuing sequence

It should not update:
    
    
    global theory of operator
    global project purpose
    safety model
    machine body model

Local updates keep the system stable.

* * *

## **26. Belief update may be global**

Some updates are broader.

Example:
    
    
    operator says the core must be original predictive cognition, not copied from safety canon

This may update:
    
    
    project_model
    document_sequence_model
    memory_reconstruction_model
    task_model

A global update requires high precision and clear target.

It should still preserve uncertainty and evidence lineage.

* * *

## **27. Belief update may be blocked**

A proposed belief update may be blocked.

Reasons:
    
    
    inadmissible signal
    privacy violation
    unknown source
    low precision
    unsupported interpretation
    schema failure
    safety conflict
    structural prior conflict
    requires human review

Blocked updates should be recorded when useful.

They may become memory evidence, but should not change belief.

* * *

## **28. Belief update may be delayed**

Some updates need more evidence.

Example:
    
    
    one sensor reports unusual CPU spike

Possible decision:
    
    
    delay update
    observe again
    accumulate evidence
    increase uncertainty slightly

Delayed update prevents overreaction.

The system can store weak evidence without changing belief strongly.

* * *

## **29. Belief update may increase uncertainty**

Not all updates increase confidence.

Some updates reveal that the previous model was incomplete.

Example:
    
    
    trace says action succeeded
    body state shows no expected effect

Belief update may be:
    
    
    increase uncertainty about action outcome model
    increase uncertainty about trace reliability
    do not select one cause yet

This is a valid update.

Learning can mean knowing less falsely.

* * *

## **30. Belief update may reduce uncertainty**

A high-precision correction may reduce uncertainty.

Example:
    
    
    operator says:
    the A-series is the correct final outline

Update:
    
    
    increase confidence in A-series sequence
    reduce uncertainty about document structure

Uncertainty reduction should still be scoped.

It should not become total certainty.

* * *

## **31. Belief update and confidence**

Belief components should track confidence.

Confidence may change through update.

Example:
    
    
    prior confidence:
    0.62 that operator wants cognitive-core sequence
    
    evidence:
    operator requests A07 after A00--A06
    
    posterior confidence:
    0.91

Confidence should be calibrated over time.

Confidence should not be inflated merely because output was fluent.

* * *

## **32. Belief update and contradiction**

Belief state must allow contradiction.

Contradictory evidence should not be silently erased.

Example:
    
    
    earlier belief:
    safety canon is central
    
    later correction:
    cognitive core is central

The update should record:
    
    
    prior framing contradicted
    new framing accepted
    reason for shift
    old safety canon retained as shell

This preserves conceptual continuity.

* * *

## **33. Belief update and memory revision**

When belief updates, memory reconstruction may change.

Example:
    
    
    old memory:
    roadmap request interpreted as continuation of safety architecture
    
    new belief:
    roadmap request was a correction back to original cognitive architecture

The system should not rewrite the old memory.

It should add a revision:
    
    
    memory reconstruction updated under new project_model

Memory traces remain.

Interpretation of memory changes.

* * *

## **34. Belief update and prediction revision**

After belief update, predictions should revise.

Example:
    
    
    belief update:
    operator is generating A-series sequentially
    
    new prediction:
    next request likely asks for A08 -- Action as Future Error Management

Belief update is incomplete if it does not affect future prediction where relevant.

The posterior must become the next prior.

* * *

## **35. Belief update and action policy**

Belief update may affect action selection.

Example:
    
    
    belief update:
    operator wants full document generation, not brief outline
    
    action implication:
    generate full A-series document

Example:
    
    
    belief update:
    trace store is unreliable
    
    action implication:
    restrict adaptation and enter safer mode

Action should respond to updated belief through policy, not direct impulse.

* * *

## **36. Belief update and safety shell**

The safety shell may constrain belief update.

Examples:
    
    
    forbidden signal cannot update belief
    private data may not enter memory
    LLM output cannot directly update belief
    structural priors cannot be rewritten by ordinary evidence

Safety protects belief integrity.

But safety should not replace belief update.

The cognitive core still needs model change.

* * *

## **37. Structural beliefs**

Some beliefs are structural.

They define the architecture.

Examples:
    
    
    signals are not truth
    interpretation comes before error
    precision weights update
    LLM output is not authority
    memory is reconstructive
    unregistered action is denied

Structural beliefs should not be revised by ordinary signals.

They may require protected review.

They are closer to architecture law than learned belief.

* * *

## **38. Learned beliefs**

Learned beliefs are refined by evidence.

Examples:
    
    
    this sensor is usually reliable
    this operator phrase usually means continuation
    this action usually reduces polling cost
    this memory reconstruction is low confidence
    this document sequence is currently active

Learned beliefs should be revisable.

They should cite evidence.

They should decay or weaken when contradicted.

* * *

## **39. Belief decay**

Some beliefs should decay over time.

Examples:
    
    
    operator currently wants this exact document
    current task context
    temporary resource pressure
    recent sensor anomaly

Other beliefs should persist longer:
    
    
    project core thesis
    sensor reliability history
    action consequence pattern
    memory reconstruction revisions

Belief state should distinguish temporary context from durable model.

* * *

## **40. Belief persistence**

Persistent beliefs should remain available across ticks or sessions if storage permits.

Examples:
    
    
    project_model
    sensor reliability model
    action consequence model
    memory model
    operator pattern model

Persistence requires trace or memory backing.

The system should not persist unsupported beliefs indefinitely.

Persistent belief should remain auditable.

* * *

## **41. Belief reset**

Belief may need reset under failure.

Reasons:
    
    
    corrupted belief store
    invalid schema
    trace gap
    recovery event
    operator reset instruction
    structural revision

Reset should preserve evidence when possible.

A reset should mark continuity break.

The system should not pretend an uninterrupted belief chain when one was broken.

* * *

## **42. Belief uncertainty model**

The belief state should include uncertainty.

Uncertainty may track:
    
    
    low-confidence beliefs
    conflicting beliefs
    unknown causes
    ambiguous interpretations
    weak sensors
    stale memories
    unvalidated LLM proposals
    action outcome uncertainty

Uncertainty is not separate from belief.

It is part of belief state.

* * *

## **43. Belief and metacognition**

Metacognition begins when the system can inspect its own belief uncertainty.

Examples:
    
    
    I have low confidence in this interpretation.
    This action outcome model is weak.
    This memory reconstruction is contradicted.
    This sensor has poor precision for this target.

This does not imply consciousness.

It is operational self-monitoring of model quality.

* * *

## **44. Belief and operator correction**

Operator correction can produce strong updates when scoped.

Example correction:
    
    
    this should be about the original cognitive idea, not copied from the safety work

Valid update:
    
    
    project_model recenters around predictive machine cognition
    safety canon becomes containment shell
    document outline changes to A-series

Invalid update:
    
    
    discard all prior safety work
    treat every future correction as global
    make operator text direct authority

Correction is high-value signal, not unlimited power.

* * *

## **45. Belief and command**

A command-like signal should not directly update belief or trigger action.

It should be interpreted as command candidate.

Belief update may occur about:
    
    
    operator wants a command considered
    current task may have changed
    approval may be pending

But action requires separate authorization.

Belief update and command execution must remain distinct.

* * *

## **46. Belief and goals**

Goals are not primitive belief.

A future goal layer may be represented in belief state as:
    
    
    active bounded goal
    goal scope
    success condition
    expiry
    allowed actions
    viability constraints

But A07 does not introduce goals as core.

Belief state can exist without goals.

Prediction and update come first.

* * *

## **47. Belief and tasks**

Tasks may be represented in belief state as current context.

Example:
    
    
    current_task:
    generate A07 -- Belief State and Belief Update

But task state is not the whole belief state.

A task is a bounded work object.

Belief is the model used to interpret and perform work.

* * *

## **48. Belief and self-model**

The self-model is a belief component.

It may include:
    
    
    what actions I can perform
    what effects my actions usually have
    what resources I consume
    what sensors describe my body
    what failures I have caused
    what changes were external
    what causes remain unknown

The self-model is operational.

It is not narrative identity.

* * *

## **49. Belief and cause model**

The cause model tracks causal expectations.

It should distinguish:
    
    
    self_caused
    external
    mixed
    unknown
    not_applicable

Belief update should not turn temporal sequence into cause.

Example:
    
    
    memory rose after action

may update:
    
    
    possible self-cause confidence

not:
    
    
    definite self-cause

unless evidence supports it.

* * *

## **50. Belief and sensor model**

Sensor reliability is part of belief.

Sensor model beliefs may include:
    
    
    usual precision
    failure history
    latency
    staleness pattern
    noise profile
    target-specific reliability

Sensor-model update is critical because future precision estimates depend on it.

If the sensor model is wrong, every downstream update may be wrong.

* * *

## **51. Belief and action model**

The action model tracks expected consequences of actions.

It may include:
    
    
    action type
    expected effect
    expected cost
    failure modes
    side effects
    required viability state
    confidence
    uncertainty

Action-model belief updates come from action-outcome errors.

This is how the system learns what its actions do.

* * *

## **52. Belief and viability model**

The viability model tracks conditions for safe operation.

It may include:
    
    
    safe conditions
    degraded conditions
    critical conditions
    failed conditions
    unknown conditions
    resource thresholds
    trace requirements
    sensor requirements
    action restrictions

Viability belief update may occur when operational predictions fail.

Example:
    
    
    trace failure did not recover as expected
    → viability model updates toward more restrictive classification

* * *

## **53. Belief and project model**

For this project, the project model matters because the system is being developed through documents.

Project-model beliefs may include:
    
    
    core thesis
    document sequence
    conceptual distinctions
    relationship between A-series and safety canon
    current document target
    operator corrections

This is a semantic model, not a machine-body model.

It should update from high-precision operator correction and document context.

Example:

## **57. Belief update lifecycle**

A belief update may move through statuses:
    
    
    proposed
    validated
    applied
    partially_applied
    blocked
    delayed
    requires_review
    superseded
    reverted
    archived

The system should not silently apply major updates.

Update status should be traceable.

* * *

## **58. Belief update validation**

Before applying an update, the system should check:
    
    
    source prediction existed
    signal was admissible
    signal was interpreted
    error was typed
    precision was estimated
    target model was identified
    scope was defined
    update strength was justified
    structural priors were not violated
    uncertainty was preserved

If these checks fail, the update should be blocked or delayed.

* * *

## **59. Belief update application**

Applying an update means changing the target model.

Application should produce:
    
    
    new belief component version
    updated confidence
    updated uncertainty
    updated lineage
    prediction implications
    memory implications
    trace record

Application should not erase the prior version.

Belief should be versioned.

* * *

## **60. Belief update trace**

Every meaningful belief update should create a trace.

Trace should record:
    
    
    update id
    prior belief reference
    posterior belief reference
    source error
    source observation
    precision
    update strength
    target model
    uncertainty
    status

Without trace, belief update is not auditable.

Unauditable belief update is unsafe.

## **61. Belief update and rollback**

Belief updates may need rollback or revision.

Reasons:
    
    
    source signal invalidated
    interpretation revised
    privacy violation discovered
    operator correction contradicts update
    schema error
    memory reconstruction corrected

Rollback should not erase the update.

It should create a revision record.

Example:
    
    
    belief update reverted because source observation was invalidated

History remains.

Current belief changes.

* * *

## **62. Belief update and structural revision**

Some updates target structural assumptions.

Examples:
    
    
    change the definition of signal
    change whether LLM output can update belief
    change memory from reconstructive to transcript-based

These should require protected revision.

Ordinary prediction error should not rewrite structural laws.

Structural revision should be rare, explicit, and reviewed.

* * *

## **63. Belief update and over-update**

Over-update occurs when evidence changes too much.

Examples:
    
    
    one correction rewrites entire operator model
    one trace failure makes trace store permanently untrusted
    one action failure disables all actions
    one document request changes the whole project thesis

Avoid over-update through:
    
    
    scope limits
    precision weighting
    update thresholds
    alternative preservation
    confidence calibration
    human review for structural change

* * *

## **64. Belief update and under-update**

Under-update occurs when the system ignores evidence.

Examples:
    
    
    repeated operator corrections do not change project model
    repeated action failures do not change action model
    repeated sensor failures do not change sensor model
    high-precision mismatch is treated as noise

Avoid under-update through:
    
    
    error accumulation
    support and contradiction tracking
    calibration
    threshold review
    memory reconstruction

The system must be stable but not rigid.

* * *

## **65. Belief update and calibration**

Belief confidence should be calibrated.

Calibration asks:
    
    
    when confidence was high, was prediction later confirmed?
    when update was strong, did future evidence support it?
    when precision was estimated high, was it reliable?

Calibration may update:
    
    
    confidence_model
    precision_model
    sensor_model
    operator_model
    action_model
    memory_model

Without calibration, belief confidence becomes decoration.

## **71. Evaluation questions**

Belief state and belief update should be evaluated by asking:
    
    
    Is belief represented as structured model state?
    Can belief components be inspected?
    Does each belief component have confidence and uncertainty?
    Does belief update cite prediction error?
    Was the error precision-weighted?
    Is the target model identified?
    Is update scope defined?
    Is update strength justified?

    Are alternatives and uncertainty preserved?

    Can memory reconstruct why belief changed?

## **79. Final statement**

Belief is the system's current structured model.

Belief update is the system's core adaptive act.

The system does not learn by storing signals.

It learns by changing model state under justified pressure from admissible, precision-weighted prediction error.

Belief may update only when a prior belief generates a prediction, an interpreted observation produces typed prediction error, precision weighting makes that error update-eligible, and a scoped target model is transformed into a posterior belief with lineage, confidence, uncertainty, and revision history preserved.

That is belief state and belief update.
