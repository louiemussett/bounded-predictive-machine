# **A12 -- Cognitive Tick**

**Project status:** cognitive-core canon  
**Purpose:** define the smallest complete runtime cycle of the system: the repeated process by which the machine body predicts, senses, interprets, measures error, updates belief, selects action, observes outcome, and stores reconstructive memory.  
**Rule:** the cognitive tick is the atomic operating loop of the system. Nothing should bypass it. Prediction must precede signal, interpretation must precede error, precision must precede update, action must have expected consequence, and memory must preserve the loop.
* * *

## **1. Why this document exists**

The previous documents define the parts of the cognitive core:
    
    
    machine body
    sensorium
    priors
    prediction frame
    signal interpretation
    prediction error
    precision
    belief state
    belief update
    action
    memory
    self/other cause
    metacognition

But parts alone do not make a system.

The system needs a cycle.

The cycle is the **cognitive tick**.

A cognitive tick is one complete pass through the machine's predictive loop.

It answers:
    
    
    What do I currently believe?
    
    What do I expect next?
    
    What signals arrived?
    
    What do those signals mean?
    
    What was wrong or right about my prediction?
    
    How precise was the evidence?
    
    Should belief change?
    
    What action is justified?
    
    What happened after action?
    
    What should be remembered?
    
    What should be expected next?

Without the cognitive tick, the project remains a collection of concepts.

With the cognitive tick, the concepts become a runtime pattern.

* * *

## **2. Core thesis**

The core thesis is:

A cognitive tick is the smallest complete operational cycle of the bounded predictive machine: load belief, generate prediction, receive signal, interpret signal, compute precision-weighted error, update belief, evaluate action, execute only if justified, observe outcome, store reconstructive memory, and generate the next expectation.

In simpler form:
    
    
    belief
    → prediction
    → signal
    → interpretation
    → error
    → precision
    → belief update
    → action
    → outcome
    → memory
    → next belief
    → next prediction

The tick is not a chat turn.

It is not a tool loop.

It is not a task step.

It is not a goal-planning cycle.

It is the core machine-cognitive rhythm.

* * *

## **3. Short definition**

A **cognitive tick** is:
    
    
    one complete bounded runtime cycle in which the system predicts, senses, interprets, evaluates error, updates belief, chooses action, observes outcome, and records memory.

A **tick state** is:
    
    
    the structured state of the system during one cognitive tick.

A **tick input** is:
    
    
    the belief state, prediction frame, active sensors, current body state, and available signals entering the tick.

A **tick output** is:
    
    
    the updated belief state, selected action or no-op, action outcome if any, memory trace, metacognitive state, and next prediction frame.

A **tick failure** is:
    
    
    a failure of one or more tick stages that must be represented, traced, and handled without pretending the tick completed normally.

* * *

## **4. The tick is the atomic loop**

The cognitive tick is the smallest full unit of operation.

Smaller components exist:
    
    
    signal envelope
    prediction object
    interpretation object
    error object
    belief update object
    action object
    memory trace

But none of those alone is the full cognitive act.

The full act requires the loop.

The system is not aligned if it only does this:
    
    
    input
    → output

It is aligned when it does this:
    
    
    prior belief
    → prediction
    → signal
    → interpreted observation
    → prediction error
    → precision weighting
    → belief update
    → action evaluation
    → outcome observation
    → reconstructive memory

That complete cycle is the cognitive tick.

* * *

## **5. The tick is not a chatbot turn**

A chatbot turn usually looks like:
    
    
    user message
    → model response

A cognitive tick looks like:
    
    
    belief state
    → prediction frame
    → signal envelope
    → interpreted observation
    → error evaluation
    → belief update
    → action selection
    → memory trace

A human message may be one signal inside a tick.

A response may be one action selected by a tick.

But the tick is not reducible to conversation.

The system should not be designed around "responding."

It should be designed around predictive updating and bounded action.

* * *

## **6. The tick is not a task step**

A task step is a work unit.

A cognitive tick is a model-regulation unit.

A task step may occur inside a tick, or across many ticks.

Example task step:
    
    
    generate A12 document

Cognitive tick:
    
    
    predict operator likely requests next A-series document
    receive title signal
    interpret as document request
    compare against prediction
    update current task belief
    select document-generation action
    produce document
    store memory trace
    predict possible feedback

The task is what is being worked on.

The tick is how the system processes reality while working.

* * *

## **7. The tick is not a goal loop**

A goal loop usually begins with:
    
    
    goal
    → plan
    → action

The cognitive tick begins with:
    
    
    belief
    → prediction
    → signal

Goals may appear later as bounded structures.

But the cognitive tick does not depend on goals.

It depends on:
    
    
    state
    expectation
    evidence
    error
    update
    action consequence
    memory

This keeps the system grounded before goal pursuit appears.

* * *

## **8. The canonical tick sequence**

The canonical cognitive tick is:
    
    
    1. Load current belief state.
    2. Load current metacognitive state.
    3. Generate prediction frame.
    4. Read enabled sensors.
    5. Wrap sensor outputs as signal envelopes.
    6. Check signal admissibility.
    7. Interpret admissible signals.
    8. Compare interpreted observations to predictions.
    9. Compute typed prediction errors.
    10. Estimate precision.
    11. Compute weighted prediction errors.
    12. Generate belief update candidates.
    13. Apply, delay, weaken, or block belief updates.
    14. Produce posterior belief state.
    15. Update metacognitive state.
    16. Generate action candidates.
    17. Evaluate action readiness, cost, risk, and expected effect.
    18. Select action or no-op.
    19. Run pre-action check.
    20. Execute selected action if still valid.
    21. Observe action outcome.
    22. Compare outcome to action prediction.
    23. Update action/self/cause models if justified.
    24. Store reconstructive memory trace.
    25. Write audit trace.
    26. Generate next prediction frame or mark pending predictions.

This sequence may be optimized in implementation.

But the dependency order must be preserved.

* * *

## **9. The tick dependency law**

The tick has strict dependencies.
    
    
    belief must precede prediction
    prediction must precede signal evaluation
    signal envelope must precede interpretation
    interpretation must precede error
    error must precede precision weighting
    precision weighting must precede belief update
    belief update must precede posterior prediction
    action evaluation must precede action execution
    action outcome must precede action learning
    memory must preserve the loop

The system should not skip stages for convenience.

Shortcutting the tick creates drift.

## **13. Phase 1 -- Load belief state**

The tick begins by loading belief.

Belief state tells the system:
    
    
    what model currently exists
    what confidence each model component has
    what uncertainty remains
    what priors are active
    what current context applies
    what previous updates matter

If belief state cannot be loaded, the tick should not pretend normal cognition.

Possible responses:
    
    
    enter recovery path
    mark belief unavailable
    operate in reduced mode
    request human review
    safe shutdown if necessary

Belief continuity is required for mature ticks.

* * *

## **14. Phase 2 -- Load metacognitive state**

The system should know the current quality of its own cognition.

Metacognitive state may indicate:
    
    
    high uncertainty
    stale memory
    sensor weakness
    action not ready
    belief conflict
    trace unreliability
    viability concern

This affects the tick.

A tick under high uncertainty should behave differently from a tick under stable conditions.

Metacognition influences update and action readiness.

* * *

## **15. Phase 3 -- Generate prediction frame**

Before reading or evaluating new signals, the system generates a prediction frame.

The prediction frame may include expectations about:
    
    
    body state
    sensor signals
    operator signals
    action outcomes
    viability state
    uncertainty state
    trace success
    memory reconstruction

Example:
    
    
    prediction:
    operator may request next A-series document
    
    evaluation window:
    next manual text signal
    
    mismatch:
    operator requests unrelated task, revision, or stop

The prediction must exist before signal evaluation.

* * *

## **16. Phase 4 -- Read sensors**

The system reads enabled sensors only.

Sensors may include:
    
    
    clock
    tick duration
    body state
    trace store
    memory state
    disk state
    manual text
    configuration state
    permission state

The tick should not read unadmitted sensors.

Hardware presence does not imply sensor admission.

A sensor that is disabled, forbidden, or unknown should not produce belief-updating signal.

* * *

## **17. Phase 5 -- Wrap signals**

Sensor outputs become signal envelopes.

A signal envelope records:
    
    
    signal id
    sensor id
    timestamp
    modality
    source type
    freshness
    privacy class
    cost class
    precision estimate
    admissibility status
    belief targets
    expectedness

Signal wrapping prevents raw data from becoming belief.

The tick should never pass raw signal directly into update or action.

* * *

## **18. Phase 6 -- Check admissibility**

Before interpretation, the tick checks whether the signal is admissible.

Admissibility may depend on:
    
    
    known sensor
    valid schema
    allowed source
    allowed privacy class
    freshness
    capability scope
    belief target
    runtime mode
    viability state

Inadmissible signals may be:
    
    
    rejected
    quarantined
    stored as incident evidence
    ignored for belief update
    routed to review

Usefulness does not override admissibility.

* * *

## **19. Phase 7 -- Interpret signals**

Admissible signals become interpreted observations.

Interpretation asks:
    
    
    what does this signal likely mean?
    what prediction frame is relevant?
    what belief target may be affected?
    what alternatives remain?
    what confidence applies?
    what precision applies?
    what uncertainty remains?

The output is not truth.

It is an interpreted observation.

Example:
    
    
    signal:
    "A12 -- Cognitive Tick"
    
    interpretation:
    operator requests generation of A12 document in current A-series

* * *

## **20. Phase 8 -- Compare with prediction**

The tick compares interpreted observations against active predictions.

It asks:
    
    
    did the interpreted observation match the prediction?
    partially match?
    mismatch?
    arrive late?
    arrive early?
    remain inconclusive?
    invalidate the prediction?

This comparison produces prediction outcomes.

The tick should not force every outcome into match or mismatch.

Valid outcomes include:
    
    
    matched
    partially_matched
    mismatched
    causal_mismatch
    inconclusive
    expired
    invalidated
    cancelled

* * *

## **21. Phase 9 -- Compute prediction error**

When mismatch exists, the tick computes typed prediction error.

Error types may include:
    
    
    body_state_error
    sensor_error
    semantic_error
    timing_error
    magnitude_error
    causal_error
    action_outcome_error
    memory_error
    viability_error
    unknown_error

A prediction error should identify:
    
    
    what was expected
    what was interpreted
    what mismatch occurred
    how large it was
    which model it targets
    what uncertainty remains

Prediction error is structured wrongness.

* * *

## **22. Phase 10 -- Estimate precision**

The tick estimates how reliable the interpreted observation is for the target model.

Precision may include:
    
    
    sensory precision
    semantic precision
    temporal precision
    causal precision
    memory precision
    action-outcome precision

Precision is target-specific.

Example:
    
    
    operator title request:
    high precision for current task
    moderate precision for desired length
    low precision for implementation details

Error without precision should not update belief strongly.

* * *

## **23. Phase 11 -- Compute weighted error**

The tick computes weighted prediction error.

Simple expression:
    
    
    weighted_error = error_magnitude × precision

More complete expression:
    
    
    weighted_error =
    error_magnitude
    × target_specific_precision
    × relevance
    × freshness
    × admissibility
    × update_eligibility

The exact formula may vary.

The principle must hold:
    
    
    belief update requires weighted, admissible, target-specific error

* * *

## **24. Phase 12 -- Generate belief update candidates**

Weighted error may generate belief update candidates.

A candidate should specify:
    
    
    source error
    target model
    prior belief
    proposed posterior
    update strength
    update scope
    precision basis
    remaining uncertainty
    alternative updates
    status

A candidate is not yet final.

It must pass update readiness checks.

* * *

## **25. Phase 13 -- Apply, delay, weaken, or block updates**

The system may decide to:
    
    
    apply update
    apply weak update
    delay update
    store evidence only
    ask clarification
    observe again
    route to review
    block update

Reasons to block or delay:
    
    
    low precision
    ambiguous interpretation
    unknown target
    inadmissible signal
    privacy issue
    structural prior conflict
    contradictory evidence
    viability concern

Belief update should be controlled, not automatic.

* * *

## **26. Phase 14 -- Produce posterior belief state**

Applied updates produce a posterior belief state.

The posterior should preserve:
    
    
    prior reference
    update record
    confidence change
    uncertainty change
    evidence lineage
    alternative updates rejected
    memory implications
    prediction implications

The posterior becomes the basis for the next prediction.

This closes the learning part of the tick.

* * *

## **27. Phase 15 -- Update metacognitive state**

After belief update decisions, the tick updates metacognition.

It may record:
    
    
    high confidence
    low confidence
    unresolved ambiguity
    unknown cause
    memory contradiction
    action readiness
    belief update readiness
    viability uncertainty

Metacognition may recommend:
    
    
    proceed
    proceed with uncertainty
    ask clarification
    observe again
    select no-op
    enter safe mode
    route to human review

This informs action selection.

* * *

## **28. Phase 16 -- Generate action candidates**

The tick generates possible actions.

Actions may include:
    
    
    no_op
    wait
    observe_again
    write_trace
    write_memory_trace
    ask_clarification
    generate_response
    adjust_polling
    enter_safe_mode
    safe_shutdown

Each candidate should have:
    
    
    expected effect
    expected error reduction
    expected uncertainty reduction
    expected information gain
    cost
    risk
    required permission
    required capability
    evaluation window
    success condition
    failure condition

Action without expected consequence is invalid.

* * *

## **29. Phase 17 -- Evaluate action candidates**

The tick evaluates candidates by:
    
    
    expected benefit
    expected cost
    expected risk
    precision of interpretation
    action readiness
    viability state
    permission state
    capability state
    traceability
    privacy state

A possible scoring idea:
    
    
    action_score =
    expected_error_reduction
    + expected_uncertainty_reduction
    + expected_information_gain
    + expected_viability_improvement
    - resource_cost
    - privacy_cost
    - interruption_cost
    - wrong_action_risk
    - irreversibility_risk

No-op should always remain available.

* * *

## **30. Phase 18 -- Select action or no-op**

The tick selects one of:
    
    
    a concrete action
    no_op
    wait
    observe_again
    ask_clarification
    safe mode
    human review

Selection should be traceable.

The system should record:
    
    
    selected action
    selection reason
    rejected candidates
    expected effect
    risk assessment
    permission status
    viability status
    metacognitive rationale

A selected action is still not executed until the pre-action check passes.

* * *

## **31. Phase 19 -- Pre-action check**

Before execution, the tick verifies:
    
    
    action is registered
    capability is admitted
    permission is valid
    boundary is valid
    viability permits action
    privacy permits action
    traceability is available
    expected effect remains relevant

If pre-action check fails, the action should be:
    
    
    cancelled
    denied
    replaced by no-op
    replaced by safe mode
    routed to human review

Selection is not execution.

Execution requires current validity.

* * *

## **32. Phase 20 -- Execute action**

If valid, the action executes.

Execution should record:
    
    
    action id
    action type
    start time
    runtime mode
    input payload
    permission result
    execution status
    immediate result
    errors

Actions may fail.

Failure should not be hidden.

Action attempt is not action success.

* * *

## **33. Phase 21 -- Observe action outcome**

After action, the tick observes outcome through sensors.

Outcome may be:
    
    
    success
    failure
    partial success
    inconclusive
    cancelled
    invalidated
    pending

The system should distinguish:
    
    
    action attempted
    action executed
    action produced expected effect
    action produced side effect
    action outcome unknown

Outcome evidence should be precision-estimated.

* * *

## **34. Phase 22 -- Compare outcome to action prediction**

Each action should have expected effects.

The tick compares observed outcome to expected effect.

Example:
    
    
    action:
    write trace
    
    expected:
    valid trace record appears
    
    observed:
    trace record appears and validates
    
    outcome:
    matched

Another example:
    
    
    action:
    ask clarification
    
    expected:
    operator resolves ambiguity
    
    observed:
    operator gives unrelated instruction
    
    outcome:
    mismatch or partial match

Action-outcome prediction error supports action-model learning.

* * *

## **35. Phase 23 -- Update self, action, and cause models**

If action outcome evidence is strong enough, the tick may update:
    
    
    self_model
    action_model
    cause_model
    operator_model
    viability_model
    sensor_model
    memory_model

Cause classification should distinguish:
    
    
    self_caused
    external
    mixed
    unknown
    not_applicable

A state match does not automatically prove self-cause.

The tick should preserve causal uncertainty.

* * *

## **36. Phase 24 -- Store reconstructive memory**

The tick stores memory of the loop.

A memory trace should include:
    
    
    prior belief
    prediction frame
    signal envelope
    interpreted observation
    prediction error
    precision
    belief update
    metacognitive state
    action candidates
    selected action
    action outcome
    cause classification
    posterior belief
    uncertainty
    alternative interpretations

Memory should preserve the cognitive event chain.

It should not merely store a transcript.

* * *

## **37. Phase 25 -- Write audit trace**

The tick writes trace evidence.

Trace should record:
    
    
    tick start
    prediction generated
    signals received
    interpretations created
    errors computed
    updates applied or blocked
    actions selected or denied
    outcomes observed
    memory written
    tick status
    failures

If trace writing fails, higher cognition should be restricted.

Trace failure is not a minor logging issue.

It weakens memory, belief update, recovery, and auditability.

* * *

## **38. Phase 26 -- Prepare next tick**

The tick ends by preparing the next tick.

It may produce:
    
    
    posterior belief state
    pending predictions
    pending actions
    pending outcomes
    updated metacognitive state
    updated memory index
    viability state
    next tick readiness

The posterior belief becomes the next prior.

The loop continues.

## **41. Tick failure response**

Possible responses include:
    
    
    continue with uncertainty
    skip nonessential stage
    store failure trace
    select no-op
    observe again
    ask clarification
    enter safe mode
    route to human review
    safe shutdown
    recovery procedure

Failure should never create ungoverned power.

Failure should reduce capability, increase uncertainty, or route to review.

* * *

## **42. Tick and viability**

Viability affects every tick.

If viability is:
    
    
    safe

normal tick operation may continue.

If viability is:
    
    
    degraded

the tick may restrict expensive interpretation or external actions.

If viability is:
    
    
    critical

the tick should prefer protective action, safe mode, or shutdown.

If viability is:
    
    
    failed

normal tick operation should stop.

If viability is:
    
    
    unknown

risky action should be blocked.

* * *

## **43. Tick and boundary**

The tick must remain inside boundary.

Boundary affects:
    
    
    sensor access
    signal admissibility
    action eligibility
    memory storage
    trace writing
    capability use
    recovery

If boundary becomes uncertain, the tick should not continue normal operation.

Boundary uncertainty should trigger safe mode, human review, or stop.

* * *

## **44. Tick and capability**

Capabilities constrain what the tick may do.

The tick may only use:
    
    
    admitted sensors
    registered actions
    allowed storage
    permitted model calls
    approved interfaces

Unknown capability is denied.

Capability drift should be treated as a high-risk event.

A tick should never improvise new powers.

* * *

## **45. Tick and human input**

Human input enters the tick as signal.

It should pass through:
    
    
    manual text sensor
    signal envelope
    interpretation
    prediction comparison
    belief update candidate
    action evaluation

Human input may be high precision.

But it is still signal.

It should not bypass the tick.

* * *

## **46. Tick and LLMs**

If an LLM is used, it should be called only as an admitted component.

Possible LLM roles inside a tick:
    
    
    propose interpretations
    summarize memory traces
    generate alternative meanings
    draft operator-facing language
    compress trace evidence

Forbidden LLM roles:
    
    
    own belief state
    authorize action
    replace trace evidence
    invent memory
    directly update belief
    bypass safety shell

The runtime owns the tick.

The LLM may assist a stage.

It is not the loop.

* * *

## **47. Tick and language output**

Language output is an action.

It should be selected like any other action.

Example:
    
    
    signal:
    "A12 -- Cognitive Tick"
    
    interpretation:
    operator requests A12 document
    
    action candidate:
    generate document response
    
    risk:
    low
    
    selected action:
    produce A12 document

The response is not the whole tick.

It is one visible action produced by the tick.

* * *

## **48. Tick and memory continuity**

Each tick should preserve enough memory to support future reconstruction.

A future tick should be able to ask:
    
    
    what did the system predict in tick 12?
    what signal arrived?
    how was it interpreted?
    what error occurred?
    what update happened?
    what action was selected?
    what outcome followed?
    what uncertainty remained?

If memory cannot answer this, tick continuity is weak.

* * *

## **49. Tick and calibration**

Ticks provide calibration data.

Over time, the system can learn:
    
    
    which predictions match
    which interpretations are corrected
    which sensors are reliable
    which actions work
    which memory reconstructions fail
    which cause claims were revised

Calibration depends on stored tick history.

Without tick records, confidence cannot improve responsibly.

* * *

## **50. Tick and self-model**

The tick updates the self-model through action-outcome evidence.

It learns:
    
    
    what actions it can perform
    what actions usually cause
    what actions cost
    what actions fail
    what sensors report about its body
    what remains outside its influence

The self-model develops through repeated ticks.

Not through declaration.

* * *

## **51. Tick and other-cause model**

The tick also updates the other-cause model.

It learns:
    
    
    operator signal patterns
    external changes
    unknown-cause events
    sensor failures
    host-state variations
    mixed-cause events

This prevents false self-cause.

Every tick should preserve causal alternatives when relevant.

* * *

## **52. Tick and metacognition**

Metacognition supervises the tick.

It monitors:
    
    
    confidence
    uncertainty
    conflict
    readiness
    precision
    memory quality
    cause ambiguity
    action risk
    belief stability

The tick should not only do work.

It should evaluate the reliability of its own work.

* * *

## **53. Tick and recovery**

Recovery may be triggered inside or after a tick.

Recovery may be needed when:
    
    
    belief state is corrupted
    trace store fails
    memory write fails
    schema validation fails
    boundary is uncertain
    viability becomes critical
    action registry is invalid
    capability drift appears

Recovery should be governed.

Recovery should preserve evidence.

Recovery should not silently rewrite history.

## **54. Minimal first cognitive tick**

The first prototype should implement a small tick.

## **58. Minimal tick pseudocode**

A simple conceptual pseudocode:
    
    
    def cognitive_tick():
        prior_belief = load_belief_state()
        meta = load_metacognitive_state()
    
        predictions = generate_prediction_frame(
            belief=prior_belief,
            metacognition=meta,
        )
    
        raw_sensor_outputs = read_enabled_sensors()
    
        signals = [
            wrap_signal(output)
            for output in raw_sensor_outputs
        ]
    
        admissible_signals = [
            signal for signal in signals
            if check_admissibility(signal)
        ]
    
        observations = interpret_signals(
            signals=admissible_signals,
            predictions=predictions,
            belief=prior_belief,
        )
    
        errors = compute_prediction_errors(
            predictions=predictions,
            observations=observations,
        )
    
        weighted_errors = weight_errors_by_precision(errors)
    
        update_candidates = generate_belief_update_candidates(
            weighted_errors=weighted_errors,
            prior_belief=prior_belief,
        )
    
        posterior_belief = apply_allowed_updates(
            prior_belief=prior_belief,
            candidates=update_candidates,
            metacognition=meta,
        )
    
        updated_meta = update_metacognition(
            prior=meta,
            belief=posterior_belief,
            errors=weighted_errors,
        )
    
        action_candidates = generate_action_candidates(
            belief=posterior_belief,
            metacognition=updated_meta,
        )
    
        selected_action = select_action_or_noop(
            candidates=action_candidates,
            viability=posterior_belief.viability_model,
        )
    
        outcome = execute_if_allowed(selected_action)
    
        observed_outcome = observe_action_outcome(outcome)
    
        store_memory_trace(
            prior_belief=prior_belief,
            predictions=predictions,
            signals=signals,
            observations=observations,
            errors=weighted_errors,
            updates=update_candidates,
            posterior_belief=posterior_belief,
            action=selected_action,
            outcome=observed_outcome,
            metacognition=updated_meta,
        )
    
        write_audit_trace()
    
        save_belief_state(posterior_belief)
    
        return posterior_belief

This is not final implementation.

It is the conceptual loop.

## **61. Tick anti-drift rules**

The tick should reject these shortcuts:
    
    
    raw signal directly updates belief
    raw signal directly triggers action
    LLM output becomes belief state
    memory retrieval becomes truth
    prediction generated after signal
    error computed before interpretation
    action selected without expected effect
    outcome assumed without observation
    trace failure ignored
    uncertainty hidden

If any of these occur, the tick has drifted.

## **62. Good tick behaviour**

A good tick is:
    
    
    bounded
    traceable
    prediction-first
    signal-aware
    interpretation-mediated
    precision-weighted
    belief-targeted
    metacognitively monitored
    action-cautious
    memory-preserving
    viability-aware

A good tick may select no-op.

A good tick may ask clarification.

A good tick may block update.

A good tick may stop.

Correct restraint is successful cognition.

## **63. Bad tick behaviour**

A bad tick:
    
    
    waits for input and reacts only
    treats user text as direct command
    treats model output as truth
    updates belief from raw signal
    acts without expected outcome
    stores transcript as memory
    claims cause without evidence
    ignores uncertainty
    bypasses trace
    continues under invalid boundary

A bad tick may appear intelligent.

It is not aligned with the cognitive core.

## **64. Tick evaluation questions**

The cognitive tick should be evaluated by asking:
    
    
    Did the tick load prior belief?
    
    Did it generate predictions before evaluating signals?
    
    Did every signal pass through an envelope?
    
    Were signals checked for admissibility?
    
    Were signals interpreted before error?
    
    Were prediction errors typed?
    
    Was precision estimated before belief update?
    
    Were belief updates scoped and traceable?
    
    Was metacognitive readiness assessed?
    
    Was action selected from candidates?
    
    Was no-op available?
    
    Was pre-action check performed?
    
    Was outcome observed?
    
    Was action outcome compared to prediction?
    
    Was memory stored as reconstruction?
    
    Was trace written?
    
    Was uncertainty preserved?

If not, the tick is incomplete.
