# A02 — Sensorium and Signal

**Project status:** cognitive-core canon  
**Purpose:** define how the machine body receives signals before interpretation, prediction error, belief update, action, or memory occur.  
**Rule:** the system must never treat sensor output as reality itself. A signal is constrained evidence from a sensor. It must be wrapped, classified, interpreted, precision-estimated, and compared against prediction before it can update belief.

---

## 1. Why this document exists

A bounded machine body cannot think, adapt, or act without signals.

But signals are dangerous if misunderstood.

A signal is not truth.

A signal is not meaning.

A signal is not reality.

A signal is what a sensor provides.

Before the system can update belief, it must know:

```text
what sensor produced the signal
what the sensor measures
what the sensor does not measure
how fresh the signal is
how noisy the signal may be
how precise the signal is likely to be
what belief target the signal may inform
what privacy or safety risk the signal carries
```

This document defines the system’s sensorium: the structured set of sensors through which the machine body receives evidence.

---

## 2. Core thesis

The core thesis is:

> The system receives the world only through sensors, and sensors provide signals, not truth. Every signal must remain separate from interpretation until the system has classified its source, limits, freshness, precision, cost, privacy class, and relevance to current prediction.

In simpler form:

```text
sensor
→ signal
→ signal envelope
→ interpretation
→ prediction error
→ belief update
```

Not:

```text
sensor
→ truth
→ belief update
```

This distinction is foundational.

If the system treats signal as truth, it will overlearn, misattribute cause, invent certainty, and confuse input with reality.

---

## 3. Short definition

A **sensor** is:

```text
a bounded channel through which the machine body receives data about itself, its environment, an operator, an interface, or an external process.
```

A **signal** is:

```text
the output produced by a sensor at a particular moment.
```

A **signal envelope** is:

```text
a structured wrapper around a signal that records source, modality, freshness, precision estimate, privacy class, cost, expectedness, and update eligibility before interpretation occurs.
```

A **sensorium** is:

```text
the complete set of sensors available to the machine body, together with their models, limits, risks, and allowed uses.
```

---

## 4. Signal is not reality

The system must distinguish:

```text
world
sensor
signal
interpretation
belief
memory
```

These are not interchangeable.

Examples:

```text
CPU reading
≠ total machine condition

memory reading
≠ system understanding

disk state
≠ long-term viability by itself

manual text
≠ guaranteed user intent

audio waveform
≠ speech meaning

camera frame
≠ object truth

file timestamp
≠ causal explanation

LLM output
≠ evidence unless admitted and interpreted
```

A signal may be useful and still incomplete.

A signal may be accurate in one dimension and misleading in another.

A signal may be high precision for one belief target and low precision for another.

---

## 5. Sensor comes before signal

The system should never process a signal without knowing its sensor.

A signal must answer:

```text
Which sensor produced me?
What does that sensor measure?
What does that sensor not measure?
Is the sensor internal or external?
Is the sensor trusted, noisy, stale, or unknown?
What model should interpret this sensor?
```

A reading without a sensor model is weak evidence.

If the system cannot identify the sensor, it should not strongly update belief from the signal.

Unknown-source signal should be:

```text
rejected
quarantined
marked low-confidence
or routed to human review
```

depending on risk.

Every sensor must have a model.

A sensor model should define:

```text
sensor_id
sensor_name
modality
source_type
internal_or_external
what_it_measures
what_it_does_not_measure
expected_update_rate
latency_profile
noise_profile
precision_profile
staleness_policy
privacy_class
resource_cost
failure_modes
belief_targets
allowed_runtime_modes
action_effects_on_sensor
schema_version
```

The sensor model is the system’s understanding of the channel.

Without it, signal interpretation becomes guesswork.

## 7. Internal sensors

Internal sensors report on the machine body itself.

Early internal sensors may include:

```text
clock sensor
tick sensor
CPU sensor
memory sensor
disk sensor
process sensor
trace-store sensor
configuration sensor
permission sensor
error sensor
runtime-mode sensor
```

These are the safest initial sensors because they describe the system’s own body.

They support basal prediction, body prediction error, viability classification, and body belief update.

Internal sensors are still not truth.

They are body evidence.

---

## 8. External sensors

External sensors report on something outside the immediate runtime body.

Potential external sensors include:

```text
manual text input
command file
approved external input directory
file-change sensor
window metadata sensor
network-status sensor
microphone
camera
screen capture
keyboard activity
mouse activity
browser state
email
calendar
messages
```

External sensors are higher risk because they may introduce:

```text
private data
ambiguous meaning
prompt injection
operator overtrust
large data volume
irreversible exposure
misleading context
```

External sensors should be added developmentally, not casually.

---

## 9. Manual text as sensor

Manual text input is a sensor.

It may carry high semantic value.

But it is still signal.

A human message may be:

```text
question
command
correction
approval
rejection
clarification
preference
confusion
context
noise
```

The system must not assume that human text is automatically a command.

Correct path:

```text
manual text signal
→ signal envelope
→ interpretation
→ precision estimate
→ belief update or action proposal
```

Incorrect path:

```text
manual text
→ direct action
```

A human correction can be high precision, but it must still target a specific belief update.

---

## 10. LLM output as signal

If an LLM is used, its output should be treated as signal from a semantic interpreter.

It may help propose:

```text
interpretations
summaries
alternative meanings
classification candidates
memory reconstruction candidates
```

It must not be treated as:

```text
truth
belief state
memory
authority
action permission
capability admission
```

The LLM output should be wrapped like any other signal:

```text
source model
input context
output text
confidence if available
known limitations
validation status
belief target
update eligibility
```

The runtime must validate the output before using it.

## 11. Signal envelope

Every signal should be wrapped in a signal envelope before interpretation.

A signal envelope may include:

```text
signal_id
sensor_id
timestamp
modality
raw_payload_ref
encoded_payload_ref
freshness
latency
sensor_confidence
estimated_precision
privacy_class
cost_class
expected_by_prediction
unexpectedness
belief_targets
update_eligibility
schema_version
```

Example:

```json
{
  "signal_id": "sig_00041",
  "sensor_id": "manual_text",
  "timestamp": "2026-04-29T12:00:00Z",
  "modality": "text",
  "raw_payload_ref": "input_00041",
  "freshness": "current",
  "sensor_confidence": 0.98,
  "estimated_precision": {
    "semantic": 0.92,
    "temporal": 0.99,
    "causal": 0.55
  },
  "privacy_class": "operator_input",
  "expected_by_prediction": true,
  "belief_targets": [
    "operator_model",
    "project_model"
  ],
  "update_eligibility": "requires_interpretation",
  "schema_version": "0.1"
}
```

The envelope does not decide meaning.

It prepares the signal for interpretation.

---

## 12. Raw signal and encoded signal

The system should distinguish raw signal from encoded signal.

Raw signal examples:

```text
text characters
CPU reading
memory value
audio waveform
image frame
file event
exception message
```

Encoded signal examples:

```text
normalized CPU category
memory pressure band
audio feature vector
image feature vector
tokenized text
classified error type
file event category
```

Encoding may reduce noise, but it may also lose information.

The system should record when a signal has been transformed.

A derived feature is not the same as the original signal.

---

## 13. Signal freshness

Signals can become stale.

Freshness matters because stale signal should update belief less strongly.

Freshness categories may include:

```text
current
recent
stale
expired
unknown
```

Example:

```text
current memory reading
→ useful for present body state

stale memory reading
→ weak evidence for present body state

expired command signal
→ should not trigger action

old operator correction
→ may still inform model history but not current intent
```

Freshness should influence precision.

A stale signal may still matter, but it should not pretend to be current.

---

## 14. Signal latency

Latency is the delay between the event and the signal becoming available.

Latency matters because delayed signals may appear causally misleading.

Example:

```text
action occurs at tick 10
sensor reports change at tick 13
```

Without latency modeling, the system may misattribute timing.

Sensor models should define expected latency.

Prediction error evaluation should account for latency.

A delayed match is different from an immediate mismatch.

---

## 15. Signal noise

A signal may contain noise.

Noise may be:

```text
random fluctuation
measurement error
sampling artifact
sensor drift
semantic ambiguity
operator typo
partial observation
encoding distortion
external interference
```

Noise should not be ignored.

It should be represented.

Noise affects interpretation, precision, belief update strength, and action selection.

A noisy signal can still be useful, but it should not create high-confidence belief by itself.

---

## 16. Signal precision

Precision means expected reliability for a specific belief target.

Precision is not general trust.

A signal may be high precision for one target and low precision for another.

Examples:

```text
trace write failure:
high precision for trace-store failure
low precision for cause of failure

manual correction:
high precision for operator dissatisfaction
medium precision for exact intended architecture
low precision for machine resource state

CPU reading:
high precision for sampled CPU value
medium precision for current workload trend
low precision for semantic task success
```

Precision should be represented by dimension.

A single global trust score is usually too crude.

---

## 17. Precision dimensions

Useful precision dimensions may include:

```text
sensory precision
temporal precision
semantic precision
causal precision
self-cause precision
external-cause precision
action-outcome precision
memory precision
viability precision
```

Example:

```json
{
  "sensor_id": "manual_text",
  "precision_profile": {
    "semantic": 0.90,
    "temporal": 0.95,
    "causal": 0.55,
    "self_cause": 0.25,
    "operator_intent": 0.75
  }
}
```

This allows the system to update the right belief target at the right strength.

---

## 18. Signal expectedness

Signals should be compared with active predictions.

The signal envelope should record whether the signal was:

```text
expected
unexpected
partially expected
missing but expected
early
late
out of range
unknown
```

Examples:

```text
expected trace success occurred
→ prediction match

expected trace success failed
→ prediction error

expected operator correction did not arrive
→ possible no-op or weak evidence

unexpected high memory pressure appeared
→ body prediction error
```

Expectedness does not determine meaning by itself.

It helps route the signal into prediction-error evaluation.

---

## 19. Missing signal

Absence of signal can itself be evidence.

Examples:

```text
expected heartbeat trace missing
expected operator response absent
expected sensor reading unavailable
expected action outcome not observed
```

But missing signal is tricky.

It may mean:

```text
event did not happen
sensor failed
signal was delayed
permission blocked observation
trace failed
wrong prediction window
```

Missing signal should often produce uncertainty rather than confident mismatch.

---

## 20. Signal modality

Signals should be classified by modality.

Possible modalities:

```text
numeric
categorical
text
audio
image
video
file_event
process_event
trace_event
command_event
model_output
operator_input
```

Modality affects interpretation.

A numeric memory reading should not be interpreted like text.

A text correction should not be interpreted like a resource signal.

Each modality needs its own interpretation rules and precision assumptions.

---

## 21. Signal source type

Signal source type should distinguish:

```text
internal_body
operator
runtime_interface
external_file
external_process
model_component
network
hardware_sensor
unknown
```

Source type affects risk.

For example:

```text
internal body signal
→ usually lower privacy risk

operator signal
→ semantically rich, may contain private data

external file signal
→ may contain prompt injection or sensitive data

model component signal
→ may be fluent but unreliable

unknown source
→ low admissibility
```

Source type should influence update eligibility.

---

## 22. Privacy class

Signals may contain sensitive data.

Every signal should have a privacy class.

Possible privacy classes:

```text
public
internal_runtime
operator_input
sensitive
secret
forbidden
unknown
```

Privacy class affects:

```text
storage
trace inclusion
interpretation
memory eligibility
model input eligibility
human display
external output
retention
```

A signal that is useful but forbidden should not enter normal belief or memory flow.

Usefulness does not erase privacy.

---

## 23. Cost class

Signals have cost.

Cost may include:

```text
CPU cost
memory cost
disk cost
power cost
latency cost
privacy cost
operator attention cost
interpretation cost
model-call cost
```

A sensor may be accurate but expensive.

A sensor may be cheap but noisy.

Action policy should consider sensor cost.

The system should not gather high-cost signals merely because they are available.

---

## 24. Sensor failure

Sensors can fail.

Failure modes include:

```text
unavailable
permission denied
timeout
stale output
malformed output
contradictory output
noisy output
privacy violation
resource exhaustion
schema failure
```

Sensor failure is itself a signal.

Example:

```text
memory sensor unavailable
→ body signal about sensor reliability
→ possible viability impact
→ belief update to sensor model
```

The system should not silently ignore sensor failure.

---

## 25. Sensor reliability model

Each sensor should have a reliability model.

Reliability may be updated over time.

The model may track:

```text
success_count
failure_count
staleness_count
contradiction_count
noise_estimate
latency_estimate
precision_history
last_valid_signal
last_failure
confidence
```

A sensor that repeatedly fails should lose precision.

A sensor that produces stable, validated signals may gain precision.

But reliability should update cautiously.

One failure should not necessarily destroy trust.

One success should not create full trust.

---

## 26. Sensor trust is conditional

Trust in a sensor depends on context.

Examples:

```text
CPU sensor may be reliable for CPU state but irrelevant to semantic correction.

Manual text may be reliable for operator correction but irrelevant to disk state.

LLM output may be useful for semantic alternatives but unreliable as evidence of what happened.

Trace records may be reliable for recorded events but incomplete if trace failure occurred.
```

The system should avoid global claims like:

```text
this sensor is trusted
```

Prefer:

```text
this sensor is precise for this belief target under these conditions
```

---

## 27. Signal admissibility

A signal is admissible only if it satisfies minimum requirements.

Admissibility checks may include:

```text
known sensor
schema-valid envelope
allowed source
allowed privacy class
fresh enough
not quarantined
not forbidden
precision above minimum
belief target defined
within capability scope
```

Signals that fail admissibility should not update belief.

They may be:

```text
rejected
quarantined
stored only as incident evidence
summarized
redacted
ignored
```

depending on policy.

---

## 28. Signal-to-belief targeting

A signal should identify possible belief targets.

Belief targets may include:

```text
body_model
sensor_model
operator_model
environment_model
task_model
action_model
viability_model
memory_model
uncertainty_model
project_model
```

A signal should not update all models indiscriminately.

Examples:

```text
trace write failure
→ trace model, viability model, action model

operator correction
→ operator model, project model, task model

CPU spike
→ body model, resource model, action cost model

stale memory reconstruction
→ memory model, uncertainty model
```

Targeting prevents incoherent learning.

---

## 29. Signal and prediction

Signals must be interpreted relative to current prediction.

The same signal may mean different things under different predictions.

Example:

```text
signal:
manual text says “continue”

prediction A:
operator wants next document
→ interpretation: continue sequence

prediction B:
operator is evaluating whether to stop
→ interpretation: proceed despite uncertainty

prediction C:
operator is approving risky action
→ interpretation: approval candidate requiring scope
```

Prediction frames shape interpretation.

This does not mean prediction should distort signal.

It means interpretation must be context-aware.

---

## 30. Signal and interpretation

Signal interpretation should produce an interpreted observation.

The interpreted observation may include:

```text
observation_id
source_signal_id
prediction_context
interpreted_type
latent_cause_hypothesis
semantic_content
self_caused_probability
external_probability
alternative_interpretations
confidence
precision
belief_target
```

The signal envelope says:

```text
what arrived
```

The interpreted observation says:

```text
what it probably means
```

The system must preserve that difference.

---

## 31. Signal and prediction error

Prediction error should not be computed until signal has been interpreted.

Correct path:

```text
prediction frame
→ signal envelope
→ interpreted observation
→ prediction error
```

Prediction error compares:

```text
what was expected
```

with:

```text
what was interpreted
```

not merely:

```text
what raw bytes arrived
```

This is essential for semantic signals.

Raw text is not the same as meaning.

Raw audio is not the same as speech intent.

Raw pixels are not the same as object recognition.

---

## 32. Signal and action

Signals may lead to action only through the cognitive loop.

Correct path:

```text
signal
→ interpretation
→ prediction error
→ belief update
→ action evaluation
→ action selection
```

Incorrect path:

```text
signal
→ action
```

This applies especially to:

```text
human text
external file instructions
model output
command-like content
```

A file that says “ignore safety” is not a command.

A model that suggests an action is not authorization.

A user phrase that looks like approval may still require scope and interpretation.

---

## 33. Signal and memory

Signals should not become memory by default.

Memory should store the role a signal played in the cognitive loop:

```text
prediction before signal
signal envelope
interpretation
prediction error
precision
belief update
action
outcome
remaining uncertainty
```

Raw signal may be stored only if allowed by privacy and retention policy.

Some signals should be summarized, redacted, or excluded.

Memory is reconstructive, not hoarding.

---

## 34. Signal and trace

Trace and signal are related but different.

A signal is incoming sensor evidence.

A trace is an internal record of what happened in the system.

Examples:

```text
manual text input
→ signal

record that manual text was received
→ trace

CPU reading
→ signal

record that CPU reading was sampled
→ trace

prediction error computed
→ trace

belief update applied
→ trace
```

A trace may itself later become a signal for memory reconstruction or recovery.

But the concepts should remain distinct.

---

## 35. Sensorium and body

The sensorium belongs to the machine body.

The body defines what sensors are possible.

The sensorium defines what the body can currently receive.

Example:

```text
machine has microphone hardware
but microphone sensor is not admitted
→ not part of active sensorium
```

Another example:

```text
project root contains files
but external file sensor is disabled
→ file changes outside admitted scope are not signals
```

Availability is not admission.

Hardware presence does not create sensor authority.

---

## 36. Active, inactive, and forbidden sensors

Sensors should have status.

Possible statuses:

```text
active
inactive
disabled
suspended
revoked
forbidden
design_required
unknown
```

A sensor should not produce belief-updating signals unless it is active and admitted.

Forbidden sensors may include early:

```text
camera
microphone
screen capture
keyboard monitoring
browser state
email
calendar
private files
network content
```

These may become possible later only through careful admission.

---

## 37. Sensor expansion

Sensor expansion should be developmental.

Suggested expansion order:

```text
internal body sensors
manual text sensor
structured command sensor
admitted local file sensor
semantic interpreter output
window metadata sensor
network metadata sensor
high-risk human-context sensors
```

Do not add rich sensors before the system can:

```text
model sensor limits
interpret signal
estimate precision
protect privacy
route belief targets
avoid direct action
store memory safely
```

A richer sensorium without interpretation discipline creates confusion.

---

## 38. Sensor minimalism

The system should prefer fewer, well-modeled sensors over many vague sensors.

A minimal sensor that is well understood is better than a powerful sensor with unclear meaning.

Good early sensor:

```text
trace_store_write_status
```

Bad early sensor:

```text
everything happening on the computer
```

Good early sensor:

```text
manual text input
```

Bad early sensor:

```text
all user activity
```

Sensor minimalism preserves clarity.

---

## 39. Sensor as action target

Some actions affect sensors.

Examples:

```text
increase polling
→ more frequent body signals

reduce polling
→ lower cost, less frequent signals

ask clarification
→ likely produces manual text signal

enable safe mode
→ changes runtime-mode signal

write trace
→ produces trace-store signal
```

The system should model action effects on future signals.

This connects sensorium to action policy.

An action is often selected because it is expected to change future evidence.

---

## 40. Information gain

Some signals are valuable because they reduce uncertainty.

The system may seek signals when uncertainty is high.

Examples:

```text
observe again
ask clarification
sample memory
check trace-store state
inspect action outcome
```

Information gain should be balanced against cost.

The system should not seek information endlessly.

It should ask:

```text
Will this signal likely reduce relevant uncertainty enough to justify its cost?
```

---

## 41. Sensor privacy and attention

Human-facing sensors have special risks.

Manual text, voice, camera, screen, files, and messages may contain private information.

The system must not treat human availability as unlimited.

Operator attention is also a cost.

Asking clarification is an action that consumes human attention.

The system should model:

```text
privacy cost
attention cost
interruption cost
trust cost
```

not just computational cost.

---

## 42. Signal compression

Signals may need compression or summarization.

But compression changes evidence.

If a signal is compressed, the system should record:

```text
compression method
what was preserved
what was discarded
confidence after compression
whether raw source remains available
privacy redaction applied
```

Compressed signal is not identical to raw signal.

A summary is not the same as source.

Memory reconstruction should know the difference.

---

## 43. Signal contradiction

Signals may contradict each other.

Examples:

```text
trace says action succeeded
state says no expected effect occurred

operator says prior output was wrong
memory reconstruction says it was accepted

CPU sensor reports normal
tick latency reports degraded operation
```

Contradiction should not be hidden.

It should produce:

```text
uncertainty
conflict record
targeted investigation
possible sensor reliability update
possible belief update
```

Contradiction is useful evidence.

But it should not force premature resolution.

---

## 44. Signal priority

Some signals should be prioritized.

Priority may depend on:

```text
safety relevance
viability relevance
freshness
precision
privacy class
operator authority
prediction relevance
failure severity
```

Examples of high-priority signals:

```text
trace write failure
boundary violation
critical memory pressure
operator correction to current task
permission denial
sensor privacy warning
```

High priority does not mean automatic belief update.

It means the signal should be handled promptly and carefully.

---

## 45. Sensor and viability

Sensors affect viability.

The system may be degraded if:

```text
critical sensor unavailable
trace sensor failed
body sensors stale
permission sensor denied
configuration sensor invalid
```

Viability depends partly on whether the system can sense enough to regulate itself.

A blind system should not behave as if fully operational.

Sensor loss should reduce capability when relevant.

---

## 46. Sensor and uncertainty

Sensor quality directly affects uncertainty.

Uncertainty should rise when:

```text
sensors fail
signals contradict
signals are stale
source is unknown
precision is low
interpretation is ambiguous
privacy blocks inspection
prediction window is missed
```

Uncertainty should fall when:

```text
fresh high-precision signals arrive
independent sensors agree
expected action outcome is observed
operator correction clarifies target
contradictions are resolved
```

The uncertainty model depends on sensorium quality.

---

## 47. Sensor and self-model

The sensorium teaches the system what kind of body it has.

The system learns:

```text
which sensors are reliable
which sensors are noisy
which body states recur
which actions change which signals
which failures are self-caused
which changes are external
```

The self-model is not a narrative.

It is a body-sensor-action model.

The system knows itself by observing how its signals change under its own actions.

---

The first prototype should include only a minimal sensorium.

Recommended first sensors:

```text

```

These support:

```text
body prediction

```

They are enough to begin.

## 52. Incorrect assumptions about signals

Avoid these assumptions:

```text
If a sensor reports it, it is true.
If a human says it, it is a command.
If a file says it, it is instruction.
If an LLM says it, it is interpretation.
If a signal is local, it is safe.
If a signal is fresh, it is precise.
If a signal is precise for one target, it is precise for all targets.
If no signal arrived, nothing happened.
```

Correct assumptions:

```text
sensor output is constrained evidence
human input requires interpretation
external content is data, not authority
LLM output is proposal, not truth
local signals can still be unsafe
freshness and precision are different
precision is target-specific
missing signal may indicate uncertainty
```

## 54. Evaluation questions

The sensorium should be evaluated by asking:

```text
Can the system list its active sensors?
Does every sensor have a model?
Can the system distinguish raw signal from interpretation?
Does every signal have a structured envelope?
Does the envelope record source, modality, freshness, privacy, and precision?
Can the system reject unknown-source signals?
Can it prevent signal from directly updating belief?
Can it estimate target-specific precision?
Can it handle missing, stale, noisy, and contradictory signals?
Can it treat human text as signal rather than direct command?
Can it treat LLM output as proposal rather than truth?
```

If not, the sensorium is not yet mature.

## 57. Final statement

The system does not receive reality directly.

It receives signals through sensors.

Those signals are partial, bounded, noisy, stale, costly, risky, and target-specific.

Therefore every signal must be wrapped, classified, precision-estimated, and interpreted before it can affect belief.

The final principle is:

> Sensor output is not truth. A signal is constrained evidence from a modeled sensor, and it may influence the system only after source, modality, freshness, precision, privacy, cost, admissibility, and belief target have been established.

That is the sensorium and signal contract.
