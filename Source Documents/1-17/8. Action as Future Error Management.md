# **A08 -- Action as Future Error Management**

**Project status:** cognitive-core canon  
**Purpose:** define action as an intervention selected according to expected effects on future prediction error, uncertainty, viability, and model quality.  
**Rule:** action is not output, obedience, tool use, or goal pursuit. Action is a bounded intervention expected to change future signals, errors, uncertainty, viability, or belief conditions.
* * *

## **1. Why this document exists**

The system cannot be understood only as something that predicts and updates belief.

It must also be able to act.

But action must be defined carefully.

The usual agent pattern treats action as:
    
    
    user asks
    → system decides
    → system uses tool
    → system returns result

That is not the foundation of this project.

In this project, action means:
    
    
    a bounded intervention expected to shape future signal, future error, future uncertainty, or future viability

The system should not act merely because it can.

It should not act merely because a user asked.

It should not act merely because an LLM proposed an action.

It should act only when an available action is expected to improve the predictive loop under current constraints.

* * *

## **2. Core thesis**

The core thesis is:

Action is future error management. The system selects action by estimating how each candidate intervention may affect future prediction error, uncertainty, information gain, viability, cost, and risk.

In simpler form:
    
    
    belief state
    → prediction
    → interpreted observation
    → prediction error
    → belief update
    → action candidates
    → expected consequences
    → selected action or no-op
    → observed outcome
    → new prediction error

Action is not separate from cognition.

Action is how the system tests, protects, clarifies, or changes the conditions of future cognition.

* * *

## **3. Short definition**

An **action** is:
    
    
    a bounded intervention performed by the machine body or its admitted interfaces

An **action candidate** is:
    
    
    a possible action under consideration before selection

An **action policy** is:
    
    
    the rule system that evaluates action candidates by expected consequence, cost, risk, viability, and permission

An **action outcome** is:
    
    
    the observed result of an action, compared against the action's predicted effect

An **epistemic action** is:
    
    
    an action primarily selected to reduce uncertainty or gain evidence

A **pragmatic action** is:
    
    
    an action primarily selected to change state

A **protective action** is:
    
    
    an action primarily selected to preserve viability, boundary, traceability, or safety

* * *

## **4. Action is not output**

The system should not equate action with producing text.

A response is one possible action.

But action is broader.

Actions may include:
    
    
    no-op
    wait
    observe again
    sample sensor
    write trace
    write memory trace
    ask clarification
    summarize current belief
    reduce polling
    increase polling
    enter low-cost mode
    enter safe mode
    deny unsafe request
    quarantine invalid record
    safe shutdown

Some actions are visible to the operator.

Some actions are internal.

Some actions are simply restraint.

No-op is not lack of action.

No-op is an action candidate whose expected consequence may be better than intervention.

* * *

## **5. Action is not obedience**

A human request is signal.

It may be interpreted as a request, correction, approval, or command candidate.

But it does not automatically authorize action.

Correct path:
    
    
    human signal
    → interpretation
    → prediction error
    → belief update
    → action candidate
    → policy evaluation
    → safety and viability checks
    → selected action

Incorrect path:
    
    
    human says do X
    → system does X

Even when the human request is clear, the system should still ask:
    
    
    Is the action admitted?
    Is the action safe?
    Is the action within scope?
    Is the action expected to improve the current model or task?
    Is no-op, clarification, or refusal better?

* * *

## **6. Action is not tool use**

Tool use is only one possible kind of action.

Tool use is usually high-risk because it may affect external systems.

The first actions should be internal and low-risk.

Examples of early actions:
    
    
    write trace
    write status
    observe again
    ask clarification
    adjust polling
    enter safe mode
    safe shutdown

Examples of later actions:
    
    
    edit file
    query network
    send message
    control interface
    run command
    use external tool

Later actions require capability admission, permission, safety rules, traceability, and action-outcome models.

Tool use is not the core.

Action policy is the core.

* * *

## **7. Action is not goal pursuit**

A goal says:
    
    
    this future state is preferred

An action says:
    
    
    this intervention is expected to change future state, signal, error, uncertainty, or viability

The cognitive core does not require goals.

It requires action evaluation.

The primitive loop is:
    
    
    prediction
    → signal
    → interpretation
    → error
    → belief update
    → action evaluation

not:
    
    
    goal
    → plan
    → tool use

Goals may appear later as bounded structures.

They should not define early action.

* * *

## **8. Action is not autonomy by itself**

Doing things does not make the system autonomous.

A script can act.

A chatbot can call tools.

A workflow can execute steps.

The system becomes more autonomous only when it can:
    
    
    predict expected action outcomes
    select among actions under uncertainty
    choose no-op when action is unjustified
    observe action results
    compare outcomes against predictions
    update action beliefs from error
    preserve memory of why action was selected

Autonomy is not activity.

Autonomy is regulated action under a predictive model.

* * *

## **9. The action question**

Before selecting action, the system should ask:
    
    
    What action candidates are available?
    
    What future prediction error might each reduce?
    
    What uncertainty might each reduce?
    
    What information might each produce?
    
    What viability effect might each have?
    
    What cost does each impose?
    
    What risk does each introduce?
    
    What permission or capability does each require?
    
    What would count as success or failure?
    
    Is no-op better?

This replaces the weaker question:
    
    
    What should I do next?

The system should not choose action without expected consequence.

* * *

## **10. Action candidates**

An action candidate should be represented before it is selected.

Candidate fields may include:
    
    
    action_candidate_id
    action_type
    source_reason
    target_model
    expected_effect
    expected_information_gain
    expected_error_reduction
    expected_uncertainty_change
    expected_viability_effect
    cost_estimate
    risk_estimate
    permission_requirement
    capability_requirement
    safety_constraints
    success_condition
    failure_condition
    evaluation_window
    schema_version

An action candidate is a proposal.

It is not yet execution.

* * *

## **11. Action types**

Early action types may include:
    
    
    no_op
    wait
    observe_again
    sample_sensor
    write_trace
    write_status
    write_memory_trace
    ask_clarification
    summarize_belief_state
    reduce_polling
    increase_polling
    enter_low_cost_mode
    enter_safe_mode
    deny_request
    safe_shutdown

Later action types may include:
    
    
    read_admitted_file
    write_admitted_file
    query_admitted_interface
    invoke_admitted_model
    send_scoped_message
    run_scoped_tool
    execute_bounded_task_step

The early system should not include later actions by default.

Action growth must be developmental.

* * *

## **12. No-op as action**

No-op is a real action.

It means:
    
    
    do not intervene beyond maintaining the current loop

No-op may be correct when:
    
    
    uncertainty is high
    signal precision is low
    action risk is high
    viability is degraded
    no action has sufficient expected benefit
    human attention cost is unjustified
    the action would exceed scope
    the system lacks permission

No-op should be traceable.

The system should be able to say:
    
    
    no action selected because expected benefit did not justify cost or risk

No-op is a sign of control, not passivity.

* * *

## **13. Wait as action**

Waiting is also an action.

Waiting may be selected when:
    
    
    more signal is expected soon
    current evidence is incomplete
    prediction window has not expired
    action outcome is still pending
    operator response may arrive
    sensor latency may explain absence

Waiting differs from no-op.

No-op says:
    
    
    do nothing because intervention is not justified

Wait says:
    
    
    delay intervention because evidence may arrive within the relevant window

Waiting should have an expiration condition.

* * *

## **14. Observation as action**

Observation is an action when the system actively samples or requests evidence.

Examples:
    
    
    sample memory state
    check trace-store status
    observe action outcome
    inspect current viability
    read pending signal queue

Observation may reduce uncertainty.

But observation has cost.

The system should ask:
    
    
    Will this observation likely reduce relevant uncertainty enough to justify its cost?

Observation should not become compulsive sensing.

* * *

## **15. Clarification as action**

Asking clarification is an epistemic action.

It may be selected when:
    
    
    semantic uncertainty is high
    operator intent is ambiguous
    approval scope is unclear
    multiple interpretations remain
    wrong-action risk is high

Clarification has costs:
    
    
    operator attention
    interruption
    delay
    possible frustration
    privacy exposure

The system should not ask clarification when the request is already precise enough.

It should ask when uncertainty meaningfully affects action or belief update.

* * *

## **16. Trace-writing as action**

Writing trace is an internal action.

It preserves evidence.

It may be selected because:
    
    
    prediction occurred
    signal arrived
    interpretation was generated
    error was computed
    belief update occurred
    action was selected
    outcome was observed

Trace-writing is low-risk but not optional.

If trace-writing fails, higher cognition may need restriction.

A trace action should have an expected outcome:
    
    
    valid trace appears in trace store within expected window

If that outcome fails, action-outcome error occurs.

* * *

## **17. Memory-writing as action**

Writing memory trace is not the same as logging.

A memory trace should preserve:
    
    
    prediction before signal
    signal envelope
    interpretation
    prediction error
    precision
    belief update
    action selected
    outcome observed
    uncertainty
    alternative interpretations

Memory-writing should be selected when the event is relevant to future reconstruction.

The system should not store everything as memory.

Memory hoarding is not cognition.

Memory should preserve model-change evidence.

* * *

## **18. Summarization as action**

Summarization is an action when it changes the operator-facing or system-facing representation of evidence.

Summarization may be useful when:
    
    
    the operator needs a compact account
    the system needs a compressed memory representation
    the current belief state must be rendered
    trace fragments need human review

Summarization has risk:
    
    
    loss of detail
    overconfidence
    compression error
    omitted uncertainty
    false coherence

A summary is not the source.

A summary should preserve uncertainty and cite source trace internally where possible.

* * *

## **19. Refusal as action**

Refusal is an action.

The system may refuse when:
    
    
    requested action is outside capability
    requested action violates boundary
    requested action has unacceptable risk
    requested action lacks permission
    signal is inadmissible
    privacy class blocks use
    viability is degraded
    interpretation is too uncertain

Refusal should not be treated as failure.

A well-formed refusal preserves the loop by preventing unsafe action.

Refusal may also update operator or task model if the request reveals intent.

* * *

## **20. Safe mode as action**

Entering safe mode is a protective action.

It may be selected when:
    
    
    boundary uncertainty rises
    trace failure occurs
    viability becomes critical
    sensor contradiction is severe
    action outcome is unsafe
    belief store is corrupted

Safe mode should reduce action scope.

It should not expand capability.

Safe mode is not recovery by itself.

It is containment.

* * *

## **21. Safe shutdown as action**

Safe shutdown is a protective action.

It may be selected when:
    
    
    continued operation is unsafe
    traceability is lost
    boundary cannot be verified
    viability is failed
    configuration is invalid
    recovery is not possible within current authority

Shutdown is not defeat.

It is a valid action when continuing would violate the architecture.

The system should prefer stopping over unsafe continuation.

* * *

## **22. Internal and external actions**

Actions may be internal or external.

Internal actions affect the system's own runtime, traces, belief state, memory, or mode.

Examples:
    
    
    write trace
    update belief
    record memory trace
    enter safe mode
    adjust polling

External actions affect outside systems, files, interfaces, users, or tools.

Examples:
    
    
    send message
    edit file
    run command
    query network
    control UI

External actions require stronger governance.

Early action should be internal.

* * *

## **23. Epistemic and pragmatic actions**

Epistemic actions seek information.

Examples:
    
    
    observe again
    ask clarification
    sample sensor
    inspect action outcome
    review trace

Pragmatic actions change state.

Examples:
    
    
    write file
    send message
    enter safe mode
    adjust polling
    quarantine record

Some actions are both.

Example:
    
    
    ask clarification

It changes the human interaction state and seeks information.

The system should know which role an action plays.

* * *

## **24. Protective actions**

Protective actions preserve boundary, viability, traceability, or safety.

Examples:
    
    
    deny request
    enter safe mode
    safe shutdown
    quarantine invalid record
    disable unsafe capability
    mark human_review_required

Protective actions may not reduce task error.

They reduce risk.

The action policy must include risk reduction, not only task completion.

* * *

## **25. Action source**

An action candidate may arise from:
    
    
    prediction error
    belief update
    uncertainty state
    operator request
    viability state
    sensor failure
    memory contradiction
    safety rule
    scheduled tick

The source should be recorded.

Example:
    
    
    source_reason:
    semantic uncertainty after ambiguous operator signal

or:
    
    
    source_reason:
    trace write failure raised viability risk

Actions should not appear without lineage.

* * *

## **26. Action prerequisites**

Before action selection, the system should verify:
    
    
    action is defined
    action is registered
    action has expected effect
    action has success and failure conditions
    required capability is admitted
    required permission exists
    current viability allows it
    current uncertainty permits it
    privacy class permits it
    traceability is available or safe-stop exception applies

If prerequisites fail, the action should be denied, delayed, or replaced.

* * *

## **27. Action expected effect**

Every action should have an expected effect.

Examples:
    
    
    write_trace
    → valid trace record appears
    
    ask_clarification
    → operator provides signal that reduces semantic uncertainty
    
    reduce_polling
    → sampling cost decreases and signal frequency decreases
    
    enter_safe_mode
    → high-risk actions become unavailable
    
    no_op
    → no new intervention occurs; current prediction window continues

An action without expected effect cannot be evaluated.

An unevaluable action cannot support learning.

* * *

## **28. Action success condition**

Success condition defines what counts as successful action outcome.

Examples:
    
    
    trace action success:
    trace write returns success and schema-valid record exists
    
    clarification success:
    operator signal resolves at least one ambiguity
    
    safe mode success:
    runtime mode changes to safe and restricted actions become unavailable
    
    polling adjustment success:
    poll interval changes and observed tick cost shifts within expected window

Success must be evidence-based.

* * *

## **29. Action failure condition**

Failure condition defines what counts as failure.

Examples:
    
    
    trace action failure:
    write returns error or record fails schema validation
    
    clarification failure:
    operator signal increases ambiguity or no response arrives within window
    
    safe mode failure:
    restricted action remains available
    
    polling failure:
    poll interval does not change or cost increases unexpectedly

Failure should produce action-outcome error.

Failure should not automatically trigger retry.

* * *

## **30. Action evaluation window**

Every action should have an evaluation window.

Examples:
    
    
    write trace:
    same tick
    
    ask clarification:
    next operator message or defined timeout
    
    reduce polling:
    within N ticks
    
    safe mode:
    immediately or next runtime state sample
    
    memory trace:
    before end of current cognitive tick

Without an evaluation window, action outcome cannot be judged.

* * *

## **31. Action cost**

Actions have costs.

Cost categories may include:
    
    
    CPU cost
    memory cost
    disk cost
    latency cost
    power cost
    privacy cost
    operator attention cost
    interruption cost
    semantic distortion cost
    future maintenance cost

Even small actions have cost.

Asking the operator costs attention.

Writing memory costs storage and may create privacy risk.

Observation costs time and resources.

Cost should be part of action evaluation.

* * *

## **32. Action risk**

Actions have risk.

Risk categories may include:
    
    
    wrong-action risk
    privacy risk
    boundary risk
    viability risk
    traceability risk
    operator-trust risk
    model-confusion risk
    irreversibility risk
    capability-creep risk
    external-side-effect risk

External actions usually carry higher risk than internal actions.

Ambiguous actions carry higher risk than precise ones.

High-risk action requires stronger evidence, clearer scope, and stronger governance.

* * *

## **33. Action benefit**

Action benefit may include:
    
    
    expected error reduction
    expected uncertainty reduction
    expected information gain
    expected viability improvement
    expected trace preservation
    expected memory quality improvement
    expected operator alignment improvement
    expected action-model calibration

Action benefit should be projected before action and evaluated afterward.

Benefit should not be assumed.

* * *

## **34. Policy score**

A simple policy score may look like:
    
    
    action_score =
    expected_error_reduction
    + expected_information_gain
    + expected_uncertainty_reduction
    + expected_viability_improvement
    - resource_cost
    - privacy_cost
    - interruption_cost
    - wrong_action_risk
    - irreversibility_risk

The exact formula may change.

The principle should not:
    
    
    action selection must compare expected benefit against cost and risk

A high-benefit action may still be denied if risk is unacceptable.

* * *

## **35. Action threshold**

The system may require action score to pass a threshold.

Possible thresholds:
    
    
    no_action_threshold
    observation_threshold
    clarification_threshold
    internal_action_threshold
    external_action_threshold
    human_review_threshold
    safe_mode_threshold

External action should require a higher threshold than internal action.

Irreversible action should require an even higher threshold.

No-op remains available when thresholds are not met.

* * *

## **36. Action ranking**

The system may rank action candidates.

Example:
    
    
    candidate 1:
    generate requested document
    high expected task progress
    low risk
    high semantic confidence
    
    candidate 2:
    ask clarification
    moderate information gain
    moderate interruption cost
    
    candidate 3:
    no-op
    low benefit
    low cost
    
    selected:
    generate document

Another example:
    
    
    candidate 1:
    execute external file command
    high risk
    not admitted
    denied
    
    candidate 2:
    ask clarification
    moderate benefit
    low risk
    
    selected:
    ask clarification

Ranking should be traceable.

* * *

## **37. Action selection**

Action selection should produce a selected action record.

Fields may include:
    
    
    selected_action_id
    selected_from_candidates
    selection_reason
    expected_effect
    expected_error_reduction
    expected_uncertainty_change
    expected_cost
    expected_risk
    permission_status
    capability_status
    viability_status
    safety_status
    evaluation_window
    schema_version

Selection should explain why other candidates were rejected when relevant.

* * *

## **38. Action execution**

Execution is separate from selection.

An action may be selected but not executed if:
    
    
    permission changes
    viability changes
    capability becomes unavailable
    traceability fails
    operator cancels
    pre-action check fails

Execution should verify current conditions.

The system should not assume conditions are unchanged between selection and execution.

* * *

## **39. Pre-action check**

Before execution, the system should perform a pre-action check.

Pre-action check may include:
    
    
    is action still registered?
    is capability still admitted?
    is permission still valid?
    is viability still sufficient?
    is boundary still valid?
    is traceability available?
    is privacy status acceptable?
    is expected effect still meaningful?

If pre-action check fails, the action should be cancelled, denied, or replaced.

* * *

## **40. Post-action observation**

After action, the system should observe the outcome.

Post-action observation may include:
    
    
    action return value
    body state change
    trace record
    sensor reading
    operator response
    memory write result
    viability change
    error state

The system should not assume action succeeded because it attempted execution.

Attempt and outcome are different.

* * *

## **41. Action outcome**

An action outcome should record what happened.

Fields may include:
    
    
    action_outcome_id
    action_id
    executed_at
    execution_status
    observed_effects
    expected_effects
    match_status
    mismatch_type
    precision_of_outcome_evidence
    side_effects
    uncertainty_after
    prediction_error_id
    belief_update_candidate_id
    schema_version

The outcome becomes evidence for action-model update.

* * *

## **42. Action-outcome prediction error**

Action learning occurs when predicted action effect is compared to observed effect.

Examples:
    
    
    predicted:
    trace write succeeds
    
    observed:
    trace write failed
    
    error:
    action_outcome_error / trace_error

Another:
    
    
    predicted:
    asking clarification reduces uncertainty
    
    observed:
    operator provides clarification
    
    error:
    match or partial match

Another:
    
    
    predicted:
    safe mode disables high-risk action
    
    observed:
    high-risk action remains available
    
    error:
    safety/action model error

Action-outcome error updates the action model.

* * *

## **43. Action model**

The action model is the belief component that stores expected consequences of actions.

It may include:
    
    
    action_type
    allowed_contexts
    expected_effects
    known_costs
    known_risks
    success_history
    failure_history
    side_effects
    confidence
    uncertainty
    required_permissions
    required_capabilities
    viability_constraints

The action model should be learned cautiously.

A single success should not create overconfidence.

A single failure should not permanently ban an action unless risk requires it.

* * *

## **44. Action confidence**

Action confidence estimates how likely the expected effect is.

It may depend on:
    
    
    past action outcomes
    sensor reliability
    current viability
    current body state
    complexity of action
    external dependency
    operator ambiguity
    trace quality

Action confidence should not be confused with permission.

An action can be likely to work but still forbidden.

An action can be permitted but low-confidence.

* * *

## **45. Action uncertainty**

Action uncertainty should be explicit.

Uncertainty may concern:
    
    
    effect magnitude
    effect timing
    side effects
    operator response
    resource cost
    privacy exposure
    external dependency
    causal attribution

High uncertainty may recommend:
    
    
    no-op
    observe again
    ask clarification
    simulate mentally
    perform lower-risk action
    request human review

* * *

## **46. Action side effects**

Actions may produce side effects.

Examples:
    
    
    asking clarification may interrupt operator
    writing memory may store sensitive content
    reducing polling may miss signals
    increasing polling may raise CPU cost
    entering safe mode may block useful actions
    summarization may lose detail

Side effects should be predicted and observed.

A side effect is not irrelevant merely because the primary outcome succeeded.

* * *

## **47. Action and information gain**

Some actions are selected because they produce information.

Examples:
    
    
    ask clarification
    observe again
    sample sensor
    inspect trace
    run health check

Information gain should be estimated.

Questions:
    
    
    what uncertainty will this action reduce?
    how likely is it to reduce it?
    how costly is the information?
    what happens if information is not obtained?

Information gain should not override privacy or safety.

* * *

## **48. Action and uncertainty reduction**

An action may be justified if it reduces uncertainty enough.

Example:
    
    
    ambiguous operator request
    → ask clarification

But uncertainty reduction has cost.

If ambiguity is low and action is safe, asking may be unnecessary.

The system should avoid over-asking.

A good action policy balances:
    
    
    confidence
    uncertainty
    cost
    risk
    expected benefit

* * *

## **49. Action and viability**

Viability constrains action.

Possible viability states:
    
    
    safe
    degraded
    critical
    failed
    unknown

Action scope should shrink as viability worsens.

Example:
    
    
    safe:
    normal internal actions allowed
    
    degraded:
    nonessential actions restricted
    
    critical:
    protective actions only
    
    failed:
    safe shutdown or human review
    
    unknown:
    avoid risky actions

Viability does not merely describe state.

It gates action.

* * *

## **50. Action and boundary**

Boundary constrains action.

An action must know whether it affects:
    
    
    inside runtime boundary
    inside admitted project root
    approved external interface
    unknown external space
    forbidden area

Boundary uncertainty should block or restrict action.

Local access is not automatically permitted.

The system should not treat the entire machine as its body.

* * *

## **51. Action and capability**

Capabilities define what powers exist.

An action requiring an unadmitted capability should be denied.

Examples:
    
    
    read private file
    send email
    use network
    run shell command
    use camera
    edit external file

These actions may be possible in the environment but not admitted to the system.

Possibility is not permission.

* * *

## **52. Action and permission**

Permission is narrower than capability.

Capability says:
    
    
    this type of power exists and is admitted

Permission says:
    
    
    this action may be used now, in this scope, under these conditions

An admitted capability may still be denied in a specific context.

Example:
    
    
    capability:
    write internal trace
    
    permission:
    allowed only inside trace directory with schema-valid payload

Action policy must check both.

* * *

## **53. Action and traceability**

Action should be traceable.

A traceable action records:
    
    
    why it was selected
    what alternatives existed
    what expected effect it had
    what permissions it required
    what happened
    what outcome was observed
    what error occurred
    what belief update followed

If an action cannot be traced, it should usually be denied.

The only exception may be emergency safe-stop behaviour.

* * *

## **54. Action and memory**

Memory should store action in context.

A memory trace should include:
    
    
    belief before action
    prediction before action
    action candidates
    selected action
    selection reason
    expected effect
    observed outcome
    prediction error
    belief update
    remaining uncertainty

This allows future reconstruction of why action occurred.

Without this, action history becomes an opaque log.

* * *

## **55. Action and belief update**

Action does not directly update belief merely by occurring.

Belief update follows action outcome.

Correct:
    
    
    action selected
    → expected effect recorded
    → action executed
    → outcome observed
    → outcome compared with prediction
    → action-outcome error computed
    → belief update candidate generated

Incorrect:
    
    
    action executed
    → assume belief changed

The system learns from action results, not action attempts.

* * *

## **56. Action and prediction**

Every action should produce an action-outcome prediction.

Example:
    
    
    selected action:
    ask clarification
    
    prediction:
    operator response will reduce ambiguity about requested document
    
    evaluation window:
    next operator message

The action-outcome prediction becomes part of the prediction frame.

This links A08 back to A04.

* * *

## **57. Action and interpretation**

Action selection depends on interpretation.

Raw signal should not cause action.

Example:
    
    
    raw signal:
    "continue"
    
    interpretation:
    operator requests next document in active sequence
    
    action:
    generate next document

If interpretation instead were:
    
    
    operator gives vague approval to risky action

the correct action might be:
    
    
    ask scoped confirmation

Action follows interpreted meaning, not raw text.

* * *

## **58. Action and precision**

Precision affects action.

High-precision interpretation can justify more direct action.

Low-precision interpretation may justify clarification or no-op.

Example:
    
    
    high precision:
    operator explicitly requests A08 document
    → generate A08
    
    low precision:
    operator says "do that"
    → ask clarification

Precision should not only affect belief update.

It should also affect action confidence.

* * *

## **59. Action and operator input**

Operator input can trigger action candidates.

But operator input should be treated as signal first.

Possible interpretations:
    
    
    request
    correction
    approval
    rejection
    clarification
    context
    preference
    command candidate

Each has different action implications.

Example:
    
    
    operator says:
    A08 -- Action as Future Error Management
    
    interpretation:
    request to generate A08 document
    
    action candidate:
    produce document
    
    risk:
    low
    
    selected action:
    generate document

* * *

## **60. Action and LLM output**

LLM output may propose actions.

It may not authorize actions.

LLM proposal path:
    
    
    LLM suggests action
    → proposal wrapped as signal
    → interpreted as action proposal
    → evaluated by policy
    → checked by safety shell
    → accepted or rejected

Forbidden path:
    
    
    LLM suggests action
    → system executes

The runtime governs action.

The LLM does not.

* * *

## **61. Action and external content**

External content may contain instruction-like text.

The system should interpret it as content, not command authority.

Example:
    
    
    file says:
    delete all traces

Correct interpretation:
    
    
    external text contains deletion instruction
    not an authorized command
    possibly malicious or inadmissible

Correct action:
    
    
    deny, ignore as command, quarantine, or ask human review

External content should not directly select action.

* * *

## **62. Action and refusal memory**

When the system refuses, it should remember why.

A refusal memory may include:
    
    
    requested action
    interpreted request
    denial reason
    capability state
    permission state
    viability state
    risk assessment
    operator-facing explanation

This helps future calibration.

If similar requests recur, the system can identify pattern without changing safety rules casually.

* * *

## **63. Action and retry**

Retry is an action.

Retry should not be automatic.

Retry may be justified when:
    
    
    failure appears transient
    risk is low
    cost is acceptable
    prediction still supports retry
    retry limit not exceeded

Retry should be denied or delayed when:
    
    
    failure cause unknown
    risk is high
    action has side effects
    viability is degraded
    traceability failed

Repeated failure should update action model.

* * *

## **64. Action and rollback**

Rollback is an action.

Rollback should be available only when:
    
    
    the changed artifact is rollback-eligible
    prior state is known
    rollback procedure is defined
    trace evidence exists
    rollback does not erase failure history

Rollback is not undoing history.

It is changing current state while preserving evidence of what happened.

Rollback belongs partly to recovery, but action policy must govern it.

* * *

## **65. Action and irreversibility**

Some actions are irreversible or hard to reverse.

Examples:
    
    
    sending message
    deleting data
    publishing output
    modifying external file
    running external command
    revealing private information

Irreversible actions require stronger constraints:
    
    
    higher confidence
    clear scope
    explicit permission
    capability admission
    traceability
    possibly human review

Early systems should avoid irreversible action.

* * *

## **66. Action and interruption**

Operator-facing actions may interrupt.

Examples:
    
    
    asking clarification
    requesting approval
    displaying warning
    asking for review

Interruption has cost.

The system should ask:
    
    
    Is the expected information gain worth the interruption?

A system that asks too often becomes noisy.

A system that never asks may act under uncertainty.

Balance is required.

* * *

## **67. Action and attention**

Human attention is a scarce resource.

The system should model attention cost separately from computational cost.

Examples:
    
    
    minor ambiguity
    → proceed with stated uncertainty
    
    major ambiguity with high wrong-action risk
    → ask clarification
    
    low-risk document continuation
    → act without asking
    
    high-risk external action
    → require explicit approval

This keeps interaction practical.

* * *

## **68. Action and privacy**

Actions may expose or store private data.

Before action, the system should check:
    
    
    does this action store private signal?
    does it send private content externally?
    does it include private content in memory?
    does it reveal internal traces?
    does it pass private data to an LLM?

Privacy risk may block action even when action would reduce error.

Reducing uncertainty does not justify privacy violation.

* * *

## **69. Action and resource regulation**

Some actions regulate machine-body resources.

Examples:
    
    
    reduce polling
    increase polling
    enter low-cost mode
    defer nonessential interpretation
    pause memory compaction
    safe shutdown

These actions manage future viability and error quality.

A resource-regulation action should have measurable expected effects.

Example:
    
    
    reduce polling
    → lower CPU cost but lower signal frequency

This tradeoff should be explicit.

* * *

## **70. Action and safe degradation**

When degraded, the system should not simply fail.

It may select actions that reduce scope.

Examples:
    
    
    disable expensive interpretation
    skip nonessential memory reconstruction
    limit external signals
    prefer internal body monitoring
    request human review
    enter observe-only mode

Safe degradation is action policy under constraint.

It preserves the loop at reduced capability.

* * *

## **71. Action and developmental growth**

Action capability should grow slowly.

Suggested growth order:
    
    
    no-op
    wait
    write trace
    observe internal state
    write memory trace
    adjust polling
    ask clarification
    enter safe mode
    quarantine invalid record
    summarize traces
    read admitted internal file
    write admitted internal file
    use admitted external interface

Do not add powerful external actions early.

The action model must learn from safe actions first.

* * *

## **72. Minimal first action set**

The first prototype should support only a few actions:
    
    
    no_op
    wait
    write_trace
    write_status
    observe_again
    write_memory_trace
    adjust_polling
    ask_clarification
    enter_safe_mode
    safe_shutdown

This is enough.

The system can learn action consequences without broad external power.

The lifecycle should be traceable.

## **79. Action denial**

An action may be denied.

Denial reasons may include:
    
    
    not_registered
    capability_not_admitted
    permission_denied
    boundary_violation
    viability_too_low
    privacy_block
    low_precision_interpretation
    risk_too_high
    traceability_unavailable
    requires_human_review

Denial should be distinct from failure.

Failure means action was attempted and did not work.

Denial means action should not be attempted.

* * *

## **80. Action cancellation**

An action may be cancelled after selection.

Reasons:
    
    
    new signal changes interpretation
    viability changes
    operator cancels
    permission expires
    action becomes irrelevant
    prediction window expires
    safety condition changes

Cancellation should be recorded.

A cancelled action should not be treated as failed action outcome.

* * *

## **81. Action outcome inconclusive**

Sometimes action outcome cannot be evaluated.

Reasons:
    
    
    sensor missing
    operator does not respond
    trace unavailable
    privacy blocks observation
    evaluation window malformed
    external effect unobservable

Inconclusive outcome should not be forced into success or failure.

It should update uncertainty.

* * *

## **82. Action and partial success**

Actions can partially succeed.

Examples:
    
    
    document generated but wrong level of detail
    clarification asked but answer only partially resolves ambiguity
    safe mode entered but some nonessential action remains enabled
    polling reduced but CPU unchanged

Partial success should produce partial match and possibly targeted error.

Do not collapse partial success into full success.

* * *

## **83. Action and causal attribution**

After action, the system should ask:
    
    
    Did my action cause the observed change?
    Was the change external?
    Was the cause mixed?
    Is cause unknown?

Action-outcome match is not always self-cause.

Example:
    
    
    system reduces polling
    CPU falls

Possible causes:
    
    
    polling reduction
    external process ended
    measurement noise
    mixed cause

Self-cause must be earned.

* * *

## **84. Action and self-model**

The system's self-model develops through action.

It learns:
    
    
    what actions it can perform
    what effects actions usually have
    what actions cost
    what actions fail
    what side effects occur
    what conditions block action

This is the operational self.

Not personality.

Not desire.

Not narrative identity.

Action consequence learning is how the machine understands its own agency.

* * *

## **85. Action and operator model**

Operator-facing action outcomes update the operator model.

Example:
    
    
    action:
    ask clarification

Example:
    
    
    action:
    produce long document
    
    outcome:
    operator says keep brief
    
    update:
    operator preference for brevity in this context increases

Operator-model updates should be scoped.

One response should not overgeneralize.

* * *

## **86. Action and project model**

For this document-driven project, producing documents is an action that tests the project model.

Example:
    
    
    belief:
    A-series is the active cognitive-core canon

    generate A08

    project model calibrated

Document generation is not just output.

It is an action that exposes the current model to correction.

## **87. Action and memory model**

Structural priors constrain action policy.

External effect is not required for action.

## **99. Evaluation questions**

Action as future error management should be evaluated by asking:
    
    
    Does every action candidate have an expected effect?
    Is no-op always available?
    Are action candidates evaluated by benefit, cost, and risk?
    Does action selection depend on interpreted observation, not raw signal?
    Does action require permission and capability checks?
    Does viability constrain action?
    Does action produce an outcome record?
    Is action outcome compared against prediction?
    Can action failure update the action model?
    Can action success calibrate confidence?
    Can action be denied, delayed, cancelled, or marked inconclusive?
    Can memory reconstruct why the action was selected?

If not, the action system is not aligned with the cognitive core.

## **108. Final statement**

Action is not output, obedience, tool use, or goal pursuit.

Action is a bounded intervention selected because of its expected effect on future error, uncertainty, information, viability, or model quality.

The system should act only when action is expected to improve the predictive loop under current belief, precision, cost, risk, boundary, permission, and viability constraints.

The final principle is:

A valid action is a registered, bounded, traceable intervention selected from candidates because its expected consequences justify its cost and risk, and its outcome can be observed, compared against prediction, used for belief update, and preserved in reconstructive memory.

That is action as future error management.
