# A01 — Machine Body

**Project status:** cognitive-core canon  
**Purpose:** define the artificial body of the system before sensors, prediction, interpretation, belief update, action, or memory are introduced.  
**Rule:** the system must be treated as a bounded machine body before it is treated as intelligent, autonomous, adaptive, agentic, conversational, or goal-directed.

---

## 1. Why this document exists

The system cannot have cognition in the intended sense unless it first has a body.

Not a biological body.

Not a human body.

Not a metaphorical soul.

A machine body.

The body is the bounded runtime substrate through which the system exists, senses, consumes resources, acts, fails, and persists.

Before the system can ask:

```text
What do I believe?
What did I predict?
What signal arrived?
What action should I take?
What memory should I reconstruct?
```

it must first answer:

```text
What am I?
Where do I exist?
What resources do I consume?
What can I sense?
What can I change?
What can damage or limit me?
What counts as inside or outside my body?
```

The machine body is the first world the system must learn to model.

---

## 2. Core thesis

The core thesis of this document is:

> The system’s first form of embodiment is its bounded runtime condition: process, operating environment, resources, permissions, sensors, storage, trace channels, and action surfaces.

The system does not begin as a mind.

It begins as a bounded process.

It does not first know a user.

It first knows its own runtime condition.

It does not first model the world.

It first models the machine body through which any world-signal must arrive.

In simpler form:

```text
machine body
→ sensorium
→ prediction
→ interpretation
→ error
→ belief update
→ action
→ memory
```

The body comes first.

---

## 3. Short definition

A **machine body** is:

```text
the bounded physical, operating-system, process, resource, permission, storage, sensor, and action substrate through which the system exists and interacts.
```

The body may include:

```text
hardware
operating system
runtime process
container or virtual environment
CPU
memory
disk
clock
battery or power state
permissions
files
trace store
sensors
interfaces
action channels
resource limits
failure modes
```

The body is not just where the system runs.

The body is what makes the system situated.

---

## 4. The machine body is not consciousness

Machine embodiment does not imply consciousness.

The system may have:

```text
body state
resource pressure
sensor input
internal prediction
self-caused action
external disturbance
memory trace
```

without having:

```text
subjective experience
feeling
desire
personhood
emotion
biological need
human-like awareness
```

The project should avoid saying:

```text
the system feels tired
the system wants to survive
the system is afraid of failure
the system has a body like a human
```

Prefer:

```text
memory pressure increased
viability was classified degraded
trace writing failed
resource cost rose
action was denied under current body state
```

The body is operational, not psychological.

---

## 5. The body defines the first boundary

The machine body defines the first boundary of the system.

It answers:

```text
what is inside the runtime
what is outside the runtime
what can be sensed directly
what can only be inferred
what can be changed
what cannot be changed
what requires permission
what requires capability admission
```

A system without a body boundary cannot distinguish:

```text
self from environment
internal from external
action from disturbance
sensor from world
resource state from belief state
```

The boundary is not only a safety rule.

It is also a cognitive condition.

Without boundary, there is no stable self-model.

---

## 6. The first body is local and narrow

The first machine body should be small.

It should not begin with:

```text
network access
camera
microphone
browser
email
calendar
private files
screen control
keyboard control
arbitrary tools
shell execution
```

The first body should be:

```text
one bounded runtime process
inside a declared project root
with limited internal sensors
with limited internal actions
with traceable state
```

The first body is not impressive.

It is inspectable.

That is the correct beginning.

---

## 7. Body layers

The machine body may be understood in layers:

```text
physical layer
operating-system layer
process layer
runtime layer
storage layer
sensor layer
action layer
permission layer
trace layer
viability layer
```

Each layer provides part of the body.

Each layer can fail.

Each layer can produce signals.

Each layer can constrain action.

---

## 8. Physical layer

The physical layer may include:

```text
CPU
memory
disk
battery
thermal condition
network hardware
display
keyboard
mouse
camera
microphone
speakers
```

Early versions may not access most of these directly.

But they still matter because the runtime depends on them.

For the first prototype, physical-layer awareness may be limited to:

```text
CPU load
memory use
disk availability
clock time
```

The system should not pretend to sense what it cannot measure.

---

## 9. Operating-system layer

The operating-system layer may include:

```text
process table
filesystem permissions
environment variables
user permissions
resource limits
signals
scheduling
file descriptors
network status
system time
```

The operating system mediates what the runtime can sense and do.

The system should not assume that being on a machine means it owns the machine.

The host is not the self.

The host is part of the surrounding environment.

The bounded runtime is the first self.

---

## 10. Process layer

The process layer is the immediate body.

It includes:

```text
process id
process alive/dead status
memory allocation
CPU use
open files
current working directory
runtime arguments
environment
execution loop
exception state
```

The first self-model should begin here.

A minimal body-state question is:

```text
Am I running?
```

Then:

```text
Am I running inside the expected boundary?
Am I consuming expected resources?
Can I write traces?
Can I read required configuration?
Can I continue safely?
```

---

## 11. Runtime layer

The runtime layer includes the software loop itself.

It may contain:

```text
current tick
current mode
loaded configuration
loaded schemas
enabled sensors
enabled actions
current belief state
current prediction frame
current trace status
current viability state
```

The runtime layer is where body state becomes cognitive state.

For example:

```text
trace_store_status = write_failed
```

is a body condition.

When interpreted, it may become:

```text
viability risk increased
prediction of successful trace write failed
future adaptation should be restricted
```

The body provides the signal.

The cognitive loop interprets it.

---

## 12. Storage layer

The storage layer includes:

```text
state files
trace files
belief state files
memory traces
configuration files
schema files
quarantine
recovery records
logs
```

Storage is part of the body because it determines what the system can preserve.

If storage fails, memory, trace, belief continuity, and recovery may fail.

Storage should be treated as embodied continuity.

A system that cannot write traces should not behave as if cognition is unaffected.

---

## 13. Sensor layer

The sensor layer is how the body receives signals.

Initial internal sensors may include:

```text
clock sensor
CPU sensor
memory sensor
disk sensor
process sensor
trace-store sensor
configuration sensor
permission sensor
error sensor
manual text sensor
```

Each sensor must be modeled.

A sensor model should define:

```text
what it measures
what it does not measure
how fresh the signal is
how noisy the signal may be
what precision it usually has
what belief targets it informs
what privacy risk it carries
what resource cost it imposes
```

The body does not “know” through sensors automatically.

It receives constrained signals.

---

## 14. Action layer

The action layer is how the body changes itself or its environment.

Initial actions should be minimal:

```text
no_op
wait
write_trace
write_status
adjust_polling
ask_clarification
enter_low_cost_mode
enter_safe_mode
safe_shutdown
```

Later actions may include more powerful operations.

But early body action should be internal, reversible where possible, and traceable.

An action is not just “doing something.”

An action is a body-mediated intervention expected to change future signal, error, uncertainty, or viability.

---

## 15. Permission layer

The permission layer defines what the body is allowed to access or change.

Permissions may include:

```text
read internal config
write internal trace
read internal state
write internal state
read external input
write external output
use model
use network
run subprocess
modify protected config
```

The first body should have very few permissions.

Permission is not the same as capability.

Capability means the system has a structured power.

Permission means the system may use that power in a specific context.

The body must know both.

---

## 16. Trace layer

The trace layer is part of the body because it preserves evidence of the body’s own operation.

The trace layer records:

```text
body state
sensor signal
prediction
interpretation
error
belief update
action
outcome
memory trace
failure
recovery
```

Without traces, the machine body has no durable evidence of its own history.

A trace failure is therefore not merely a logging issue.

It is a body-continuity issue.

---

## 17. Viability layer

The viability layer classifies whether the machine body can continue safe operation.

Possible body viability states:

```text
safe
degraded
critical
failed
unknown
```

Viability depends on body signals such as:

```text
memory pressure
disk availability
trace-store status
configuration validity
permission availability
runtime exceptions
sensor reliability
action failure
```

The body is viable when the runtime can continue bounded, traceable, interpretable, and safe operation.

Viability is not a survival instinct.

It is an operational classification.

---

## 18. Body state

A **body state** is a structured snapshot of the system’s embodied condition.

A minimal body state may include:

```text
body_state_id
timestamp
runtime_id
process_alive
runtime_mode
tick_count
cpu_state
memory_state
disk_state
trace_store_state
config_state
permission_state
sensor_state
action_state
error_state
viability_state
schema_version
```

Example:

```json
{
  "body_state_id": "body_0001",
  "timestamp": "2026-04-29T12:00:00Z",
  "runtime_mode": "normal",
  "tick_count": 12,
  "cpu_state": "normal",
  "memory_state": "normal",
  "disk_state": "normal",
  "trace_store_state": "writable",
  "config_state": "valid",
  "permission_state": "minimal_ok",
  "error_state": "none",
  "viability_state": "safe",
  "schema_version": "0.1"
}
```

The exact schema may change.

The principle should not.

The system must model its body state.

---

## 19. Body signals

A **body signal** is sensor output concerning the body.

Examples:

```text
CPU increased
memory pressure rose
disk available decreased
trace write succeeded
trace write failed
permission denied
config invalid
runtime tick delayed
exception occurred
manual text arrived
```

Body signals should not directly become beliefs.

They should pass through:

```text
signal envelope
interpretation
prediction comparison
precision weighting
belief update
```

A body signal is evidence.

It is not yet understanding.

---

## 20. Body predictions

The machine body should generate basal predictions.

Examples:

```text
next tick should complete
trace write should succeed
memory should remain within range
CPU should remain within range
disk should remain available
config should validate
sensor should report within expected window
action should produce expected body change
```

A body prediction does not need to be complex.

It only needs to define what the system expects before the next body signal arrives.

Without body prediction, the system cannot compute body prediction error.

Without body prediction error, it cannot learn its own operational regularities.

---

## 21. Body prediction error

A body prediction error occurs when interpreted body state differs from expected body state.

Examples:

```text
predicted trace write success
observed trace write failure

predicted stable memory
observed memory pressure increase

predicted tick completion under threshold
observed delayed tick

predicted action would reduce polling cost
observed CPU unchanged
```

Body prediction error should update the relevant model:

```text
trace model
resource model
action consequence model
sensor model
viability model
self-model
```

It should not update unrelated models.

A disk error should not update the operator model.

A user correction should not update the CPU model.

---

## 22. Body precision

Body signals have precision.

Examples:

```text
direct trace write failure: high precision for trace-store state
CPU sample: medium precision for current resource load
single memory spike: lower precision for long-term memory trend
manual text: high semantic potential, but requires interpretation
exception log: high precision for error occurrence, not always for cause
```

Precision affects update strength.

The system should not overreact to one noisy signal.

It should not ignore high-precision failure evidence.

Body learning requires precision-aware update.

---

## 23. Body belief

The system should maintain a body belief model.

It may include:

```text
resource expectations
sensor reliability
trace reliability
action cost estimates
runtime stability
failure patterns
viability expectations
self-caused effect estimates
```

The body belief model answers:

```text
What is usually true about my body?
What body signals are reliable?
What actions affect my body?
What failures recur?
What conditions threaten viability?
```

This is the first belief model.

Before the system models users, goals, or tasks, it should model its own machine condition.

---

## 24. Body action

A body action changes the system’s own runtime condition or body-facing records.

Examples:

```text
write trace
write status
increase sampling
reduce sampling
enter safe mode
enter low-cost mode
clear transient internal flag
quarantine invalid internal record
safe shutdown
```

Body actions are the first actions because they are closest to the system’s own state.

They are also easier to evaluate than broad external actions.

A good first action test is:

```text
If I reduce sampling frequency, does CPU or tick cost change as predicted?
```

This connects body action to body prediction error.

---

## 25. The body and self-model

The first self-model is body-based.

It should include:

```text
what actions I can perform
what effects I expect from those actions
what resources I consume
what sensors report about me
what errors I produce
what state changes I caused
what changes were external
what changes remain unknown
```

The system should not begin with a narrative self.

It should begin with an operational self-model.

Not:

```text
I am an assistant trying to help.
```

But:

```text
I am a bounded runtime process with sensors, resource state, predictions, actions, and traces.
```

That is the correct starting self-model.

---

## 26. The body and external world

The machine body is not the whole world.

It is the system’s interface to the world.

The system should distinguish:

```text
body state
environment state
operator signal
host system condition
external file state
network state
tool output
```

Early versions may only model the body.

Later versions may add external sensors.

But every external sensor should be admitted carefully.

The body is the first world because it is the safest and most direct.

---

## 27. The body and human input

Human input enters the system through the body as signal.

For example:

```text
keyboard input
text message
command file
spoken audio
UI event
```

The system should not treat human input as direct command by default.

Human input is a signal from an external source.

It must be:

```text
captured
classified
interpreted
precision-estimated
compared against prediction
used for belief update or action only when justified
```

A human correction can be high precision.

But it still passes through the cognitive loop.

---

## 28. The body and LLMs

An LLM is not the body.

An LLM may become a semantic organ used by the body.

If used, it is an admitted component that helps interpret signals.

It should not own:

```text
body state
belief state
action policy
memory truth
capability authority
```

The machine body must remain outside the LLM.

The runtime must be able to inspect what it passed to the LLM, what the LLM returned, how that output was interpreted, and whether belief changed.

The LLM is a sensor/interpretation aid, not the organism.

---

## 29. Body failure

The body can fail.

Possible failures:

```text
process crash
trace-store failure
disk exhaustion
memory pressure
invalid configuration
permission denial
sensor unavailable
action failed
schema invalid
clock inconsistency
runtime exception
```

Failure must be modeled.

A body failure is not merely an error.

It is evidence.

It may update:

```text
viability model
resource model
action model
sensor model
recovery model
```

Failure should reduce unsafe action.

Failure should not create new powers.

---

## 30. Body continuity

The system’s continuity depends on preserved body evidence.

Continuity may include:

```text
state continuity
trace continuity
belief continuity
memory continuity
configuration continuity
recovery continuity
```

If continuity is broken, the system must mark it.

Examples:

```text
state reconstructed
memory uncertain
trace gap detected
belief reset
recovery occurred
```

The body should not pretend continuity when its evidence chain is broken.

---

## 31. Body memory

The earliest memory should be body memory.

Body memory stores:

```text
prediction before body signal
body signal
interpretation
prediction error
precision
belief update
body action
outcome
```

Example:

```text
Predicted trace write would succeed.
Trace write failed.
Interpreted as trace-store failure.
High precision.
Updated trace-store reliability downward.
Entered safe mode.
Stored memory trace.
```

This is more important than remembering conversations.

The first memory is how the system learns its own machine condition.

---

## 32. Body development

The machine body may develop over time.

Development may include adding:

```text
new internal sensors
new body-state categories
new low-risk actions
new action-effect models
new viability rules
new recovery procedures
new external sensors
new semantic interpreter
```

But body development must be gradual.

Each new body extension should answer:

```text
What new signal does this provide?
What new action does this enable?
What new failure mode appears?
What new privacy risk appears?
What prediction does it support?
What belief target does it update?
```

No body extension should be added merely because it is useful.

## 36. Body evaluation questions

The machine body should be evaluated by asking:

```text
Can the system identify its own runtime boundary?
Can it distinguish body state from environment state?
Can it sample basic internal resources?
Can it wrap body signals without treating them as truth?
Can it generate basal body predictions?
Can it compute body prediction error?
Can it update body belief from weighted error?
Can it select low-risk body actions?
Can it store body memory traces?
Can it mark body failure and uncertainty?
```

If not, the machine body is not yet implemented.

---

## 37. Incorrect assumptions about the body

Avoid these assumptions:

```text
The body is just the computer.
The body is just the code.
The body is just the process.
If the OS permits it, the body owns it.
If a signal is local, it is self-state.
If a sensor exists, its signal is truth.
If a body action is internal, it is safe.
If a body failure occurs, the system should try harder.
```

Correct assumptions:

```text
the body is the bounded runtime substrate
the host is partly environment
local signals still need interpretation
sensor output is evidence, not truth
internal action can still be risky
failure should reduce unsafe capability
body state must be modeled explicitly
```

## 40. Final statement

The system begins as a bounded machine body.

Before language, tools, goals, memory, or broad autonomy, it must know its own embodied runtime condition.

It must sense its resources.

It must predict its next body state.

It must interpret body signals.

It must compute body prediction error.

It must update body belief.

It must select low-risk body actions.

It must preserve body memory.

The final principle is:

> The machine body is the first self of the system: a bounded runtime substrate with resources, sensors, permissions, actions, failures, and continuity. Every later cognitive layer must remain grounded in this body rather than floating as disembodied language, tool use, or abstract agency.

That is the machine body.
