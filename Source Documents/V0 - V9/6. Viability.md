# v5 — Viability

## 1. What this version IS (conceptually)
A viability-preserving control machine: action policy is grounded in machine-operational health, not free-form objective pursuit.

## 2. What it DOES (in practice)
- **Commands available:** all prior commands, with `viability` as a central operational command.
- **Observable behavior:** computes and stores `state/viability.json` with score/state from CPU, memory, disk availability, error rate, and trace-write success.
- **What changes over time:** viability score/state feeds decision choice and confidence.

## 3. Internal capabilities added
- Viability scoring function (0–100).
- Viability state classification (`safe`, `degraded`, `critical`).
- Decision policy branches tied to viability state.
- Runtime fallback behavior when viability inputs are missing.

## 4. What changed from previous version
- **Added:** explicit viability computation and persistence.
- **Became possible:** deterministic action prioritization driven by operational survivability.

## 5. Why these changes were necessary
Controlled action without viability grounding is arbitrary; viability provides a principled internal criterion for bounded self-maintenance.

## 6. Example run
- **Commands:**
  - `python -m phase0_runtime viability`
  - `python -m phase0_runtime act`
- **Expected behavior:** viability state is computed first; selected action reflects the viability-conditioned policy.

## 7. Limitations
- Viability is narrow (resource/trace health only).
- No broad utility optimization.
- No external objective planning.

## 8. Conceptual interpretation
This is **adaptive control with viability regulation**.

## 9. Transition to next version
What is missing: safe external interaction under explicit governance.
Next version adds: interface registry enforcement and permissioned external read pathway.
