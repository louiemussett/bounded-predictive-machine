# v7 — Tasks

## 1. What this version IS (conceptually)
A bounded task-execution machine: predefined task types coordinate allowed actions under hard step limits.

## 2. What it DOES (in practice)
- **Commands available:** all prior commands plus `create-task --type ...` and `task-run` (and `cycle --tasks`).
- **Observable behavior:** stores tasks in `state/tasks.json` with status transitions (`pending`, `running`, `complete`, `failed`) and per-step records.
- **What changes over time:** task queue, task steps, terminal task status, and task trace events.

## 3. Internal capabilities added
- Task schema validation with fail-closed behavior.
- Predefined task templates and allowed-action constraints.
- Task step execution + terminal condition evaluation.
- Task trace events: `task_created`, `task_step`, `task_completed`, `task_failed`.

## 4. What changed from previous version
- **Added:** bounded multi-step execution abstraction.
- **Became possible:** repeatable operational workflows without adding new action powers.

## 5. Why these changes were necessary
Single-step actions are insufficient for routine operations; tasks provide structure while preserving strict safety constraints.

## 6. Example run
- **Commands:**
  - `python -m phase0_runtime create-task --type maintain_viability`
  - `python -m phase0_runtime task-run`
  - `python -m phase0_runtime task-run`
- **Expected behavior:** task advances through bounded steps until complete/failed according to task conditions.

## 7. Limitations
- No user-defined arbitrary task logic.
- Max steps capped (`<= 5`).
- Tasks cannot expand permissions or mutate interface registry.

## 8. Conceptual interpretation
This is **agent-like bounded execution**, but still constrained and non-open.

## 9. Transition to next version
What is missing: human-operable command channel with structured I/O records.
Next version adds: human-facing command queue and results stream.
